# CI (the iemmixer baseline, copied @ 22372bc)

- **Tier 0:** nothing compiles locally (not even `cargo mutants --list`, which the tier-0 hook blocks); push `dev` and read CI. Locally: `cargo fmt`, `cargo metadata`/`tree`/`update`, `ruff check .`, `python3 -m unittest discover -s scripts -p 'test_*.py'`, `python3 -m unittest discover -s live-script/tests`, `python3 scripts/check_integrity.py`, `python3 scripts/check_version.py`, `actionlint`, and `npx playwright test --list` in `e2e/` (parses the specs, runs no browser).
- **Pinned toolchain** in `rust-toolchain.toml` (1.98.1 + rustfmt, clippy, llvm-tools-preview, wasm32). Every Rust job runs `rustup toolchain install` first. A new stable can add clippy lints: bump it in its own commit.
- **`--locked` everywhere;** tools come prebuilt from `taiki-e/install-action` at pinned versions (trunk 0.21.14, cargo-llvm-cov 0.9.1, cargo-deny 0.20.2, cargo-mutants 27.1.0, cargo-nextest 0.9.146). `Cargo.lock` was seeded from iemmixer's lock so shared crates (Leptos, wasm-bindgen whose CLI Trunk downloads, axum, tokio) run at versions iemmixer's CI already proves.
- **Every `uses:` is pinned to a full commit SHA** with a `# vX.Y.Z` comment (`scripts/check_integrity.py`); no `continue-on-error`, no self-hosted runners, no `pull_request_target`.
- **Placeholder dist:** `fohmixer-hub` embeds `crates/fohmixer-ui/dist/` (rust-embed fails to compile without the folder), so every native cargo job first writes `dist/index.html` = `placeholder`. The router tests serve that placeholder; only `hub-e2e` (the hub of the four `e2e` legs and `companion`, #43), `bundle` and `wasm-stress.yml`'s `build` build the hub with the real Trunk bundle (downloaded from the `wasm` job).
- **A new RustSec advisory turns `supply-chain` red with no code change** (cargo-deny reads the advisory database at run time): on 2026-10-14 four rustls 0.23.45 advisories failed master's run of an unrelated merge. Read the job's `Solution:` lines, `cargo update -p <crate>` (a non-compiling local command, allowed under Tier 0), check `git diff Cargo.lock` moved only that crate, and ship it as its own release; the hub's TLS (rustls) reaches the PC only with a deploy.
- **Coverage floor:** `.github/coverage-floor`, line coverage of `fohmixer-proto` + `fohmixer-hub` + `fohmixer-tray` (`cargo llvm-cov`, the hub's process tests included; the tray's Windows glue is not compiled on Linux).
- **The tray (#39, `crates/fohmixer-tray`):** Tauri 2 and its plugins are `cfg(windows)` dependencies (`tauri-build` a `cfg(windows)` build-dependency, called under `#[cfg(windows)]` in `build.rs`), and the glue `src/tray.rs` is `#[cfg(windows)]`: on Linux the crate is its pure decisions (`args`, `links`, `poll`, `view`, `logs`), built by `lint`, tested with coverage by `test` and mutated by the gate; `tray.rs` and `main.rs` are excluded in `.cargo/mutants.toml`. The `windows` job lints the glue (clippy `-p fohmixer-tray`) and passes the debug tray to `Test-Fohmixer.ps1`; `bundle` builds it in release. It does not run the tray's unit tests on Windows: tauri-build's Common-Controls v6 manifest goes into the binary only (`rustc-link-arg-bins`), and a test binary that links Tauri can die with `STATUS_ENTRYPOINT_NOT_FOUND` (Tauri's own build.rs works around exactly that); the tests are the platform-free decisions, run on Linux. `tauri-build` writes `crates/fohmixer-tray/gen/` on every Windows build (git-ignored). Its icon `crates/fohmixer-tray/icons/icon.ico` (the exe's icon, `tauri-build`'s default path; the tray shows it as the default window icon) is drawn by `scripts/tray_icon.py` (stdlib, uncompressed BMP images so the bytes are stable); `scripts/test_tray_icon.py` fails when the committed file differs. Adding Tauri raised the shared `serde_json`, `toml` and `semver` (their minimums in `tauri-utils` / `tauri-build`'s `cargo_toml`); `cargo update --workspace` adds a new crate's dependencies without touching the rest. The dev box's `/usr/bin/cargo` is 1.75 and cannot read edition-2024 manifests: run the non-compiling cargo commands through rustup's pinned toolchain: the `cargo` first on PATH is rustup's (`/opt/rust/cargo/bin`; there is no `~/.cargo/bin` on this account), which reads `rust-toolchain.toml`, so a plain `cargo fmt --all` / `cargo update --workspace` runs the pinned 1.98.1. A new workspace crate goes into `scripts/check_version.py` `CRATES` (its test compares that list with the workspace members) and into every mutation job's package list. Raise it to `floor(measured) - 2` when coverage grows; never lower it without a reason on the ticket.
- **Python:** the `python` job runs ruff 0.16.2 and the FohMixer tests on Python 3.11, Live 12's embedded Python. Keep the explicit `select` in `pyproject.toml`: ruff 0.16's default rules include pep8-naming, which rejects Live's fixed module names (`Live`, `_Framework`, `ControlSurface`, the `FohMixer` folder).
- **Mutation gate (PR only):** `mutants-list` counts the PR's diff-scoped mutants (`cargo mutants --list --in-diff`, parsed only) and outputs one shard per 4 mutants as the `mutation` matrix, so no shard outgrows its 20-minute budget (a mutant costs ~150 s of build since #17's TLS/ACME dependencies; at 12 per shard two shards ran over; since the Stream Deck (#52) a hub mutant costs ~240 s of build two at a time, and at 8 per shard 9 of 45 shards ran out of the 20 minutes in PR #53; since the Pro-Q 4 screen (#71) a hub mutant costs ~300 s of build and the shard's setup ~3.5 minutes, and at 6 per shard 9 of 136 shards ran out in PR #73, so 4 was 2 rounds plus setup, about 15 minutes; #130 PR 4's 221 hub mutants at 4 per shard (run 39044523754): a mutated hub's build took 269–500 s two at a time and the setup 4.3 minutes, the shards' median 17.2 minutes, 21 of 56 over 19 and 7 cancelled at 20, so it is 2 per shard since: one round with `--jobs 2` plus setup, 9–14 minutes, at twice the shard count; a matrix runs at most 256 jobs, so the gate takes at most 512 diff-scoped mutants now, and `mutants-list` fails past it with `::error::` naming the counts and asking to split the PR; #137 is the follow-up: cut a mutated hub's build cost instead of halving the mutants per shard again); `mutation-warmup` builds the `mutants` profile once and runs the unmutated suite under it. Shards: `--baseline=skip --timeout 190 --jobs 2 --copy-target=true`, then `scripts/mutants_recheck.py` re-tests any catch that was only a timeout (`mutants-recheck` nextest profile, `--timeout 190`); **the 190 s is measured, never a guess (#130 review I2):** cargo-mutants' `--timeout` bounds a mutant's WHOLE test run, so it must lie above the slowest package's unmutated suite, else a survivor reads as TIMEOUT (exit 3) instead of MISSED and a catch by a late test as a false hang (PR #134's first round: two `lonely_lines` survivors at 60 s). `mutation-warmup` measured the hub's 964 tests at 78.8 s (run 39020008838): 156 s of lib and other binaries' work on 4 threads until ~44 s, then the `hub-hosts` group alone, 86 s of real host processes at its 2 threads (`max-threads = 2` keeps their timing checks honest), from ~35 s to 79 s; the largest in-process waits (the Pro-Q probe's real holds, ~92 s, the probe's own timing on the PC) finish by ~32 s, off that path, so a shorter wait there would not shorten the suite, and no ordering gets 242 s of work on 4 threads under ~61 s. 2 x 78.8 s = 157.5 s, rounded up: 160 s (headroom for `--jobs 2`, two suites on one runner). The next two warmups measured 80.3 s (966 tests, run 39026862404) and 78.6 s (966 tests, run 39031854114): ±1 s of noise around 79 s, and 2 x 80.3 s = 160.6 s is past 160 s, so it was 170 s from #130 PR 3 (2x the slowest measured, rounded up to the next 10 s). #130 PR 4 (REVERB AUT, 1.6.0) added three SimLive host tests to the `hub-hosts` group (7.4 s, 5.9 s and 2.0 s of real host time: the 2 s stop wait and 2 s glide are the rule's own timing), and the warmup measured the hub's 1003 tests at 88.0 s (run 39044523754): 2 x 88.0 s = 176 s, past 170 s, so it is 180 s. A shard's 20 minutes still hold (one round of 2, a survivor: ~14 min + 90 s). #104 (AUTOTUNE AUT, 1.8.0) added `tests/autotune.rs` to `hub-hosts`, and the warmup measured the hub's 1093 tests at 90.2 s (run 39603755343): 2 x 90.2 s = 180.4 s, past 180 s, so it is 190 s (the gate, its recheck and `mutation-full.yml`; that PR's survivors ran their hub suite in 91–95 s on a shard). Measure again (the warmup's hub `Summary`) when the hub suite grows past ~90 s, and set it from that, 2x. code that lets a mutant hang or grow memory without bound breaks this (see `.claude/rules/hub-rust.md`). A survivor is work not done: kill it with a test; exclude only browser-only code (web_sys, JS closures, Leptos component bodies) per function in `.cargo/mutants.toml` with a reason. `.config/nextest.toml` runs the bounded `serve_until_answers_then_stops_within_six_seconds` (`tests/serve_until.rs`) first (priority) and gives `fohmixer-hub` 30 s per test (its stop-drain test holds 5 s on purpose). The full-tree sweep is `mutation-full.yml`, on demand only.
- **build.rs (fohmixer-proto):** GIT_HASH from git when it answers, else CI's `GITHUB_SHA` prefix (cargo-mutants' scratch copy has no `.git`), else "unknown"; GIT_BRANCH from `GITHUB_REF_NAME`. The proto tests compare the branch with `GITHUB_REF_NAME` when it is set.
- **Remote access (#17):** the `windows` job runs the DPAPI-sealed secrets' tests (`pepper::`, `sealed::`, `cf_token::`); the `wasm` job checks the service worker is network-only and gated on https; the `e2e` job sets up the test CA, `/etc/hosts` and the Access key (`.claude/rules/remote-access.md`).
- **Hub port tests run one at a time** (`SERIAL` in `tests/serve_until.rs` and `tests/graceful_stop.rs`, the `hub-ports` nextest test group; `cargo test` runs one test binary at a time). Run in parallel, the in-process "the listener is closed" check failed on CI twice (a re-bind, then a connect, right after `serve_until` returned) while the process tests were spawning hubs. The likely causes: a child spawned while another test's listener is open holds a copy of that socket until its exec, and the kernel readily hands a just-freed port to the next bind to port 0 (iemmixer's `free_port_except` exists for the same reason). The process tests start the hub with `PORT=0` and read the port from its `HTTP server listening addr=…` log line — never probe a free port and release it.
- **Read BOTH runs of a head, the push run and the PR run (#43 PR G):** they run the same e2e legs, and a race can pass one and fail the other. The first GREEN head of PR G passed its PR run, while its push run failed on a Chromium zoom race (`touch-guard.spec.ts`). Only the round-1 fresh-context review had flagged that race. A head is green only when both runs are.
- **Never cancel the push run of the PR's head commit** (#21, PR #24): its cancelled checks stay on that commit and GitHub then reports the PR `unstable`, not `clean`; `gh run rerun <id>` makes it green again, one more cycle. Cancel only the runs of commits a newer push superseded.
- **Open the PR right after the first push of a batch:** `mutants-list`, `mutation-warmup`, the mutation shards and `version` run on `pull_request` only, and the shards need `test` green, so a push-only cycle never shows mutation results.
- **A test struct with one field set: spell every field (#43 PR C).** Clippy's `field_reassign_with_default` refuses `let mut x = T::default(); x.f = v;` under `-D warnings` (the `lint` job of 90c0f3a failed on exactly that), and a struct-update base (`..T::default()`) is out too (`.claude/rules/hub-rust.md`); write the literal with every field.
- **Skip fixtures in tests are assembled from pieces** (`scripts/test_check_integrity.py`: `SKIP = ".skip"`, `IGNORE = "#[" + "ignore]"`, also inside expected messages): the fleet's push-time test-skip scan reads a whole `#[ignore]` / `test.skip(` / `unittest.skip` literal in any added test-file line as a real skip and blocks the push.
- **A bump touches only the workspace's own crates in `Cargo.lock` (#3, 1.0.0 → 1.0.1):** since the releases are plain SemVer, a `sed` of `version = "<old>"` over `Cargo.lock` also hits third-party crates at the same version (it changed `defmt-parser` and `winnow` 1.0.0, and `check_version.py` does not notice). Change only the `[[package]]` blocks named `fohmixer-*` without a `source` line, then check that `git diff Cargo.lock` names only those crates.
- **Version bump push (#9):** the fleet's pre-push test check counts `live-script/FohMixer/version.py` as feature code, so a push of the bump alone is blocked unless a commit in the range carries `[no-test: <reason>]`. The hook reads the commits before the command runs: commit in one call, `git push` in the next (never `commit && push` in one command).
- **Prove CI-only reds (#9):** Tier 0 cannot run a Rust, Playwright or PowerShell test locally, so push a batch's `[red]` commits alone first (one cycle, the PR opened) and read the failures before the `[green]` push; the Python reds run locally. Every python test step runs `if: !cancelled()`, so one red suite does not hide another.
- **A `[red]` pushed together with its `[green]` is never seen red (#43 PR D):** a wrong test then shows only as a failing GREEN run (c951403's first upload swallowed the events it was about). When a red cannot go alone, walk the test by hand against the old and new code, and name the gate mutant that stands in for the red (here `+` → `-` of `self.unsent + commas`, caught by the test in the mutation shards).
- **A commit message names only its ticket (`(#9)`), never "PR #18":** the commit gate reads the first `#N` as the ticket and refuses a commit whose "ticket" has no design comment.
- **Core dumps off in the `e2e` job (#9):** the step before Playwright sets `kernel.core_pattern=core` (a piped pattern ignores RLIMIT_CORE) and the Playwright step runs `ulimit -c 0` and fails if the pattern still pipes; a crashed test browser then reports at once instead of freezing through its 15–45 s dump. `crash.spec.ts` checks it on the runner; on failure the `Kernel crash evidence` step adds the pattern, the kernel's segfault/trap lines and `coredumpctl list` to `e2e-logs/kernel/`. The why and the rerun policy: `.claude/rules/e2e.md`.
- **The wasm stress run (#43, `wasm-stress.yml`, `workflow_dispatch` only):** `gh workflow run wasm-stress.yml --ref dev -f loads=1500 [-f jsc="JSC_<option>=<value> ...[; ...]"] [-f only_custom=true]`. `legs` checks the inputs and makes the matrix (`scripts/wasm_stress_legs.py`: the fixed legs, then the `jsc` input's legs, one per `;`-separated group, `custom` or `custom-1`, `custom-2`, ...; `only_custom` runs just those, e.g. the early-tier-up amplifier with each tier off, #43; only `JSC_<option>=<value>` words, loads 1 to 4000); `build` makes the UI (names kept) and the hub once (`wasm-dist`, `hub` artifacts, 7 days); each `stress` leg (`fail-fast: false`, 300 minutes) runs the e2e job's harness steps and `playwright.stress.config.ts` with the leg's settings exported in the Playwright step only, writes its numbers to the run's summary and uploads `wasm-stress-<leg>` (7 days; the hub's event log stays out). The option names come from JavaScriptCore's `OptionsList.h` at the WebKit base of Playwright's build (`browser_patches/webkit/UPSTREAM_CONFIG.sh` of the Playwright tag); JavaScriptCore reads `JSC_*` at start on Linux (`Options.cpp`).
- **The real Companion job (`companion`, #52):** it runs `hub-e2e`'s hub as the legs do (below). `ghcr.io/bitfocus/companion/companion:v5.0.7` pinned by digest as a service container (ports 8000 and 16622; its health check every 2 s, the image's own is every 30 s; the runner starts the steps only once it passes). `e2e/companion/seed.mjs` imports `e2e/companion/test.companionconfig` through Companion's Import / Export page (Chromium; it waits for the sidebar's `v5.0.7`, the tRPC socket the upload needs; closes the welcome and What's New modals with CSS locators: they make the page `aria-hidden`; they can open late on a slow runner, so it clicks "Import Preserving Unselected" in a loop bounded at 60 s: a try a modal blocks gives up after 2 s, the visible closers are clicked, and it tries again), and fails unless the test variables exist (`SEED_TRACE`: a failed seed's Playwright trace goes into the failure evidence; a trace that cannot be written is logged and never hides the seed's own error). `.mjs` and `.cjs` are code to `scripts/check_integrity.py`'s force-kill scan. The export is `e2e/harness/companion_config.py`'s output (`test_companion_config.py` in the `python` job keeps them equal): regenerate it, never edit it by hand. The harness runs with `--companion 127.0.0.1:16622` (no fake), a step waits (30 s) for the hub's `deck_link` `up` record with API 1.12.0 and `/api/status` `companion.online` with 32 keys, and `playwright.companion.config.ts` runs `e2e/companion/*.spec.ts` only, both projects (the specs: `.claude/rules/e2e.md`). Companion's state is read with its HTTP API (`/api/custom-variable/<name>/value`). Core dumps are off for its browsers as in `e2e`, and on failure the same `Kernel crash evidence` step runs (the WebKit crash rerun rule needs it); `docker logs` of the service goes into `companion-failure` with the traces, the kernel evidence and the harness's logs. A new Companion version is a deliberate change: bump the tag and digest together with the site's Companion. Locally (Docker is rootless here: this account is not in the `docker` group) `dockerd-rootless.sh` with its data root in the scratchpad runs the image; the seed and a Python Satellite client prove the Companion side, the hub's side only runs in CI (Tier 0).
- **The E2E legs (#43):** the `e2e` job is a matrix, `project: [chromium, ipad]` × `shard: ["1/2", "2/2"]` (an `include` adds each project's `browser`), named `e2e <project> <i>/<n>`, `fail-fast: false`, each leg its own runner with every setup step of the old single job but the hub's build (`.claude/rules/e2e.md`). Measured before the split (PR #117 and the runs before it): one job 1549–1766 s of `timeout-minutes: 30`, its Playwright step ~1450–1550 s (Chromium ~620 s, the iPad ~870 s; growing ~100 s a day that week), setup ~230 s. The shard list stays on one line and lists every i/n of n (`scripts/check_integrity.py`: a missing shard's tests would never run). The legs build nothing (next bullet); the Playwright browser cache is keyed per browser (`<os>-playwright-<browser>-<lock hash>`; `companion` keeps the key holding both). `master` has no branch protection and no required checks (`gh api repos/<owner>/fohmixer/branches/master`: `protected: false`, 2026-10-14; the protection endpoint answers 403 to the project's token), so there is no aggregate `e2e` check: if a required check is ever added, require the four legs, or add an aggregator job named `e2e` with `needs:` on the legs and `if: always()` that fails unless every leg's result is `success`. A leg near its limit gets another shard, never a longer timeout (`no-timeout-band-aids`); no job `needs: e2e` today.
- **The E2E's hub, built once per run (#43, `hub-e2e`):** a job after `wasm` builds it as each leg did (`cargo build --locked --release -p fohmixer-hub`, `wasm-dist` in `crates/fohmixer-ui/dist`: the release profile, the default features, the UI with its function names embedded), prints its SHA-256 and gives it as the job's `sha256` output, and uploads `target/release/fohmixer-hub` as `hub-e2e` (7 days, as `wasm-dist`). The four `e2e` legs and `companion` `needs: [hub-e2e]`, download it to `target/release`, print their own sum and check it with `sha256sum --check --strict` against that output (a different file fails the job before anything runs), `chmod +x` it (an artifact keeps no file mode) and run it as before. They have no Rust toolchain, `wasm-dist`, Rust cache or cargo step: nothing else in them reads `dist/` or runs cargo (the `wasm-stress.yml` legs, the pattern copied, are the same). Before it each leg and `companion` built the hub itself: 99–151 s of build, 12 s of toolchain and 3–12 s of cache restore, five times a run (runs 38550408251, 38550457314, 38553238446). After it (PR #120's two runs): `hub-e2e` 138–166 s (the build 112–137 s), the legs 315–363 s (Chromium) and 484–555 s (the iPad), `companion` 102–117 s; about 7–11 runner-minutes saved a run, and the critical path is unchanged (the Playwright steps still start ~4–6 minutes into the run). Its Rust cache is `shared-key: e2e`, the key the legs saved under their job id, so the move kept it warm; no other job uses that key. A failed leg's rerun (`gh run rerun <run> --failed`) takes the artifact for as long as a leg could rerun before (`wasm-dist` is kept 7 days too); after that the leg's download fails: rerun the `hub-e2e` job (`gh run rerun <run> --job <its id>`), which reruns the jobs that need it.
