# A plug-in's editor window on the surface (#71, D17, F28)

What the PC tests of 2026-10-09 established (details and evidence on #71). Read this before touching the Pro-Q 4 screen.

## Never in a running Live first

- **Anything that sends input to a plug-in window is proven against the plug-in in a separate host process before it runs in a running Live.** A posted drag into Pro-Q 4.02 inside the band instance was followed by `is_editor_open = false`, and Live crashed: `FabFilter Pro-Q 4.vst3`, `0xc0000409`, Exception Data 7 (`abort`). The lead is FabFilter's own fix of "a crash when closing the interface with a text editor open". Two quick presses on a value field read as a double-click and open that text field. The owner postponed the FabFilter update (#71), so the hub must never close an editor while a text field may be open.
- **The isolated host:** Carla 2.5.10 win64, its bridge alone, on the dummy engine. No audio driver is loaded; check that the process has no `asio`, `audioses`, `mmdevapi` or `wdmaud` module.
  - It lives in the PC's probe folder.
  - Command: `$env:CARLA_BRIDGE_DUMMY = '1'` (exactly `1`), then `Start-Process <…>\Carla\carla-bridge-native.exe -ArgumentList @('vst3', '"<…>\FabFilter\FabFilter Pro-Q 4.vst3"', '""') -PassThru`.
  - Use `Start-Process`, which detaches. `Process.Start` with handles inherited keeps the MCP shell waiting until it times out.
  - The label is `""`; `"(none)"` fails ("Failed to get plugin description").
  - The editor is a top-level `Pro-Q 4 (GUI)` of class `JUCE_…`.
  - Closing that window ends the bridge with `0xC0000005` whatever the plug-in's state, so this host cannot reproduce the close crash.
- **Every injection checks the target first:** the point's window (`WindowFromPoint` → `GetAncestor(GA_ROOT)` → owner PID) must belong to the host meant, never to Live by accident.

## What Live gives

- **Opening and closing:** `PluginDevice.is_editor_open` (get / set / observe, Live 12.4.3+) opens and closes a plug-in's editor. It reads on the PC's 12.4.6 through the FohMixer script's generic `get_prop` / `set_prop`, for a device on a track and one inside a rack chain. Two editors can be open at once in one instance.
- **Identity:** `class_display_name` is the plug-in's product name (`Pro-Q 4`). It holds even when the device is renamed; `name` is the device's name.
- **The window:** a top-level `Vst3PlugWindow` titled `<device>/<track>`. The title holds a track name, so never log or print it. Pro-Q's own UI is one child, `FF_UIWindow`, at (8, 31), 1349×809 at 100 %. Find the new window by comparing the window list before and after the open; Live does not make it the foreground window.
- **Parameters:** Live exposes only one Pro-Q 4 parameter (`Device On`) unless the owner configures them in Live, so the EQ is driven through the window, not the parameters.

## Capture

- `PrintWindow(hwnd, hdc, PW_RENDERFULLCONTENT)` gives the whole editor even behind other windows, in about 17 ms per 1365×848 frame. It renders on the window's thread, which is likely Live's, so it is the fallback only.
- **Windows Graphics Capture** (the `windows-capture` crate, MIT) reads the DWM surface instead.
  - On the PC's Windows 10 19044 its yellow border cannot be switched off (needs 20348).
  - A fully off-screen or minimised window gives no frames.
- JPEG q75 of a frame: about 5 ms and 62 KB (System.Drawing), so about 2 MB/s at 30 fps.

## Input

- **Posted mouse messages** to `FF_UIWindow` give hover (`WM_MOUSEMOVE`), clicks (`WM_LBUTTONDOWN` / `UP`) and the wheel (`WM_MOUSEWHEEL`, screen coordinates). They give **no drag**, because FabFilter reads the real cursor and button state.
- **A real drag is injected touch** (the owner's decision on #71):
  - Use `InitializeTouchInjection` / `InjectTouchInput`, or the synthetic-pointer API: DOWN `INRANGE|INCONTACT|DOWN`, UPDATE `INRANGE|INCONTACT|UPDATE` every ~16 ms (re-send the last point at least every 100 ms while the finger rests: Windows cancels a contact that gets no frame for 100 ms; the hub's window worker re-sends every 50 ms), and UP `UP` at exactly the last point.
  - **Never set `POINTER_FLAG_PRIMARY`**: every call then fails with `ERROR_INVALID_PARAMETER` (87).
  - `POINTER_TOUCH_INFO` is 144 bytes, `POINTER_INFO` 96.
  - The editor must be the window at that screen point.
  - The system cursor follows the contact; put it back with `SetCursorPos` after the gesture.
  - A real-mouse drag (`SendInput` / `mouse_event`) works too.
- **On Pro-Q 4:**
  - A single tap on the curve creates nothing; a double-click creates a band.
  - A touch drag that starts on a band moves it.
  - **A double tap on a band opens its frequency text field**: the close-crash state.

## The Pro-Q 4 screen (#71 PR E)

The surface's side (the cards and the screen) is in `.claude/rules/ui-rust.md`, its E2E in `.claude/rules/e2e.md`. Nothing of it has run against a real window yet: the PC check (the plan's task 7) first runs `eq-probe` against Carla's bridge, then the first open in the band Live.

- **Protocol** (`fohmixer-proto` `client.rs`, `eq.rs`):
  - The page sends `eq_list {binding}`, `eq_open {instance, path}`, `eq_input {touch: down|move|up|cancel, x, y}` (the picture's pixels, floats) and `eq_close`.
  - The hub answers `eq_list {binding, items: [{path, place, name, picture}], error}`, `eq_locks {items: [{instance, path, mine, since}]}` (to every page at each change, and at the hello) and `eq {instance, path, state: opening|open|closed, session, width, height, reason, since}` (to the holder).
  - `reason` is `locked` (that editor is another client's, with the holder's `since`), `in use` (another client holds another editor, with its `since`: one on the PC's screen at a time, round-3 ruling), `unknown` (not in a list this hub gave), `off`, `exit`, `detach`, `switch`, `window closed`, `closing`, `moved` (the open's read found another device or name at the listed path: list again), `open on the PC` (its editor is already open in Live), `unread`, and (round-2 review) the open's failures: `instance offline` and `Live did not answer` (an open's or a list's call through the script got no answer: `router::eq::live_reason` maps `LiveError::Offline` / `Timeout`; a refused request keeps its words), `unknown instance`, `no window`, `several windows`, `NO_PICTURE` (the window has no `FF_UIWindow`), `the window did not come on top` (`NOT_ON_TOP`, round 3: the take's posted z-order change never landed within `FIND_MS`), `the window worker stopped`; a list's `the devices nest too deep` (`TOO_DEEP`); and `left open in Live`, the holder's closed reason only when its close may have left the editor open in Live (`close::Shut::LeftOpen`: the guard could not tap, the ref's turn-off failed or got no answer, the path check was not certain, the set at the path failed; the `closed` record keeps the close's own why). A close that found nothing of the hub's open in Live (`Shut::NoneOpen`: the device deleted, or no open Pro-Q 4 after a move) keeps its own reason (round 3). Every one is a constant in `fohmixer_proto::eq::reason` (the hub's `plugwin::NO_WINDOW` / `SEVERAL` / `STOPPED` / `NOT_ON_TOP`, `win::NO_PICTURE` and `router::eq::UNKNOWN_INSTANCE` / `TOO_DEEP` are those constants) with its Slovak sentence in the UI's one table (`behave::eq::reason_text`), read by a card's note (`failure_text`; `locked` and `in use` are quiet there: the card's lock says it) and by the cards' list note (`list_text`); anything else is a failure's own text.
  - **The frames are binary WebSocket messages:** 4 bytes of the session (big-endian), then the JPEG (`eq::frame`, `eq::frame_parts`). The outbox keeps only the newest frame (`Outbox::eq_frame`, one slot), and the writer sends it after each text batch, so a slow link drops frames and never queues them. A closed `eq` forgets a waiting frame. The page drops a frame whose session is not its open editor's.
  - **A card's last picture:** `GET /api/eq/picture?instance=&path=` with the token (`image/jpeg`, `no-store`; 404 before a first frame). The CSP allows `img-src blob:`.
- **Discovery** (`eq/walk.rs`): the strip's track is walked through the script's `get_prop`, one batch per level. A device of the script's class `PluginDevice` whose `class_display_name` is `Pro-Q 4` is listed (`PRODUCT`; it holds when renamed) with its `$ref` (`Found::id`, from the list answer's item, `walk::Item`). A `RackDevice`'s chains are walked down to 3 racks deep (`MAX_RACKS`), 8 batches a walk at most (`MAX_READS`). The path is Live's index form (`live_set tracks 1 devices 1 chains 0 devices 0`), the place `Vocal FX › Main`, or `na tracku`. A path not in a list the hub gave is refused (`unknown`).
  - The state keeps each list on its own, by instance and the track's LOM target, with each device (`eq::Device`: its name and `$ref`; `Eqs::listed`, `name_of`). A track's new list replaces its last one and takes the paths it names from every other list: a path belongs to the newest list that names it (a track or a device moved, so a strip not listed since may still hold the path of the device another strip has now; with the first list in map order an open of that other strip compared its device with the stale name and was refused `moved`, round-2 review).
  - **A card's picture is its device's** (round 3): after every list and every connect the router hands the cards' pictures the device each listed path names by its `$ref` (`Eqs::named` → `Pictures::named`): a picture whose path names another device now, or none, goes. By `$ref`, not by name: two Pro-Q 4s that keep their default name change places when a track moves above them. The frame sink puts a picture only while its path still names the device the open read (`Pictures::put` with the open's ref, `open::ref_id`), so a captured editor whose device moved away no longer brings it back with its next frame.
  - **A connect forgets** (`Router::eq_connected` on `LiveEvent::Connected`): the instance's lists (so its cards' pictures, through `Pictures::named`) and its editors' refs. On `Connected`, not `Disconnected`: another set and the script's new registry show only from the new connection on, and a walk answered from the old one after its `Disconnected` would otherwise list old paths again.
- **The state** (`eq.rs`, pure, tested):
  - **One editor on the PC's screen at a time** (round-3 ruling; the owner allowed it on 2026-10-09): the PC has one screen and one cursor, and two taken editors are both on top and overlap at 1349 × 809 (a picture showing the other's pixels, refused touches, a covered inert spot). While a client holds any editor (waiting for its switch, opening, open or closing), another client's open is refused: that editor `locked`, any other `in use` (`Eqs::in_use`). The same client's open of another editor switches (its own closes first, `switch`). So one open runs at a time (started at once, or once its client's switch closed: `Eqs::start`; no queue) and one finger is on the screen. The pages' cards all read ZAMKNUTÉ meanwhile (`behave::eq::card_lock`: `InUse`). Faders, mute and pan stay free for everyone.
  - **Contacts are numbered** (`Eqs::contacts`, one counter): the number rides `Act::Touch`, `Command::Touch` and `PlugwinEvent::ContactEnded`, and `contact_ended` ends only that session's contact of that number (a late word of an older contact never ends a newer one).
  - A resting contact is the window worker's to keep alive (below); the router re-sends nothing.
  - A holder silent for 2 s (`SILENT_MS`: no message at all, pings included) gets its contact cancelled (the router's tick, `deck::TICK`).
  - A detached page's editor closes (`detach`).
  - Records go to the event log as `eq` (warn class): `take`, `open`, `opened`, `touch` (down, up, cancel; never a move), `silent`, `close` (why), `closed`, `lost`, `failed` (why: `moved`, `open on the PC`, …), `refused` (why: `unknown`, `locked`, `in use`), `problem` (the close may have left the editor open in Live), `none_open` (the close found nothing open: its device deleted; a path check that finds no open Pro-Q 4 after a move is a `problem` instead, since the editor may sit deeper than the walk looks), `moved` (with `to`, only from the fallback path check), `contact_ended` (with `contact`), and once a minute per editor `rate` (grabs, sent, failed, grab and encode ms, bytes, size, `gap_ms`: the largest gap between two injections of a contact).
- **The open's read** (`eq/open.rs`, pure, tested; `open_editor`): before `is_editor_open = true`, one batch reads the device at the listed path: `class_display_name`, `name`, `is_editor_open`, and its parent's `devices` (the item at its index, when its `path` is the listed one, gives the device's `$ref`; the script registers every object it encodes).
  - Not a Pro-Q 4, or not the name the list found there: refused `moved`.
  - Its editor already open in Live (opened on the PC, left open by a failed guard or the hub's stop): refused `open on the PC`. The hub has no window of it, so it never takes it and never turns it off without the guard; adopting an already-open window is not done (the page says to close it on the PC).
  - Else the editor is opened through the `$ref` (`{"$ref", "class": "PluginDevice"}`), and a take that fails turns it off again through the ref (this open turned it on: the read found it closed).
- **The close sequence** (`router/eq.rs` `close_editor`), in this order:
  1. The guard: its editor looked up first (a guard of a window already lost fails at once and ends no contact: round-2 review), then its own contact ends at its last point (an up), another session's contact is cancelled at its last point and reported (`ContactEnded`, why `GUARD_CANCEL`: the PC injects one contact, so the tap would fail or end the other engineer's drag), the frames stop, and the inert spot is tapped (down, 30 ms, up). This closes a text field Pro-Q 4.02 may have open.
  2. A wait of 300 ms (`GUARD_WAIT`).
  3. `is_editor_open = false`, **only if the guard succeeded.** A failed guard leaves the editor open in Live (`problem`), never closed with a field possibly open. What the close left in Live is a `close::Shut`: `Off`, `NoneOpen` (nothing of the hub's open there: its holder hears its own close, record `none_open`) or `LeftOpen` (its holder hears `left open in Live`, record `problem`; round-3 review).
     - **Through the `$ref` the open read** (`EqIo::refs`, per session; `RouterMsg::EqOpened` carries it; kept only for the editor of that session, and only when its instance did not connect again since the open began: `Act::Open` and `EqOpened` carry the instance's connection number, `Eqs::connection`, which each connect counts up, since the script registers objects by Live pointer and a pointer registered anew can name another object; round-2 review; dropped when the close ends, the window is lost, or the instance connects again): the same object wherever it moved, so a close never turns off another engineer's editor that moved onto the held path.
     - **A ref turn-off that got no answer or failed otherwise** (Live offline, a timeout: its thread busy, and the set may still land; a refused request; any answer but the two below): Live is left alone (`LeftOpen`, `close::ref_failed`), never the path check, which takes any open Pro-Q 4 at the held path (another engineer's after a move; round-2 review). `close::ref_off` reads the answer (pure, tested).
     - **A ref whose device was deleted** (the script answers `errorType` `StaleRef`, `deleted` / `class changed`: `close::STALE_REF`; the pointer holding another class means the device went too): Live closed the editor with its device, so Live is left alone with nothing open (`NoneOpen`, `close::deleted`), never the path check: the held path can then only name another device (the one now at that path, its editor maybe open: turned off without its guard, the close-crash path; round-3 review).
     - **The fallback, only when the script does not know the ref or none is held** (`errorType` `UnknownRef`, `unknown id`: each connection starts a new registry, `close::UNKNOWN_REF`; no ref after a reconnect): the path check (`eq/close.rs`, pure, tested; `check_close`). The held path is Live's index form, which a track or device moved above it points elsewhere. One batch re-reads the device at the held path (`class_display_name`, `is_editor_open`). If it is still a Pro-Q 4 with its editor open, it closes there. Otherwise the set's tracks, return tracks and master track are walked for their Pro-Q 4s (the list's walk, bounded the same way, one track after another: only the fallback runs it) and their `is_editor_open` read in one batch. Exactly one open: the moved editor, closed at its new path, logged as a warning and recorded as `eq` `moved` with `to`. None open: nothing to close (`Check::NoneOpen` → `NoneOpen`). Several open, or any read or walk that failed: Live is left alone (the window is still handed back) and the router records a `problem` with the reason.
  4. The window handed back: its z-order put back, and, unless the editor may still be open in Live (`Off` or `NoneOpen`), `Backend::live_closed` (the sim closes its window then).
- **The inert spot:** `plugwin::INERT_X` = 0.405 of the picture's width and `INERT_Y` = 15 px from its top: (546, 15) at 1349 px. This is the top bar's empty middle in the mockup's picture: right of the logo panel (which ends at about 534) and left of the undo icon (about 564). The PC check confirms it (`eq-probe` saves `after-guard.jpg`). If it hits something, try `--inert` at the wide empty area right of Help (about 1100–1300, 15) and change the constant.
- **The window worker** (`plugwin.rs`): a std thread owning the `Backend`; the router talks to it over a channel.
  - **Open:** list Live's editor windows, set `is_editor_open = true`, then poll every 50 ms for up to 3 s for the ONE new window. Several new windows fail (`several windows`); none fail (`no window`). One new window the backend cannot take yet (`Backend::ready`: the hub's Windows take wants Pro-Q's `FF_UIWindow` child, which Live's window may get a moment after it shows) is awaited too, and fails `NO_PICTURE` only when the wait is over (`plugwin::found`; round-2 review: it failed on the first poll before). If the take fails, the editor is turned off again through its ref (above).
  - **Take:** the window topmost (nothing moved or sized). The z-order change is posted (`SWP_ASYNCWINDOWPOS`), as the release's: the window is Live's, and a synchronous `SetWindowPos` of another thread's window waits for Live's UI thread, busy exactly around an editor's open. **The take answers only once the window is on top** (round-3 review): the posted change lands when Live's thread takes it, and until then another window may cover the editor (a grab shows its pixels, a touch there is refused). The taken window waits in its open (`Finding::placing`) and is looked at every step (`Backend::on_top`: the Windows backend reads `WS_EX_TOPMOST` with `GetWindowLongW`, which sends no message); on top, it becomes the worker's editor and the take answers its size; not on top `FIND_MS` after its take, it is handed back and the open fails `NOT_ON_TOP` (`plugwin::placed`, pure). Until it answers it is no editor of the worker's, so nothing grabs or touches it; the stop hands back a window still waiting.
  - **Capture:** every 40 ms; the worker grabs and skips a picture equal to the last one. A new picture goes to the **encoder**, a thread of its own (`Encoder`): JPEG q70 through `jpeg-encoder` (pure Rust, `simd`; its IJG licence part is a `deny.toml` exception) to the sink. One picture waits at most, the newest (`Handoff::waiting`; a slow encode drops pictures, never queues them). The encoder reports what it made (`Encoded`: ms, size or a failure) before the sink gets the frame; the worker counts it at its next step (`Counts::grabbed` / `encoded`, pure). The guard, a release and a lost window drop a waiting picture of that session, and a frame being encoded for it never reaches the sink: the encoder hands a frame over only while its session is captured (`Handoff::captured`, `Encoder::capture` / `forget`; `deliver` checks, reports and calls the sink under the hand-off's lock, so a forget never lands in between; round-2 review); the encoder ends with the worker (stopped, joined). What blocks the worker: the grab, and the window list and its checks (`EnumWindows`, an open's polls, a take); z-order changes are posted.
  - **A contact:** a down goes only when no contact is down, any other phase only of the contact held (`accepts`, by session and number): an update of a contact the worker already ended is dropped, never injected without a down. A down dropped because another contact is still down is reported (`ContactEnded`, why `plugwin::BUSY`): the state let it go after it ended that one (a close's `close_key` clears the state's contact before the guard ends the worker's), so it must forget it again (round-2 review).
  - **Keep-alive:** a resting contact's last point is injected again once `KEEPALIVE_MS` (50 ms) passed since its last injection (a down, an update or a keep-alive). Each step (at least every `STEP`, 10 ms) looks at it first, again after the opens' polls and again after each grab, every time on a fresh read of the worker's clock (`Worker::now`): a grab blocks for its time (a BitBlt of ~4.3 MB), and several editors are grabbed one after the other (the worker takes several; the hub holds one at a time since round 3), so a look only after the step's grabs, on the step's first clock, let a resting contact go ~150 ms silent with two 35 ms grabs (round-2 review). An injection is stamped when it goes, so `gap_ms` holds the time a grab held it up. The worker's tests run it on a thread-local clock (`step_at`, `command_at`; a slow backend's grab moves it on). A refused keep-alive ends the contact like a refused update (a cancel, `ContactEnded`). The largest gap between two injections of a contact is the minute's `gap_ms`.
  - **Lost:** a window that went away (closed in Live or on the PC) releases the editor (`window closed`).
  - **The stop:** the router's end sends `Stop`; the worker ends any contact and hands every window back (the editors stay open in Live). `serve_until` awaits `HubInner::plugwin_stopped` after the Companion's wait: `Plugwin::stopped` polls the worker thread's `JoinHandle`, bounded (`STOP_WAIT` = 1 s), holding it under an async lock (`tokio::sync::Mutex`, so a second caller waits for the first's answer and never answers early; round-2 review), and a worker still running is a warning.
- **The Windows backend** (`plugwin/win.rs`, `cfg(windows)`, out of the mutation gate):
  - Calls run per-monitor aware (`SetThreadDpiAwarenessContext`, PMv2), so every coordinate is a physical pixel.
  - Editors are Live's top-level `Vst3PlugWindow`s; the picture is the `FF_UIWindow` child. The hub's backend (`Win::for_hub`, `win::hub_backend`) is not `ready` for a window without that child (the worker polls on until it comes or the wait is over), and its take refuses one still without it before it touches it (Live's other instance's window, a plug-in opened by hand at that moment); the probe's (`Win::new`, `win::probe_backend`) takes the client area then. Both constructors live in win.rs, out of the mutation gate with the rest of the Win32 glue.
  - Grab: `BitBlt` of the picture's screen rectangle from the screen DC, then `GetDIBits`. Nothing runs on Live's window thread. This is not `PrintWindow`, and not WGC (its border cannot be switched off on the PC's Windows 10).
  - Touch: `InitializeTouchInjection(1, TOUCH_FEEDBACK_NONE)`, then the flags above (a cancel is `UP|CANCELED`). The contact area is 4 × 4 px (`TOUCH_MASK_CONTACTAREA`). `ERROR_NOT_READY` is retried after 1 ms, twice.
  - A down or an update checks the point's root window and its process first. An up or a cancel goes at the last screen point injected (`Win::last`, `end_point` / `last_after`), not mapped from the window again and not checked: a window gone or moved still ends the contact where it was. The cursor is put back when the contact ends and when a down fails with no contact before it (`win::restores`); a failed update or keep-alive of a contact still down keeps it saved, since the worker's cancel at the last point follows (it moves the cursor there again) and that end puts it back (round-2 review). A window lost under a contact gets a cancel, which puts it back too.
  - `contact()` spells every field of `POINTER_INFO` / `POINTER_TOUCH_INFO` (no struct-update base).
- **Configuration:** `[eq] backend = "windows" | "sim" | "off"`. **Live's windows are never the default:** `off` on Windows, `sim` elsewhere (the tests and the E2E harness); `windows` off Windows fails the config check (`config.rs`; the Windows default is tested in the `windows` CI job, `config::tests::eq_backend`). `off` answers every list with the error `off` and every open closed with `off`; the page's cards then say "EQ je na PC vypnuté." (`behave::eq::list_text`, a plain note). The PC turns the screen on only by writing `[eq]` / `backend = "windows"` into its `fohmixer-hub.toml` after `eq-probe` passed against Carla's bridge (the steps, and that every install drops the table again: `.claude/rules/deploy-pc.md`).
- **The simulated backend** (`plugwin/sim.rs`): the hub's backend off Windows, in the tests and in the E2E harness.
  - Its windows follow Live's editor state as far as the hub changes it: asking Live to open an editor opens a window (`live_opened`); the window closes only when Live closed the editor (`live_closed`, after a release whose turn-off went through). A failed guard, a close check that left Live alone and the hub's stop leave it there. An editor already open in Live is modelled by SimLive's `is_editor_open` (the open's read refuses it).
  - Its picture is 1349 × 809 with a counter that steps every 250 ms, so frames differ; it is drawn once per count and size (a test build's grab stays cheap). Pro-Q's child is there unless a test holds it back (`child_late`: `ready` is false and the take refuses with `NO_PICTURE`, as the hub's Windows take).
  - Every take, touch (phase, x, y, and `t`: ms since the sim started), release and close is recorded in memory and in `<data>/eq-sim.jsonl` (the harness's `GET /sim/eq`).
  - A test can make it refuse touches (`refuse`), open no window (`auto_open`), make each grab take its time (`grab_delay`), hold Pro-Q's child back (`child_late`) or hold a take's place on top back (`topmost_late`: the change waits in `posted` and lands when the switch goes off; a release before drops it; `on_top` reads the window's `topmost`).
- **`eq-probe`** (`plugwin/probe.rs`; `fohmixer-hub eq-probe`): the isolated check on the PC, run against Carla's bridge (above) before any Live.
