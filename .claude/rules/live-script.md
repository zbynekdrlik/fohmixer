# FohMixer script and SimLive (learned on #9)

- **The transport is single-threaded: all socket I/O runs on Live's main thread, in the timer tick (#5).** `surface._on_timer` calls `Server.poll_in` (accept, handshakes, frames into the inbox), the drain, the subscription flush, the heartbeat, then `Server.poll_out` (each connection writes as far as its socket takes it, the rest waits in its write buffer for the next tick). Every socket is non-blocking and `select` has timeout 0; only `shutdown` (Live unloading the script) waits, up to its 0.3 s grace. Why: K1 measured the old threaded transport (ableton-js v5: an accept thread, a reader and a sender thread per connection, a heartbeat thread) on the real Live: those threads got Python only around the main thread's ~30 Hz tick, so a connection sent about one frame per tick, a result waited whole ticks (the quiet master Live 1–4), frames left in bursts one tick apart (#5 comments 5885877068, 5888410684). Never add a thread to the script: in Live it does not run between ticks.
- **Output priority** (`transport/server.py` `Connection._take_next`): the pending heartbeat, then results and events in order, then the values map as one frame, then (closing) the close frame. At most `WRITE_AHEAD_BYTES` (64 KB) are encoded ahead of the socket, so a heartbeat waits only behind those, never behind queued results: a late heartbeat makes the hub report Live busy. `test_transport` sizes its check from the kernel's `tcp_wmem`. Per tick and connection, reads and writes each go on while the socket has data / takes bytes, within `IO_BUDGET_S` (5 ms, `time.perf_counter`: Windows' `monotonic` moves in 15.6 ms steps); a byte cap instead held one large message, and the heartbeat behind it, for several ticks. The budget is per connection: with the hub (and a probe) a tick spends a few ms at most; the caps below bound a misbehaving local client, they are not a load target.
- **One client's failure closes that client only** (`Server._fail`: logged with the traceback), and `_on_timer`'s five steps (reads, drain, subscription flush, heartbeat, writes) are guarded one by one: a step that keeps raising must not stop the others (a stopped heartbeat shows Live busy for ever). JSON nested too deep (`RecursionError`) is an invalid-JSON error reply like any other. `accept()` errors that are not the listener's own (`ConnectionError`, WSAECONNRESET on Windows, and the network errors accept(2) says to treat like EAGAIN) take the next client, EMFILE and the like wait a tick; only the rest rebind: on Windows an SO_EXCLUSIVEADDRUSE port cannot be bound again while the hub's connection lives. At most 64 clients, of which 16 still in their handshake (one `select` per tick; FD_SETSIZE is 512 on Windows). Warnings that could repeat every tick (accept failing, clients refused) are logged once a minute per kind, with how many were left out (`Server._warn`).
- **Every accepted socket the server closes is reset** (SO_LINGER 0: `reset_close`, `Connection._finish`), a refusal, a 400 and a dropped handshake too: a FIN leaves a TIME_WAIT on the port, and Windows keeps an SO_EXCLUSIVEADDRUSE port busy while connections accepted on it are closing, so a set reload could not bind (`test_transport` checks `/proc/net/tcp` for none).
- **`connect` is always the first frame:** the 101 response and the `connect` frame go into the new connection's write buffer at the handshake, before anything a tick queues. (The old script could send a heartbeat first, seen on the PC; the probe still skips one, for a Live that runs the old script until its restart.)
- **A client that stops reading** is closed by the bounded result queue (`RESULT_QUEUE_MAX`), or once its socket took no byte for `SEND_STALL_S` (3 s) while output waited ("the client read nothing for 3.0 s" in the log; the hub resyncs). The drain then skips that client's remaining requests (`Drain.run`: `if not conn.is_open`).
- **The heartbeat is made in the tick, after its work** (`surface.Heartbeats`, one per `HEARTBEAT_INTERVAL_MS` on a fixed grid, so ~33 ms ticks still give 10/s): `main_tick_age_ms` is the silence since the previous tick reached the same point (normally one tick interval; a tick held by a slow command counts too, or its own heartbeat would report a short gap and the hub would flap); `gap_ms` the time since the previous heartbeat. During a stall no heartbeat goes out (the hub's 300 ms overdue check marks Live busy); the first one after it reports the stall in both fields (the hub logs a late heartbeat with its `gap_ms`, `hub-rust.md`).
- **Test the tick by hand:** with no SimLive `MainThread` installed, `Live.Base.Timer` is inert, so a test thread can be Live's main thread and call `surface._on_timer()` (`test_surface.HandTickedSurfaceTest`) or `server.poll_in()`/`poll_out()` (`test_transport.OneTickTest`) itself; `_rawclient.RawClient` reads only when the test says so. That pins what one tick does and that nothing moves between ticks. Timeouts are tested on explicit times (`Connection.flush(now)`, `Server.poll_out(now)`; the surface passes no time, so the real one), never by sleeping and bounding the elapsed time; a hand-ticked surface runs with a drain budget no command reaches (`DrainTest` pins the budget). With a `MainThread` running a timer, push to a connection only through `mt.call` (one thread touches the server). #5's review ran the hand-ticked tests on a CPU shared with two busy loops (`taskset`) to find the ones that leaned on the machine's speed.
- **A test of one rule keeps the transport's other rules from deciding it (#5).** The send stall races any test that fills a stuck client's socket: under load it closed the client before `fill` saw a queued result, and it dropped the integration test's client C before C's last request ran (the drain then skips the rest), so the push the test waited for never came. The remedies: `TransportTest.write_at` holds the timer ticks' clock (`poll_out(now)`) while the socket fills, `wait_stuck` waits for a tick that wrote nothing, then the clock moves to just before `SEND_STALL_S` (still open) and from `SEND_STALL_S` on by `SEND_STALL_S` until the stall closes it: after a tick that wrote nothing the kernel can still take a trickle of bytes (its send buffer grows by autotuning), each one progress at the held time, so a single step to `SEND_STALL_S` could land just after the last progress (#43, CI run 37221318449); the exact boundary is `OneTickTest`'s, whose `stall_closes` takes the trickle too (CI of a38d97a, #68: a trickle in the `SEND_STALL_S - 0.01` flush kept the connection open at `SEND_STALL_S`): a write that takes bytes is progress at its time and the boundary is checked again from there, a write that takes nothing must hold it exactly (the `>`, `SEND_STALL_S - 0.02` and default-clock-0 mutants still fail it); the queue-bound test runs with `SEND_STALL_S = math.inf`; the integration test waits until C's last request ran *or* the script dropped C, whichever comes first.
- **Running these tests locally:** the box's `python3` is 3.12 without `websockets`; make a Python 3.11 venv outside the repo (`uv venv --python 3.11 <dir>`, then `uv pip install --python <dir>/bin/python -r requirements-dev.txt ruff==0.16.2`) and run `python -m unittest discover -s live-script/tests` with it, as CI does. Format-check the paths CI checks (`ruff format --check live-script sim tools e2e/harness scripts/cloudflare`): `ruff format --check .` also reads `scripts/` files CI leaves as they are.
- **Read the script's goodbye through `_rawclient.RawClient.read_until_closed`, never `websockets`' sync client (#5).** That client's reader thread holds each message until the test reads it. If a heartbeat the test has not read yet is waiting when the script closes, the reader cannot answer the close within the script's 0.3 s shutdown grace, and the script resets the socket. The client's close reply then fails, and websockets drops the `disconnect` it read along with the close frame (`sync/connection.py`: "events are lost"). A `websockets` client is safe only where nothing but the goodbye itself can wait unread at the close, as in `test_transport`'s server tests, which have no heartbeat. The raw client decodes with the script's own codec, so a raw-client test checks close frames against the RFC 6455 values pinned in `_rawclient` (`CLOSE`, `EMPTY_CLOSE_FRAME`, the frame's `head` bytes), never the script's `OPCODE_CLOSE`: only a pinned value catches a wrong opcode or header bit.
- **Prove a timing flake by making its window certain,** then run the fix through the same window. In #5, 220 loaded runs never hit the lost goodbye, while a 250 ms wait before the script's disconnect failed the old tests 5 of 5. The stuck-reader races were made certain from outside the tree: `test_transport.time` swapped for a shim whose `fill` step sleeps 0.4 s (or 3.2 s), and a `sim/host.py` wrapper whose commands each sleep 3 ms (the stall unchanged; shortening the stall instead also shortens C's stuck time, which the heartbeat count needs). When a test is rewritten, run the behaviour mutants too: every mutant the old test catches, the new one must catch as well, or a named test that pins that rule on explicit times; a catch that came only through the race being removed does not count. A stricter new test is fine. In #5's stuck-reader rewrite: `TransportTest.test_a_client_that_reads_nothing_is_closed_once_its_socket_took_nothing_for_a_while` holds its ticks' clock, so it no longer catches `poll_out()`'s default clock set to 0; `OneTickTest.test_a_tick_writes_at_the_time_it_is_given_else_at_the_monotonic_clock` does. `IntegrationTest.test_a_client_that_stops_reading_blocks_nobody` no longer fails on a stall at `SEND_STALL_S / 2` (the old one failed on it only through the race); `TransportTest.test_a_client_that_reads_nothing_…`, `OneTickTest.test_a_tick_writes_at_…` and `OneTickTest.test_a_socket_that_takes_nothing_closes_its_connection_after_the_send_stall` catch it.
- **Check a transport change on Windows before the owner-timed Live restart (#5):** run the script on SimLive with the Ableton PC's own Python in a separate process on a free port (Live untouched): a zip of `live-script/FohMixer`, `sim/` and the probe from `git archive HEAD`, fetched with `Invoke-WebRequest` from `airuleset.py share` (a LAN URL; the tailscale one timed out from the PC) and its SHA-256 checked, `Expand-Archive`, then a small stdlib script that builds the site, starts SimLive's `MainThread`, drives the surface with `probe.run` and raw sockets (dense reads, a `stall`, a stuck reader, a refused request) and unloads and rebinds the port. It showed Windows' non-blocking sockets, `select`, the resets and the SO_EXCLUSIVEADDRUSE rebind behave as on Linux.
- **SimLive's observability and types follow what the PC showed (#58), never a guess:** a track's `fold_state`, `is_visible` and `group_track` cannot be listened to (Live answers `add_listener` with `not observable`; a fold shows in `Song.visible_tracks`, which can); Live's vector classes report the module `Base` (`<Base.Vector object at …>`), which the codec takes as a list; Live answers `fold_state` as a bool. Each of these once passed every test while the site failed (a keeper whose fold watches all failed, list values that reached the hub as strings). Before relying on a listener or a value's shape in Live, probe it on the PC through the hub (subscribe, read the `subbed` answer, no write) and make SimLive match.
- **SimLive writes dB strings as real Live does** (`sim/Live/__init__.py` `_live_number`): 3 significant digits, at most 3 decimals, 0 as `0.00` (`-0.811 dB`, `-6.00 dB`, `-14.0 dB`), from the one string captured on the PC. Tests that pin a SimLive display string use that form; the UI and hub never format it (spec P2: Live's string as it is).
- A SimLive load (60 metered strips at 30 Hz, two clients resubscribing) never delayed a heartbeat on CI or here (#9): SimLive does not reproduce Live's scheduling. Prove transport ordering with targeted tests, not load. (The dev box under swap pressure does delay SimLive heartbeats by up to ~360 ms, and once by 1040 ms, #5: the stuck-reader integration test then failed its 1 s heartbeat-age bound, with nothing wrong in the script. That bound stays on purpose: a main thread blocked on the stuck client shows at least the 3 s stall; changing it is a design decision on the ticket, not a flake fix. Otherwise a SimLive test must not bound the machine's timing.)
- **Live runs the script's timer at ~30 Hz** (every ~34 ms whatever `TIMER_INTERVAL_MS` asks, #5): one tick is the script's latency step in each direction; a new script version is measured on the PC with `tools/live-probe` after the owner-timed Live restart that loads it.
- **`time.monotonic()` in Live on Windows is `GetTickCount64`** (15/16 ms steps): `main_tick_age_ms`, `gap_ms` and the stall log come in those steps; `time.time()` (the frames' `ts`, `GetSystemTimeAsFileTime`) is ~0.5 ms there only while an audio app holds a raised timer resolution (15.625 ms by default; the probe's `wall_clock_step_ms` measures it).
- **A Tuner marker in SimLive (#68):** `sim/host.py`'s control line `tuner <track|return> <index> <set|add|remove> ['<name>']` renames the track's first Tuner (adding one when it has none), adds another, or deletes the first, as a user in Live would (`devices` and `name` listeners fire); it answers `TUNER <Tuners on the track>` (`-1`: no such track). The name goes in single quotes (shlex), so a marker's double quotes pass: `tuner track 1 set '"Vox 1" +G:VOCALS'`. The hub tests call it through `Host::tuner`, the E2E specs through `hostLine`.
