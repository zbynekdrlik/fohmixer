# Forensics timeline (#43, design note §5.3)

- **What it is:** `tools/forensics/timeline.py`, the command, with seven modules beside it: `timeline_read.py` (values, times, reading the logs), `timeline_model.py` (the analysis and the summary), `timeline_touch.py` (the touches of single volume faders, #43 PR D, and the Stream Deck), `timeline_eq.py` (the Pro-Q 4 screen, #71), `timeline_ableset.py` (AbleSet's tab, #90), `timeline_rules.py` (the rail buttons' steps and the hub's rule records, #130), `timeline_report.py` (the HTML). Stdlib only (Python 3.11+); the eight files always travel together (the command finds the others through its own folder on `sys.path`). It draws a time window of the hub's event log (`events-YYYY-MM-DD.jsonl`, one per UTC date) and the hub's text logs (`hub.out.log`, `hub.out.<stamp>.log`, for `Live busy changed` and late-heartbeat lines, ANSI colours stripped) as ONE self-contained HTML file: inline CSS and SVG, no script, no external resource. A report like "fader 3 jumped at 19:40" is answered from the logs alone.
- **CLI:** `python timeline.py --events <logs folder> --from <local time> --to <local time> [--key TEXT ...] --out report.html`. Times are the local time of the machine running it (`YYYY-MM-DD HH:MM[:SS[.fff]]`, `T` allowed, or `HH:MM[:SS[.fff]]` for today). `--key` keeps the controls whose key holds TEXT (any of them); the link and Live lanes and `records` stay whole. Exit 1 with one `timeline: ...` line on a usage or input error; exit 0 with a report also when the window is empty.
- **What it reads:** only the day files of the UTC dates from `--from` − 1 min to `--to` + 30 min, line by line, parsing only lines whose `"ts":` is in range. Records count from 60 s before `--from` (offsets, busy episodes that started earlier) to `--to`; a `trace` up to 30 min after `--to` (`TRACE_TAIL_MS`: its page events can fall inside; the page's recorder drains a full 768 KB backlog in ~95 s once the fingers rest, waits for the next socket while the link is down, and a hidden page uploads once a second, #43 PR E; since #51 PR 2c an idle page, hidden or untouched for the layout's `idle_after_s`, sends its smaller batches every 30 s, a full one as the cap lets it, and the rest at once when it wakes), and the `ping`s of those 30 min too (`TAIL_KINDS`; also `deck_ok`, so a press at the window's end keeps its Companion round trip), the pings for the page clocks only: a trace that goes up on the next socket has a new client number whose pings all lie after the window, and without them it would take the clock of whichever page pinged last. No other line of the tail is parsed (`TAIL_EV`), and a day file only the tail reaches is not noted as missing. AbleSet's link changes (`HEAD_KINDS`: `ableset_link`, #90) are read from the start of the day file BEFORE the window's first (`previous_day_file`), before the lead too (`HEAD_EV`, no other early line is parsed): the latest before the window is AbleSet's state at its start. The hub writes only changes, so an outage that began before UTC midnight is still the state at the start; a change older than the previous day is not read (`n/a`), and a missing previous file is not noted. `test_timeline_model.PageRecorder` checks against `diag/trace.rs` that the timeline's `LONG_FRAME_MS` is the page's, that the backlog is the 768 KB the comments name, and that a full one drains at the cap inside the tail. A line that does not parse is counted in `skipped_lines`.
- **Page errors are not in it (#43):** a page's client reports (`kind="error"` with the thrown value's stack since #43) go to the hub's text log (`client report` lines, INFO) and `/api/status` `client_reports`, never to the event log, and the timeline reads only the busy and late-heartbeat lines of the text log: read an error's stack from `hub.out*.log`.
- **Page time → hub time:** `t + offset`, where the offset is the `offset_ms` of the ping of the trace's own `client` nearest in time to the trace record (a `ping` record with `clock_step_ms` marks a clock step, #52: the hub's offset starts over there, so offsets either side of it differ by about that much). Fallbacks: the nearest ping of any client, else 0 (with a "page clock not aligned" note). A `set` carries its own `offset_ms`. Exact duplicate page events (a batch resent after a lost socket) count once, compared with sorted keys.
- **The send row:** a page's `send` events (a page before PR D recorded every send; since PR D only a write its socket did not take, drawn hollow) and the hub's `set` records at their page `t` (+ their `offset_ms`) where no keyed page send has that `t`. The page's round trips: `pong` events (before PR D) and the `rtt` summaries' `med` (the summary's `max` counts for `rtt_page_max_ms`); a summary covers a second of pongs, 10 s while the page is idle (#51 PR 2c: a ping a second).
- **Gaps:** in each control row (page sends, hub arrivals at `hub_ms`, Live's applied values at the `applied` record's `ts`), two consecutive points more than 100 ms apart are a `gap` only when both lie in ONE touch's span:
  - only continuous controls get gaps: a key with a non-final send in the window (a page `send` or hub `set` whose `final` is exactly false). A key whose sends are all final (mute, solo, stage, a param toggle's press and release) never does, whatever its touches.
  - one span per touch, never merged: a `tap` (mute, solo and the stage button without STAGE AUT record `what: "tap"`, no lift follows) spans 1000 ms. The merged STAGE button (#104, D18, a stage with `aut`) records no `touch`: its steps are essential `rail` events (`what` `press`/`tap`/`full`/`hold`/`refused`/`slid`/`lost`/`cancel`, `button`, `keys`, `pointer`; since 1.3.1, the owner's rulings on #104, `full` is the 1 s mark (`RAIL_HOLD_MS`), where nothing is sent, and `hold` is the lift that acted; a `refused` at the full mark or at the lift sent nothing), which the timeline lists in its "Rules" table (#130 PR 6, `timeline_rules.py`), never as a touch span. A `down` spans to its lift plus 1000 ms, cut at the start of the next touch (`down` or `tap`) of the key that begins at or after the lift: a fader let go and grabbed again within 1 s has no gap for the time the finger was off. Its lift is the first `up`/`cancel`/`lost` with the same pointer id whose keys name the key (`LIFTS`; #124: `lost` is the page's end of a touch whose end the browser never delivered, recorded when the next primary down of its type took the control, right before that finger's `down`, or when the page was hidden), searched only up to that pointer's next `down` of the key (a lost lift). A `down` with no lift spans to the start of the next touch of the key (any finger's or tablet's), else to the window's end (a fader held past the window keeps its gaps).
  - a gap needs both of its points in one span. Another finger's or tablet's touch that begins before a `down`'s lift does not cut that `down`'s span, and a lift on another control never ends it.
  - limits: lifts match by pointer id and key, not by socket (a lift uploaded on another socket after a reconnect mid-touch still ends its touch), so two tablets touching one control at once with the same pointer id read as one finger; and a `down` with no lift is cut by the next touch of that control, whoever makes it.
  - a key no touch names (a page before the recorder): points up to 10 s apart count as one gesture.
- **Jumps (volume keys only, TouchOSC's `value2db`, over 3 dB between consecutive applied values), first cause that holds:**
  - `link`: the largest arrival gap is over 100 ms while the page's send gap is at most 100 ms, or a dropout overlaps the jump. Both gaps are measured from the one before S1 to S2: the hub's setter writes the first set after a stall alone, so S1 can be the first of the burst.
  - `live`: the batch's `rtt_ms` or S2's wait at the hub is over 100 ms, or a busy episode overlaps.
  - `page`: a send gap over 100 ms after S1, or a long `frame` whose stall falls after S1's send and by S2's (`sent_of`, the page's own time on the hub clock): the page stamps a long frame at the frame that ends the stall (`diag::frame`, in the tick that then sends the next set), so the stall is the `ms` BEFORE its `t`, and it can only explain the jump between the last send before it and the first after it. The point matched is `INSIDE_STALL_MS` (25 ms, half the page's 50 ms threshold `LONG_FRAME_MS`) before the stamp: it lies inside the gap between the two ticks' sends (the stall's tick sends after its stamp, the tick before sent before the stall), so the few ms the trace's ping offset and the set's own offset differ cannot move it to the next jump (the stamp itself could). An idle page's frame (#51 PR 2c, `paced: true`: its loop waits 100 ms after each frame) is recorded only when it stalled beyond that pace, and its `ms` is that stall, so the timeline reads it as any long frame; a page is idle only while untouched (a touch wakes it before the control's handler, and the first gap after a wake is not recorded), so a paced frame never stands between two sends of a drag. A dropped long frame is drawn and matched as the stall it can be: `LONG_FRAME_MS` before its stamp (`NoData` of kind `frame` spans `from − 50` to `to`); its note and tooltip (`no_data_text`) give the dropped stamps and the span of page stalls they can stand for. Without both sets, the applied interval. (Before PR E the band was drawn from `t` on and matched against Live's applied interval, which trails the sends by the link's latency: a jump whose sets both went before the stall was the page's too.) Page events past the window's end are read for long frames and drop notes only (a stall the window's end falls into; a note stamped when its batch went, after the drag).
  - `no data` (PR E): none of the above, but a span of long frames the page's recorder dropped (a `frame` `NoData`, hit `nodata`; its `from`/`to` are stall ends, moved `INSIDE_STALL_MS` earlier) meets the interval from S1's send to S2's: a page stall cannot be ruled out.
  - `link`'s dropout and `live`'s busy episode are matched against the applied interval (their effect shows when Live applies), the page's long frames against the sends.
  - `move`: none of these.
- **Touches (PR D, `timeline_touch.py`):** each `touch` down of ONE volume key that says where it started (`from`; an older page's down does not), in the window. Its records are matched on the page's clock from the down's `t` to its lift's (`lift_of`, the gestures' rule; a down with no lift ends at the key's next down, else the window's end): its pointer's `mv` records of the key, and the key's sets of the socket those records name (`names_set`: `seq` == a record's `q`, `t` within `SAME_FRAME_MS` = 50 ms; each page counts its seq from 1, so another tablet's sets inside the touch stay out). The first applied value is Live's result of the first of those sets Live applied (an applied point whose identity is one of them), and the finger is read at the frame that sent that set (`finger_at`). A **first-touch jump**: that value is more than 1 dB from the first set's `live_before`, AND more than 1 dB from where the finger alone would have taken Live (`to_live(to_pos(live_before) + r − from)`: direction counts, a fader that went up while the finger went down is one); its why: `local`, `stale` (the page's `live` more than 1 dB from `live_before`), else `other`. Down to first move / first send: the first `mv` move's time (`t + dt`) / the first set's `t`, minus the down's `t + dt`. Stutter: a move gap (two consecutive moves over 50 ms apart with the coordinate changed over 3 px across it: a rest moves on by little) and a held run (3 or more frames in a row each sending the previous frame's `s` while `r` changed over 1e-4, `s` strictly inside 0..1). Every threshold is pinned at its boundary: the one-line helpers against the next float (`over_jump`, `is_move_gap`, `finger_moved`, `inside_travel`, `within`), `HELD_FRAMES` with runs of 4 and 3 frames; a touch's frames come in page-time order (`own_frames`: two sockets' offsets can interleave them on the hub's clock). `live_before` is the hub's push cache, not Live: a re-grab right after a release whose value Live has not pushed back yet (a Live stall) reads the old value and shows as a `local` jump. The report's touch table rows carry `class="touch"`, `data-first-jump`, `data-why`, `data-first-move` (PR F), `data-jump-db`, `data-finger-db`, `data-off-db`, `data-first-move-ms`, `data-first-send-ms`, `data-move-gaps`, `data-held`.
- **First move (PR F):** the touch's first `mv` carries `a`, where the touch's first pointer move left the fader. `first_move_of`: `anchored` when `a` is within `RAW_STEP` of the down's `from` (`finger_moved`), `applied` otherwise, None without `a` (an older page, or a touch that sent nothing, e.g. a tap whose only event anchored; not counted, so the two counts need not add up to `touches`). An anchored touch's first-touch jump counts the finger from the anchor, from the coordinates (`finger_raw`: `from` + (the first move of the touch's first frame, the one carrying `a`, − the last move of the frame `frame_at` picks) / `travel` (at least 1 px, as the page's `travel.max(1.0)` counts it), unclamped; `first_touch` counts it from `from`): the drag is relative, so the fader follows the finger even where the page's `r` (from the down, clamped to 0..1) is past an end — read from `r`, a pull-back after a first event past the top showed as a jump (PR F review, round 2). An anchored touch whose first frame or picked frame has no moves, or whose down has no `travel` (a malformed record), reads no finger (n/a, no jump), never `r`. A test that needs Live to apply a later set first passes `held` to `FirstMove.touch` (the first sets reach the hub together with the next). Else the finger is that frame's `r`, from `from`, as before. Row `data-first-move` (left out when None), a "first move" column; stdout `first_moves_anchored`, `first_moves_applied` after `first_touch_jumps`. **A test with several scenarios writes each into a fresh folder** (`FirstMove.touch` calls `setUp`): `Log.write` appends, and an exact duplicate page event counts once, so a second scenario's identical down merges with the first's.
- **No data (PR E):** an `overflow` page event with `from`/`to` and one kind is a span the page's recorder dropped (`Timeline._dropped`, on the hub's clock with the note's own trace offset; `NoData` with `info` = kind, count, page from, page to): a `nodata` band in the link lane (`data-kind`, `data-n`, `data-start`, `data-end`) and a note; an older page's note (no span, several kinds) stays the old note ("dropped N events before …"). Both count in `recorder_dropped`. An `mv` span is passed to each touch it reaches on the page clock (`timeline_touch.no_data`, cut to the touch): a move gap or a held run's pair of frames across it (`across`: both ends count) is not counted; the touch's row adds `data-no-data` (spans), `data-no-data-ms`, `data-no-data-sets` (the touch's own sets no kept frame names, within `SAME_FRAME_MS` of a span: they reached the hub). A span cannot be pinned to one tablet (a socket number changes at a reconnect and page events carry no tablet id), so it reaches every touch it overlaps. A held-run pair whose frames carry no `t` is not checked against spans.
- **Intent records (PR E):** `intent` page events (`key`, `seq`, `state` `unconfirmed`/`not_sent`, `t`) of a wanted key in the window are marks on that key's send row (`class="intent <state>"`, `data-state`, `data-key-hash`), and a key with only intents still gets its lane; counted in `unconfirmed` / `not_sent`.
- **System gestures (PR G):** the page's `sys` events (`what`, `on`, `keys`, `pointer`, `prevented`) and `zoom` events (`scale`) in the window, whatever `--key` says (they belong to the page, like the link lane): `timeline_touch.system_event` reads each into a `SystemEvent` (a field of the wrong type reads as missing; `prevented` only when exactly true; a zoom's `prevented` is None), `Timeline.system` in time order; `escaped`: a `contextmenu`, `selectstart` or `dragstart` (`ESCAPABLE`) that nothing prevented. Each kind counts apart, because a pinch's start comes with any two fingers down (two faders at once), a cancel with a row panned from its background, and a lost capture also with a control gone under the finger (`on` none): only `system_escaped` says the loupe or a lift got through. The report's "System gestures" table rows carry `class="sys"`, `data-time` (hub ms), `data-what`, `data-on`, `data-key-hash` (the first key's), `data-prevented`, `data-pointer`, `data-scale` (`:g`, so 1.5 / 1); the link lane gets a `gesture` mark each (`data-what`). stdout `system_events` (the `sys` events), `system_escaped`, `gesturestarts`, `pointer_cancels`, `lost_captures`, `zooms` (`system_count`), after `not_sent`.
- **The channel detail (#71):** the page's `detail` events (`what`: `press`, `slid`, `tap`, `open` with `why` `check`/`lift`, `close` with `why` `exit`/`layout`/`placeholder`/`conflict`; since #71 PR E the Pro-Q 4 screen's `eq_open`, `eq_close` with `why` `exit`/`detail`/`socket`/`locked`/the hub's reason, and `eq_locked`, listed as rows like the others and counted by no summary cell; `keys` the strip's volume and mute write keys; `pointer`, none for a close the page made) in the window, whatever `--key` says: `timeline_touch.detail_event` reads each into a `DetailEvent` (a field of the wrong type reads as missing), `Timeline.details` in time order.
