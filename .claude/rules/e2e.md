# E2E (Playwright)

- **Two projects, every spec in both:** `chromium` (Desktop Chrome) and `ipad` (`devices["iPad Pro 11 landscape"]`, WebKit, touch). The iPad is the engineer's real device, so a WebKit-only console warning or layout problem fails CI. The `e2e` job installs `chromium webkit` with `--with-deps`.
- **Console guard:** specs import `test`/`expect` from `./support/fixtures` (copied from iemmixer): an auto fixture fails any test whose browser console shows an error, a warning or a page error it did not declare in `allowedConsole`. A test that deliberately provokes a failed request declares exactly that message with `test.use({ allowedConsole: [/…/] })` in its own `describe`, with a comment saying why. Never a global allowance; where the message is an app bug, fix the app. Two or more patterns need the tuple form `test.use({ allowedConsole: [[/a/, /b/], { scope: "test" }] })` (Playwright reads a bare `[/a/, /b/]` as `[value, options]`). Browsers word the same failure differently (Chromium `net::ERR_CONNECTION_FAILED`, WebKit its own text): declare the common prefix, not one browser's wording.
- **No retries, no skips:** `retries: 0`, `forbidOnly` in CI; `scripts/check_integrity.py` fails on `.skip`/`.only`/`.fixme`/`test.fail`.
- **Base URL:** the pages open the surface through the harness's impair proxy, `E2E_LINK_URL` (CI: `http://127.0.0.1:8481`, #43), in front of the hub at `E2E_BASE_URL` (CI: `http://127.0.0.1:8480`, the hub started from the release build with the real Trunk bundle embedded); the config falls back to `E2E_BASE_URL`, then the hub's default port 8480. `BASE` in `support/live.ts` stays the hub itself: the test's own `LiveClient`, tokens and API calls never go through the proxy, so a `drop` never cuts them.
- **Version test (`version.spec.ts`, verbatim from iemmixer):** the DOM label `data-testid="version"` must read `v` + `/api/version`'s `version`, so a WASM bundle and a hub from different builds fail.
- **App download failure (`app-load.spec.ts`):** the loader in `crates/fohmixer-ui/Trunk.toml` (`pattern_script`) catches a failed bindings/WASM download and the shell shows `load-error` with Try Again. The spec aborts `fohmixer-ui-<hash>_bg.wasm` (the hash is an unpadded hex u64, 1–16 digits) and declares the browser's `Failed to load resource: ` line. The service worker exists only on the https origin (#17, spec R5), and the suite's base URL is plain http, so it never interferes with a route there.
- Failure evidence (`test-results/`, the HTML report, `hub.log`) is uploaded as the `e2e-failure` artifact.
- **Probe a browser assumption locally before a CI cycle (no hub needed):** `npm ci` in `e2e/`, then a small node script with `chromium` / `webkit` from `@playwright/test` on a `data:` page (a `page.goto`, not `setContent`: init scripts run on a navigation). The dev box may lack the lock's Chromium revision: launch an installed one with `executablePath` (`~/.cache/ms-playwright/chromium-*/chrome-linux64/chrome`). #26 checked this way that `contextOptions.screen`, an own `navigator.standalone`, dispatched `ErrorEvent` / `PromiseRejectionEvent` (no page error) and `keepalive` behave alike in both engines. A `data:` page is no secure context (no `navigator.wakeLock`, no service worker): for those, `page.route("https://probe.test/", (r) => r.fulfill({ contentType: "text/html", body }))` and go there — a secure https origin in both engines, no server or certificate (#5). Playwright's `page.evaluate` and locator actions give the page user activation themselves: an activation-gated API is modelled in a stub (`stubWakeLock({ activation: true })`) and touched with raw `page.touchscreen.tap` / `page.mouse.click`.
- **Remote access (#17, `remote.spec.ts`):** the job gives the hub the public name `foh.e2e.test` (a per-run CA trusted by both browsers, the name in `/etc/hosts`), HTTPS on 8443 (`E2E_HTTPS_URL`) and an `[access]` whose key set the harness serves from `E2E_ACCESS_KEY`. `test.use({ baseURL: E2E_HTTPS_URL })` puts `openSurface` on the https origin; an internet request is one with `cf-connecting-ip`. See `.claude/rules/remote-access.md`.
- **The harness (`e2e/harness/harness.py`, #8):** the `e2e` job starts it before Playwright; it runs two `sim/host.py` hosts (`band`, `master`) with the real FohMixer script, writes the hub's config (`layout_poll_ms = 200`) and the layout (the import tool's `tools/import-tosc/fixtures/expected-layout.json`), starts the hub from the release build and serves a control API on `E2E_HARNESS_URL` (127.0.0.1:39190): `POST /host/<name>/line` (`stall <ms>`, `rename "<a>" "<b>"`, `listeners …`), `/host/<name>/restart`, `/hub/restart {rotate_secret}`, `/hub/layout {layout}`, `/hub/layout/reset`, `GET /hub/events`, and the impair proxy's `/link` routes (#43, below). Its own tests: `python3 -m unittest discover -s e2e/harness` (the `python` job).
- **Specs share one hub and one set, so they run serially (`workers: 1`) and put back what they change:** `e2e/tests/support/live.ts` has `LiveClient` (a second WebSocket client that reads and writes Live, to set up a state and check what the surface wrote), `openSurface` (the token seeded once per tab; waits for `data-connected`; #58 removed the waits for the automatic refresh a second after load and for the page's unfold, `data-unfolds`, now the hub's), `hostLine`, `harness`. A test that renames a track, swaps the layout or restarts something restores it in a `finally` (rename back, `/hub/layout/reset` then wait until the hub serves the original again). After `/hub/layout`, wait for something only the NEW layout shows before measuring or marking: the page fetches it a moment later and replaces the whole page, so a box read in between is `null` (column.spec's pinned test first waits for the pinned strip on the other sub-page; CI of 7767ccf). The engineer PIN is `E2E_PIN` (random per run, masked).
- **A host `stall` over 3 s fails the pending commands** (a get/set or a range read through `cmd` answers "no result within 3 s", the hub's `REQUEST_TIMEOUT`); subscriptions are only delayed (the router's listener requests have no timeout). A test that must see a write fail or succeed during a stall keeps it under 3 s.
- **A hub restart closes every client socket, the test's own `LiveClient` too:** reopen it (`live.close(); live = await LiveClient.open()`) before reading Live again. `LiveClient.cmd` fails on a closed socket and after 10 s, never hangs.
- **Client reports (#26, `client-report.spec.ts`):** every page reports itself to the shared hub, so a test finds its own page's reports in `/api/status` `client_reports` by the page's user agent, a screen size no other test uses (`test.use({ contextOptions: { screen: … } })`, read back as `${screen.width}x${screen.height}@${devicePixelRatio}`) and the test's start second. Errors are provoked with a dispatched `ErrorEvent` / `PromiseRejectionEvent` (reaches the page's listener; a thrown error would be a page error the console guard fails); a Home Screen app is `navigator.standalone = true` from an init script; a build change is the hello's `build` rewritten through `routeWebSocket`; a dropped connection is `sockets[0].close({ code: 4000 })` on a routed socket (a `disconnected`, then a `reconnect` with `reconnects: "1"`); a trailing report (a change within the kind's 5 s window) is awaited, not assumed. A `perf` report (#5 K4) comes about 10 s after the surface starts drawing (`reportOf`'s `timeout` 30 s, the test's own `test.setTimeout`); simultaneous touches are `PointerEvent`s with distinct `pointerId`s dispatched on `document.body` inside one `page.evaluate` (the page counts them in the capture phase on the window, so no control is touched and nothing needs restoring; both engines checked with a local probe). Wait for the page's first periodic `perf` report before touching: the next periodic one is then a minute away, so a report within seconds can only be the touch path's (else a broken immediate report still passes). A dispatched `visibilitychange` empties the frame window (a touch report then has `fps` null: proves the pause), and a sequence that keeps three down with one `pointercancel` and one `pointerup` in between proves both are counted (a missed one reads four). The https wake-lock stub lives in `support/pwa.ts`; `HUB_SOCKET`, `RELOAD_KEY` and `countLoads` in `support/live.ts`.
- **The control link (#43, `link.spec.ts`):** `recordLink(page)` routes the hub socket through, recording both directions (`ws.onMessage` + `server.send`, `server.onMessage` + `ws.send`) and can hold the hub's messages (`hold`, then `release()`) to make a stall; `hubEvents()` (`support/live.ts`) reads the hub's event log through the harness's `GET /hub/events`. A page's writes are `set`s; its ack matches by key (`instance|target|prop`) and `seq`, but in the event log `seq` repeats across pages (each page counts from 1): find the page's `set` record by its `t` (the hub keeps the page's time to the bit, serde_json `float_roundtrip`), then follow its `client` through `batch` → `applied` → `ack`. A page's mouse drag sends no `final` set when its last move was already sent in a frame: wait for the ack of the LAST set, not of a final one. A page stall is a busy loop in `page.evaluate` (it returns the page clock at its end); a routed socket's `close()` reaches the page as an evaluate too, so it always lands after the stall, and then the close and the late timers run in either order (which one comes first varies by engine and run): only the close-first order tells a dropout tick that goes on between sockets from one on the socket's watchdog, so a stall test asserts what holds in both orders (one `socket_lost` dropout, starting at or after the stall's end).
- **The impair proxy (#43, `e2e/harness/impair.py`, PR B):** a stdlib asyncio TCP proxy the harness starts on `--link-port` (0 = any free port, its own tests) in front of the hub; `impair` in `support/live.ts` calls `POST /link/stall {ms}` (both directions held; a running stall is extended, never shortened), `/link/drop` (every connection reset, `SO_LINGER` 0), `/link/block {on}` (new connections accepted but held, not refused: a held fetch or socket is no console error, a refused one is; the page's reconnect waits in its `/api/layout` fetch, so no socket is opened and closed while connecting) and `/link/rate {bytes_per_s}` (#43 PR D, `impair.rate`: the pages' bytes to the hub at most N a second over every connection together, first in first out in 1 KB pieces, the hub's way back unlimited; a slow link — a test that sets it puts `0` back in its `afterEach`); `GET /link` reads its state. A test that blocks unblocks in a `finally`/`afterEach` (every later test goes through the proxy). A reset of an open socket is a console error in WebKit only ("WebSocket connection to '…' failed: Error receiving data: Connection reset by peer"; a local probe, both engines): a test that drops declares `/^WebSocket connection to '.*' failed/`. `resilience.spec.ts` is the §6.2 tests 1–4: a release while the link is down reaches Live after it returns (L1), a touch while it reconnects moves and the held value is sent after the hello (L2), a release inside a 1.5 s stall never shows the pre-stall value (a `requestAnimationFrame` sampler of `data-value` / `data-intent` in the page; the drag's pointer events dispatched in the page, and the stall extended by another 1.5 s right after the release, so the ack is held past the 1 s that makes it `unconfirmed` whatever the drag's timing) (L3), a release 5 s old is not sent and the fader is `not_sent` (red `outline-color` `rgb(255, 59, 48)`, `.fader-ghost` visible, `data-ghost` at Live's value, no text) until the next touch, which starts from the cap (L4); a fader rebuilt by a page switch (`selectPage` to `cue` and back to `foh`) while the link is down shows its write, is enabled and takes a drag from the cap; a page left while connected, or left during one outage and re-entered in the next, comes back waiting (no old value to touch); a value the hub sent inside a 2 s stall after the page left it is dropped, so the page re-entered in the next outage waits too (the cue toggle's first value, the answer to a sub the hub reads after the stall, proves the late value reached the page first); a not-sent release Live already holds (a dispatched drag past the top clamps the release to exactly 1.0, the test's `LiveClient` sets 1.0 meanwhile) ends `confirmed`, and its event log holds the write's `intent` records, `unconfirmed` then `not_sent`, both with the release's numeric `seq` (PR E: the resend turns it `not_sent` and Live's replayed value closes it within milliseconds); a fader taken away under a dispatched finger that never lifts (a page switch) counts as released, so its 2.5 s old write is not sent; a pan touched again and held still is held, so its write goes when the link returns. The glue the mutation gate cannot judge (`live_value`, the unmount `release`, the pan's `touch`) is covered only by these. The L3 sampler also records the cap's computed `outlineColor` (amber `rgb(245, 166, 35)` while `unconfirmed`) and the ghost's `display`; the L2 test raises the meter with the host's `meter "Hand2 #" 0.8` line (put back with `off`) and wants it to fall and the status light `unbound` once the link drops. `impair.py` also runs on its own (`--upstream <IPv4 or name>:<port>`, `--listen-host` 127.0.0.1 by default, control lines on stdin, JSON answers, `IMPAIR <port>` first) for a check of a deployed hub (`.claude/rules/deploy-pc.md`, the degraded-link check); its log goes to stderr. Dispatched pointer events (a double tap, a drag timed in the page, a finger that stays down) go through `dispatchPointer(control, steps, pointerId, primary)` in `support/live.ts` (steps: an event `dy` px above the centre, or a `wait`; `primary` true by default, false for a second finger: a dispatched `PointerEvent` is not primary unless it says so). A test that restarts a host under a held finger first waits until Live confirmed the finger's value: an unconfirmed write of a held fader is sent again once the instance is back.
- **The counter, the open-write looks and the forensics (#43, PR C):** `counter.spec.ts` samples the counter (`data-testid="dropouts"`: its text, `data-active`, computed colour) every animation frame in the page — a Playwright poll steps 100, 250, 500, 1000 ms and can miss a red phase of a few hundred ms — through an 800 ms `impair.stall` (a 400 ms stall is a dropout, but whether the page's 100 ms tick sees it lasting depends on the ping's phase; the samples are read after polling them, not the DOM, to the stall's end: the sampler records on the NEXT animation frame, and a read right after the DOM turned neutral once still ended on the red sample in WebKit, dev run 37300751198), then a cut link (`block` + `drop`: red until the reconnect) and a tap (0); it reads the page's records back from the event log (`trace` records' `events`: both dropouts, the `reset` with `count`, and the socket's `close` the page saw while its link was down, in a record whose hub `ts` is after the unblock — the backlog). Page times are `performance.timeOrigin + performance.now()` (`pageNow`), on the runner's one clock with the hub's `ts`. `intent.spec.ts` cuts the link, drags the pan and taps the mute: `data-intent` `unconfirmed` and an amber `outline-color` (`rgb(245, 166, 35)`) on the pan's `.pan-dot` and the mute after 1 s, `not_sent` and red after a reconnect more than 2 s later; Live keeps its values and the toggle keeps showing Live's (P2); the event log then holds each write's `intent` records, `unconfirmed` then `not_sent` with one `seq` (PR E, sorted by page `t`: they go up after the reconnect). `forensics.spec.ts` drags a fader (dispatched, a 1 px move every 20 ms for 1.6 s) through an 800 ms stall, finds the page's touch (its down with `dt`, `c`, `travel`, `pos`, `live`, `local`, `from`, PR D), its `mv` records (each with `e`, `r`, `s`, `q`; no `send` for a set the socket took) and the dropout in the `trace` records, the last frame's set (`seq` = the largest `q`) through `set` → `batch` → `applied` → `ack`, and `live_before` on the touch's first set only, then runs `tools/forensics/timeline.py` through the harness's `POST /forensics/timeline {from_ms, to_ms}` (answer `exit`, `stdout`, `stderr`, `html`) and wants a `<rect class="dropout">` and an arrival `<rect class="gap">` of at least 400 ms over the stall, `touches=1` and `first_touch_jumps=0`, and a stdout of numbers only; its second test stalls the page's link 2.5 s, sets Live to 0.85 through the test's own `LiveClient` meanwhile, drags 5 px from the stale 0.5 and wants `live_before` 0.85 on the first set and a `stale` first-touch jump in the timeline (`<tr class="touch" … data-first-jump="true" data-why="stale">`). `counter.spec.ts` reads the page's `rtt` summaries (no `pong` event). `recorder.spec.ts` (PR D) drags a fader twice back to back (`DRAG_PX` = 100, a 1 px move every 20 ms; PR E: with no ack records a 75 px drag left WebKit 3 881 bytes, under the 4 000 below) through a 24 KB/s `impair.rate` with the page's `trace` frames dropped by an init-script wrapper of `WebSocket.prototype.send` (`window.dropTraces`, the recorder off as the link sees it) and then kept: the sets' one-way delay (`hub_ms − t`, one clock on the runner) with the recorder must stay within that without it (median + 20 ms, p90 + 30 ms), at most 2 `trace` records may reach the hub between a drag's first and last set (5 ms either side: the socket's one task stamps both, `ts` in whole ms) while the page events recorded between the drag's first and last set fill at least 4 000 bytes (4 batches of 1 000: without the set gate at least 3 would go inside it, so the check can fail), and the second drag's lift must reach the event log within 10 s (its ~33 KB, about what PR D's drags left with their acks, drain one batch per 100 ms tick and a last partial batch after 2 s; page timers run late on a loaded runner: a 6.1 s lag for ~32 KB failed a 6 s bound once) while the hub logs a trace record at least every 500 ms from the last set to the lift (no stall), but for the gap before the drain's last batch, up to 2 500 ms: it holds what no longer fills a batch and waits its 2 s (`UPLOAD_MS`). The lag and each drag's event bytes are test annotations (`lag-ms`, `drag-bytes`). Its second test (PR E) is a long drag (`longDrag`: 1 200 dispatched 1 px moves every 20 ms, a triangle wave of ±60 px, 24 s; WebKit on the runner draws ~14 frames a second there, and 900 moves left its moves only just over 48 KB) through the same 24 KB/s, the recorder off (then 30 s for its events to drain to nowhere) and on: every set of the drag (the hub's records by key and page time) has its `mv` (`q` = `seq`) in the event log, no `overflow` note since the first drag, no `send`/`ack` page event, the drag's page events over 48 KB (PR D's bound: the check can fail), and the sets' delay with the recorder within that without it (median + 20, p90 + 30 ms); its lift may take up to 90 s to arrive (the backlog drains at the cap, ~20 s on Chromium). `pageEvents(records)` (`support/live.ts`) gives the page events of the `trace` records each once, as the timeline reads them (a batch resent after a lost socket is logged twice). `controls.spec.ts`'s SOLO clear waits for both solo buttons' `data-on="true"` before the pill's click (the pill shows from the first solo and clears only the solos the page knows of).
- **`page.routeWebSocket(/\/ws\?/, …)`** stands between the page and the hub for connection tests (`connection.spec.ts`): close the page's socket with a code (1000 or 3000–4999, as Playwright closes the hub's side with the same one; 4001 is the hub's reload code), or connect to the hub and filter the hub's messages (`server.onMessage` stops the automatic forwarding in that direction only).
- **A drag's first pointer move only anchors it (#43 PR F):** the strip's faders and pans move nothing on a touch's first `pointermove`. A dispatched drag of ONE move (`resilience.spec.ts` `touchUp`) starts with a `{ type: "pointermove", dy: 0 }` anchor; a mouse drag of several moves loses only its first (thresholds checked: still met). The parameter faders keep their first move. `touch-start.spec.ts` samples the cap's `getBoundingClientRect().top` every animation frame and the fader's `pointermove`s (a capture listener on the element) in the page: no frame between the first move (10 px) and the second may move the cap over 3 px, and the cap then rises with the finger's next 30 px (over 75 %, at most 31 px); wait 300 ms after the first move (WebKit on the runner draws ~14 frames a second). `forensics.spec.ts` wants the touch's first `mv`'s `a` equal to the down's `from` and `first_moves_anchored=1`.
- **The controls own their touches (#43 PR G, `touch-guard.spec.ts`):** a guard is checked with a DISPATCHED `new Event("touchstart", { bubbles: true, cancelable: true })` read back as `defaultPrevented` (both engines; the listener does not care about the event's interface, and WebKit's Playwright has no touch drag), on every tap target and on a child of one, and NOT prevented off them; `-webkit-user-drag` is the computed property that tells the CSS apart (both engines compute `-webkit-user-select` `none` for any child of a `user-select: none` body, before PR G too, so that check cannot fail). A real finger's tap on a control reaches it as Pointer Events although its `touchstart` is prevented: WebKit's `page.touchscreen.tap` (ipad project), Chromium's `Emulation.setTouchEmulationEnabled` + `Input.dispatchTouchEvent` `touchStart`/`touchEnd` (the desktop project has no `hasTouch`); its down and lift are in the page's `touch` records, and it adds no `sys` record (no capture lost while the finger is down). A line that does not fit (#63) shows its arrows: `touch-guard.spec.ts` adds a third row of 31 strips with a pinned master strip at its end through `/hub/layout` (`try`/`finally` reset, then waits for the group and the arrows to go), and wants the arrows' `touchstart` prevented, a line's background and a strip's tag free, ▶ moving the window (`shift-where`) with the pinned strip the same element (`data-e2e-kept`) and ◀ bringing the first window back. The page's `sys` records come from dispatched events too (`contextmenu`, `selectstart`, `dragstart`, a plain `gesturestart`, `PointerEvent`s with made-up ids for `pointercancel` and a `pointerdown` → `lostpointercapture` → `pointerup` → `lostpointercapture`, of which only the first lost capture is recorded); a zoom is Chromium's `Emulation.setPageScaleFactor` (2, then 1: the page's meta viewport does not stop it), each scale held 3 frames (`frames`) before the next: the visual viewport's resize fires once per frame with the scale of then. The timeline's stdout then counts `system_events`, `system_escaped`, `gesturestarts`, `pointer_cancels`, `lost_captures`, `zooms`.
- **The Stream Deck tab (#52, `deck.spec.ts`):** the `e2e` job's harness runs the fake Companion (`e2e/harness/fake_companion.py`, `--fake-companion-port 39192`) and puts it in the hub's `[companion]`, so every page has the deck tab (`data-testid="deck-tab"`, outside the `tab` test ids: the pages' bar specs still read the layout's tabs only). `companion` in `support/live.ts` reads the fake's presses (`key`, `pressed`, `at`) and sets its faults (`down`: Companion away, `fail`: presses refused); the spec's `afterEach` calls `companion.reset()` (`POST /companion/reset`: up, not failing, nothing recorded or held), which waits until the hub's device is registered at the fake again (`devices`; the hub reconnects with a backoff of at most 2 s). `openDeck` opens the tab and waits for 32 keys with images and Companion online; `deckKey(page, n)`. A press is dispatched pointer events (`dispatchPointer`, `pointercancel` too); a primary down anywhere on the deck page (a key, the grid's margin: the page root's capture-phase listener) first lifts every hold whose end never came (`lost`), so only a first finger is `primary`. A test leaves no key held: a page closed holding one is released by the hub after the next test began. The red flash lasts 400 ms, so a test records the keys that flash (`data-failed`) with a `MutationObserver` installed before the press; the hub's acks reach the page in Companion's order, so a later key's flash proves an earlier answer was handled. The local outline is read before any answer can exist: a 300 ms `impair.stall` (under the hub's 0.5 s `late` bound, so the down is still forwarded), the down and its read a macrotask later (Leptos' effects run in microtasks) inside one `evaluate` (`downAndRead`), and the hub's `deck_press` of it logged after the read. The late bound (C1) needs the page's clock at the hub: wait for it with `clockKnown(since)` (a `ping` record with `offset_ms`) before the stall, since `openSurface` returns once connected and no longer waits a second (#58: a down sent before the hub knew the clock counted as on time and was forwarded). A down at once into a 2 s stall (under the page's 3 s silence) flashes when the hub's `late` answer comes and never reaches the fake; a second finger's down after the dropout counter turned red (waited for in the page, frame by frame) flashes at once and is never sent; the test accepts the page refusing the first down too (a slow runner can see the dropout first), and waits for the counter's `data-active` false before the next tap. "Never sent" is read at the fake after a second, or against a later press that must arrive first (the event log and the fake keep one order); the event log is read with `until` (written a little later). The page hidden is `document.hidden` and `visibilityState` as own properties plus a dispatched `visibilitychange` with `bubbles: true` (the deck listens on the window); deleting them puts the page back. A send the socket refuses is an init-script wrapper of `WebSocket.prototype.send` that throws for a `deck_press` of one kind (`window.deckRefuse`); a socket that reads as closing is `WebSocket.prototype.readyState` overridden for one dispatched `pointerdown` only (the page refuses that down itself, so it spends no press number: the `seq`s of the presses around it run on). The hub's records: `deck_press` (`why`, `forwarded`, `reason`), `deck_ok` (the press's `client` and `seq`, `rtt_ms`), `deck_release` (`detach` after a dropped page link, `reconnect` after Companion's outage). The version label stays in the viewport beside the deck tab (in the column, #63); the deck's keys are two halves around the column (the left half's keys come first in the document: columns 0–3 of each row, then 4–7). `/hub/companion {on}` restarts the hub with or without the table: the last test, with no page open during either restart (it goes to `about:blank` first: a page's reconnect while the hub is down logs a failed load). The real Companion 5.0.7 has its own job and config (`playwright.companion.config.ts`, `e2e/companion/`, `.claude/rules/ci.md`): `companion.spec.ts` reads Companion's state through its HTTP API (custom variables, never the hub) and runs both projects against one Companion, so each test starts from a state its check changes (`scene_1` never `short`, `hold_c` `up`), and the `afterEach` puts back every variable the test `remember`ed (Companion's `POST /api/custom-variable/<name>/value?value=…`, read back), also after a failure: one project's failure never spends the other's starting state. Every key's image is a `data:image/webp;base64,` URL that draws (`naturalWidth > 0`): the fake sends PNGs, so only that job proves WebKit renders Companion's webp (a local probe: 144 × 144 lossless webp, both engines). - **Double taps never rely on real-click timing:** one WebKit click takes ~160 ms on the runner. A toggle's double tap (TouchOSC's 200 ms window, no minimum) is one `page.mouse.dblclick` (`toggleDoubleTap`); a fader's, pan's or mute's (`doubleTap`) dispatches the two taps' pointer events inside the page with `setTimeout` timing, because the fader wants its releases 50–250 ms apart, which real clicks cannot hit in both engines.

- **A crashed page process fails its test with a named message (#9).** The test browser's engine crashes now and then: Playwright's WebKit build (2248) about once per ~3,500 loads, on its main thread in JavaScriptCore while the surface loads (and often at context teardown in Mesa llvmpipe threads, harmlessly). The console guard watches `page.on('crash')` (`watchCrash`, `support/fixtures.ts`) on the test's page and on every page its context opens, and keeps its console check next to a crash (a soft expect): the test fails with "the WebKit page process crashed (a test-browser crash, see .claude/rules/e2e.md), not an app stall", after the error of the page call the crash broke (a generic "expect(locator).toBeVisible() failed", no word of the crash). The watch closes the crashed page: Playwright alone rejects a pending call only between its retries, and a locator waiting for the page's script context right after a navigation sat to its own timeout (1 run in 5). **A CI run that fails with the named crash gets one rerun; the same test failing twice with it is investigated as real** (a crash in a real iPad's WebKit freezes the page the same way). The build is stripped: a crash gives offsets only.
- **A WebAssembly trap at page load in WebKit is a page error, not a crash (#43):** `RuntimeError: Unreachable code should not be executed` or `null reference` thrown from a wasm-bindgen closure adapter within ~200 ms of `goto`, the page living on (connected) while the test fails on a control that never appeared plus the console guard. Seen twice (PR D: link.spec, PR E: params.spec, both iPad, both in the closure the JS glue's cast comment names `Function { arguments: [Externref], ret: Result(Unit) }`, wasm-bindgen-futures' task queue) in hundreds of passing loads, never with a "panicked at" line (`console_error_panic_hook` is installed, so not a Rust panic). The crash rerun rule does not cover it: investigate each one (the run's `e2e-failure` trace.zip has the stack; the `wasm-dist` artifact's name section keeps only closure adapters), record it on #43 (comment 5983136572 has the method), and a third occurrence gets a build with function names.
- **Core dumps are off in the `e2e` job, or a crash reads as a stall.** A crashed process stays alive while it writes its core dump (15–45 s), with its sockets open: no crash event, pending page calls hang, the page closes by itself only after the dump (`pageClosed` in the trace before the test's own "Close context"). A piped `core_pattern` (apport, systemd-coredump) ignores RLIMIT_CORE (core(5)), so the job sets `kernel.core_pattern=core` and the Playwright step `ulimit -c 0` (it fails if the pattern still pipes). On failure `$RUNNER_TEMP/e2e-logs/kernel/` holds the pattern, the kernel's segfault/trap lines and `coredumpctl list`. `crash.spec.ts` proves the setting on the runner: it crashes a page mid-load in a browser of its own (SIGABRT with the `kill` command to its page processes: an outside SIGSEGV is taken by JavaScriptCore's own fault handler and the page lives on) and wants both the crash event and the broken page call within 5 s.
- **The runner's own default is piped** (run 36606739954 printed `|/usr/lib/systemd/systemd-coredump %P %u %g %s %t …`), which is why the two CI stalls went silent for 15–25 s; after the job's setting the Playwright step prints `core_pattern core, ulimit -c 0`.
- **Locally, a dev box pipes its cores to systemd-coredump** and `ulimit -c` does not help (not even 1, on this kernel). `echo 0 > /proc/self/coredump_filter` in the shell that starts Playwright (inherited by the browsers) makes a crash's dump a few KB, which gives the job's timing without touching the box's global `core_pattern`. A silent WebKit page there is a crash if `segfault … WPEWebProcess` is in the kernel log or `coredumpctl list` names it; a JS spin or a stopped process never closes by itself.
