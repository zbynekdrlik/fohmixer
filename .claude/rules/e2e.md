# E2E (Playwright)

- **Two projects, every spec in both:** `chromium` (Desktop Chrome) and `ipad` (`devices["iPad Pro 11 landscape"]`, WebKit, touch). The iPad is the engineer's real device, so a WebKit-only console warning or layout problem fails CI. Each `e2e` leg installs its project's browser (`chromium` or `webkit`) with `--with-deps`.
- **The `e2e` job is four legs (#43, `.github/workflows/ci.yml`): each project in two shards,** `e2e chromium 1/2`, `e2e chromium 2/2`, `e2e ipad 1/2`, `e2e ipad 2/2` (`npx playwright test --project=<p> --shard=<i>/<n>`, `fail-fast: false`). In one job both projects ran up to 1766 s of its 30 minutes (Chromium ~620 s and the iPad ~870 s of tests, ~230 s of setup, the hub's release build ~130 s of it); a leg was the setup plus its shard, about 9–12 minutes; since `hub-e2e` a leg takes 315–555 s (5–9 minutes). Since `hub-e2e` (#43) the hub is built once per run: every leg (and `companion`) downloads that job's binary, checks it against the SHA-256 the job printed and runs it, with no Rust toolchain, cache or build of its own (`.claude/rules/ci.md`). Each leg is a runner of its own: its own hub process, harness (the fake Companion and the fake AbleSet included), test CA, core-dump setting and failure evidence, so "one hub, specs serially" below holds within a leg. Playwright shards whole spec files by test count in file order (`--list --project=ipad --shard=1/2` shows a leg's files; today `ableset-proxy` … `eq` and `forensics` … `version`), and a file moves between shards as tests are added: **a spec never relies on another spec file having run before it** (a shard starts on a fresh hub). Reproduce a leg locally with the same two flags. When a leg nears 20 minutes, add a shard (`shard: ["1/3", "2/3", "3/3"]`, on one line: `scripts/check_integrity.py` fails a list that misses an i/n), never a longer timeout.
- **Console guard:** specs import `test`/`expect` from `./support/fixtures` (copied from iemmixer): an auto fixture fails any test whose browser console shows an error, a warning or a page error it did not declare in `allowedConsole`. A test that deliberately provokes a failed request declares exactly that message with `test.use({ allowedConsole: [/…/] })` in its own `describe`, with a comment saying why. Never a global allowance; where the message is an app bug, fix the app. A failed load is declared with its URL too (#90 PR C review L9): an allowance `{ text, url }` matches only when the line's text AND `msg.location().url` match (Chromium and WebKit name the failed resource there; Chromium's text names no URL), so a failed load of any other resource still fails the test (`ableset.spec.ts`'s `PROBE_URL`). Two or more patterns need the tuple form `test.use({ allowedConsole: [[/a/, /b/], { scope: "test" }] })` (Playwright reads a bare `[/a/, /b/]` as `[value, options]`). Browsers word the same failure differently (Chromium `net::ERR_CONNECTION_FAILED`, WebKit its own text): declare the common prefix, not one browser's wording.
- **No retries, no skips:** `retries: 0`, `forbidOnly` in CI; `scripts/check_integrity.py` fails on `.skip`/`.only`/`.fixme`/`test.fail`.
- **Base URL:** the pages open the surface through the harness's impair proxy, `E2E_LINK_URL` (CI: `http://127.0.0.1:8481`, #43), in front of the hub at `E2E_BASE_URL` (CI: `http://127.0.0.1:8480`, the hub started from `hub-e2e`'s release build with the real Trunk bundle embedded); the config falls back to `E2E_BASE_URL`, then the hub's default port 8480. `BASE` in `support/live.ts` stays the hub itself: the test's own `LiveClient`, tokens and API calls never go through the proxy, so a `drop` never cuts them.
- **Version test (`version.spec.ts`, verbatim from iemmixer):** the DOM label `data-testid="version"` must read `v` + `/api/version`'s `version`, so a WASM bundle and a hub from different builds fail.
- **App download failure (`app-load.spec.ts`):** the loader in `crates/fohmixer-ui/Trunk.toml` (`pattern_script`) catches a failed bindings/WASM download and the shell shows `load-error` with Try Again. The spec aborts `fohmixer-ui-<hash>_bg.wasm` (the hash is an unpadded hex u64, 1–16 digits) and declares the browser's `Failed to load resource: ` line. The service worker exists only on the https origin (#17, spec R5), and the suite's base URL is plain http, so it never interferes with a route there.
- Failure evidence (`test-results/`, the HTML report, `hub.log`, and since #71 PR Q the hub's event log `hub-data/logs/events-*.jsonl`: the pages' flight recorders and the hub's records) is uploaded as the failed leg's `e2e-failure-<project>-<i>of<n>` artifact (e.g. `e2e-failure-ipad-1of2`; `companion-failure` likewise).
- **Probe a browser assumption locally before a CI cycle (no hub needed):** `npm ci` in `e2e/`, then a small node script with `chromium` / `webkit` from `@playwright/test` on a `data:` page (a `page.goto`, not `setContent`: init scripts run on a navigation). The dev box may lack the lock's Chromium revision: launch an installed one with `executablePath` (`~/.cache/ms-playwright/chromium-*/chrome-linux64/chrome`). #26 checked this way that `contextOptions.screen`, an own `navigator.standalone`, dispatched `ErrorEvent` / `PromiseRejectionEvent` (no page error) and `keepalive` behave alike in both engines. A `data:` page is no secure context (no `navigator.wakeLock`, no service worker): for those, `page.route("https://probe.test/", (r) => r.fulfill({ contentType: "text/html", body }))` and go there — a secure https origin in both engines, no server or certificate (#5). Playwright's `page.evaluate` and locator actions give the page user activation themselves: an activation-gated API is modelled in a stub (`stubWakeLock({ activation: true })`) and touched with raw `page.touchscreen.tap` / `page.mouse.click`.
- **Remote access (#17, `remote.spec.ts`):** the job gives the hub the public name `foh.e2e.test` (a per-run CA trusted by both browsers, the name in `/etc/hosts`), HTTPS on 8443 (`E2E_HTTPS_URL`) and an `[access]` whose key set the harness serves from `E2E_ACCESS_KEY`. `test.use({ baseURL: E2E_HTTPS_URL })` puts `openSurface` on the https origin; an internet request is one with `cf-connecting-ip`. See `.claude/rules/remote-access.md`.
- **The harness (`e2e/harness/harness.py`, #8):** the `e2e` job starts it before Playwright; it runs two `sim/host.py` hosts (`band`, `master`) with the real FohMixer script, writes the hub's config (`layout_poll_ms = 200`) and the layout (the import tool's `tools/import-tosc/fixtures/expected-layout.json`), starts the hub from the release build and serves a control API on `E2E_HARNESS_URL` (127.0.0.1:39190): `POST /host/<name>/line` (`stall <ms>`, `rename "<a>" "<b>"`, `listeners …`), `/host/<name>/restart`, `/hub/restart {rotate_secret}`, `/hub/layout {layout}`, `/hub/layout/reset`, `GET /hub/events`, and the impair proxy's `/link` routes (#43, below). Its own tests: `python3 -m unittest discover -s e2e/harness` (the `python` job). Its fixed ports (39101-39193) sit in the runner's ephemeral range (32768-60999): every job that starts it first reserves 39100-39199 (`sysctl net.ipv4.ip_local_reserved_ports`), and the harness refuses to start when a fixed port is in the range and not reserved (`check_ports`; the master run of PR #128's merge lost a leg to EADDRINUSE on 39190 before any test). A new fixed port goes inside that reserved range.
- **Specs share one hub and one set, so they run serially (`workers: 1`) and put back what they change:** `e2e/tests/support/live.ts` has `LiveClient` (a second WebSocket client that reads and writes Live, to set up a state and check what the surface wrote), `openSurface` (the token seeded once per tab; waits for `data-connected`; #58 removed the waits for the automatic refresh a second after load and for the page's unfold, `data-unfolds`, now the hub's), `hostLine`, `harness`. A test that renames a track, swaps the layout or restarts something restores it in a `finally` (rename back, `/hub/layout/reset` then wait until the hub serves the original again). After `/hub/layout`, wait for something only the NEW layout shows before measuring or marking: the page fetches it a moment later and replaces the whole page, so a box read in between is `null` (column.spec's pinned test first waits for the pinned strip on the other sub-page; CI of 7767ccf). The engineer PIN is `E2E_PIN` (random per run, masked).
- **A host `stall` over 3 s fails the pending commands** (a get/set or a range read through `cmd` answers "no result within 3 s", the hub's `REQUEST_TIMEOUT`); subscriptions are only delayed (the router's listener requests have no timeout). A test that must see a write fail or succeed during a stall keeps it under 3 s.
- **A hub restart closes every client socket, the test's own `LiveClient` too:** reopen it (`live.close(); live = await LiveClient.open()`) before reading Live again. `LiveClient.cmd` fails on a closed socket and after 10 s, never hangs.
- **Client reports (#26, `client-report.spec.ts`):** every page reports itself to the shared hub, so a test finds its own page's reports in `/api/status` `client_reports` by the page's user agent, a screen size no other test uses (`test.use({ contextOptions: { screen: … } })`, read back as `${screen.width}x${screen.height}@${devicePixelRatio}`) and the test's start second. Errors are provoked with a dispatched `ErrorEvent` / `PromiseRejectionEvent` (reaches the page's listener; a thrown error would be a page error the console guard fails); since #43 the report carries the thrown value's stack after its text (` | stack: `, its lines joined by ` | `): the event's `error` (or the rejection's `reason`) is an `Error` made in named functions inside the `page.evaluate`, with no tail call (WebKit drops a strict tail caller's frame), and `stackFrames` drops V8's first line (`Error: <message>`), so the first frames name those functions in both engines; any object's string `stack` is read, so a long synthetic stack is a plain `{ stack }` (cut at 30 lines with ` [cut]`, kept whole by the hub); an `ErrorEvent` with no `error` keeps today's exact text; a Home Screen app is `navigator.standalone = true` from an init script; a build change is the hello's `build` rewritten through `routeWebSocket`; a dropped connection is `sockets[0].close({ code: 4000 })` on a routed socket (a `disconnected`, then a `reconnect` with `reconnects: "1"`); a trailing report (a change within the kind's 5 s window) is awaited, not assumed. A `perf` report (#5 K4) comes about 10 s after the surface starts drawing (`reportOf`'s `timeout` 30 s, the test's own `test.setTimeout`); simultaneous touches are `PointerEvent`s with distinct `pointerId`s dispatched on `document.body` inside one `page.evaluate` (the page counts them in the capture phase on the window, so no control is touched and nothing needs restoring; both engines checked with a local probe). Wait for the page's first periodic `perf` report before touching: the next periodic one is then a minute away, so a report within seconds can only be the touch path's (else a broken immediate report still passes). A dispatched `visibilitychange` empties the frame window (a touch report then has `fps` null: proves the pause), and a sequence that keeps three down with one `pointercancel` and one `pointerup` in between proves both are counted (a missed one reads four). The https wake-lock stub lives in `support/pwa.ts`; `HUB_SOCKET`, `RELOAD_KEY` and `countLoads` in `support/live.ts`.
- **The control link (#43, `link.spec.ts`):** `recordLink(page)` routes the hub socket through, recording both directions (`ws.onMessage` + `server.send`, `server.onMessage` + `ws.send`) and can hold the hub's messages (`hold`, then `release()`) to make a stall; `hubEvents()` (`support/live.ts`) reads the hub's event log through the harness's `GET /hub/events`. A page's writes are `set`s; its ack matches by key (`instance|target|prop`) and `seq`, but in the event log `seq` repeats across pages (each page counts from 1): find the page's `set` record by its `t` (the hub keeps the page's time to the bit, serde_json `float_roundtrip`), then follow its `client` through `batch` → `applied` → `ack`. A page's mouse drag sends no `final` set when its last move was already sent in a frame: wait for the ack of the LAST set, not of a final one. A page stall is a busy loop in `page.evaluate` (it returns the page clock at its end); a routed socket's `close()` reaches the page as an evaluate too, so it always lands after the stall, and then the close and the late timers run in either order (which one comes first varies by engine and run): only the close-first order tells a dropout tick that goes on between sockets from one on the socket's watchdog, so a stall test asserts what holds in both orders (one `socket_lost` dropout, starting at or after the stall's end).
- **The impair proxy (#43, `e2e/harness/impair.py`, PR B):** a stdlib asyncio TCP proxy the harness starts on `--link-port` (0 = any free port, its own tests) in front of the hub, in a process of its own (`impair.Child`, below: as a thread of the harness it shared the interpreter's lock, and the harness's `GET /hub/events`, ~250 ms of Python with one ~90 ms `json.dumps` of the whole log, held every page's link in both directions: master run 38340390496's ping lag of 3 in `eq.spec.ts`); `impair` in `support/live.ts` calls `POST /link/stall {ms}` (both directions held; a running stall is extended, never shortened), `/link/drop` (every connection reset, `SO_LINGER` 0), `/link/block {on}` (new connections accepted but held, not refused: a held fetch or socket is no console error, a refused one is; the page's reconnect waits in its `/api/layout` fetch, so no socket is opened and closed while connecting) and `/link/rate {bytes_per_s}` (#43 PR D, `impair.rate`: the pages' bytes to the hub at most N a second over every connection together, first in first out in 1 KB pieces; a slow link — a test that sets it puts `0` back in its `afterEach`) and `/link/down_rate {bytes_per_s}` (#71 PR J, `impair.downRate`: the hub's bytes to the pages the same way, the Pro-Q frames on a slow Wi-Fi; put back in a `finally`); `GET /link` reads its state (`rate`, `down_rate`). A test that blocks unblocks in a `finally`/`afterEach` (every later test goes through the proxy). A reset of an open socket is a console error in WebKit only ("WebSocket connection to '…' failed: Error receiving data: Connection reset by peer"; a local probe, both engines): a test that drops declares `/^WebSocket connection to '.*' failed/`. `resilience.spec.ts` is the §6.2 tests 1–4: a release while the link is down reaches Live after it returns (L1), a touch while it reconnects moves and the held value is sent after the hello (L2), a release inside a 1.5 s stall never shows the pre-stall value (a `requestAnimationFrame` sampler of `data-value` / `data-intent` in the page; the drag's pointer events dispatched in the page, and the stall extended by another 1.5 s right after the release, so the ack is held past the 1 s that makes it `unconfirmed` whatever the drag's timing) (L3), a release 5 s old is not sent and the fader is `not_sent` (red `outline-color` `rgb(255, 59, 48)`, `.fader-ghost` visible, `data-ghost` at Live's value, no text) until the next touch, which starts from the cap (L4); a fader rebuilt by a page switch (`selectPage` to `cue` and back to `foh`) while the link is down shows its write, is enabled and takes a drag from the cap; a page left while connected, or left during one outage and re-entered in the next, comes back waiting (no old value to touch); a value the hub sent inside a 2 s stall after the page left it is dropped, so the page re-entered in the next outage waits too (the cue toggle's first value, the answer to a sub the hub reads after the stall, proves the late value reached the page first); a not-sent release Live already holds (a dispatched drag past the top clamps the release to exactly 1.0, the test's `LiveClient` sets 1.0 meanwhile) ends `confirmed`, and its event log holds the write's `intent` records, `unconfirmed` then `not_sent`, both with the release's numeric `seq` (PR E: the resend turns it `not_sent` and Live's replayed value closes it within milliseconds); a fader taken away under a dispatched finger that never lifts (a page switch) counts as released, so its 2.5 s old write is not sent; a pan touched again and held still is held, so its write goes when the link returns. The glue the mutation gate cannot judge (`live_value`, the unmount `release`, the pan's `touch`) is covered only by these. The L3 sampler also records the cap's computed `outlineColor` (amber `rgb(245, 166, 35)` while `unconfirmed`) and the ghost's `display`; the L2 test raises the meter with the host's `meter "Hand2 #" 0.8` line (put back with `off`) and wants it to fall and the status light `unbound` once the link drops. `impair.py` also runs on its own (`--upstream <IPv4 or name>:<port>`, `--listen-host` 127.0.0.1 by default, control lines on stdin, JSON answers, `IMPAIR <port>` first, or one JSON `error` line and exit 1 when it cannot listen) for a check of a deployed hub (`.claude/rules/deploy-pc.md`, the degraded-link check); its log goes to stderr. Dispatched pointer events (a double tap, a drag timed in the page, a finger that stays down) go through `dispatchPointer(control, steps, pointerId, primary)` in `support/live.ts` (steps: an event `dy` px above the centre and `dx` right of it (#124: a pan's drag), or a `wait`; `primary` true by default, false for a second finger: a dispatched `PointerEvent` is not primary unless it says so). A test that restarts a host under a held finger first waits until Live confirmed the finger's value: an unconfirmed write of a held fader is sent again once the instance is back. A test whose assertion needs the page to have sent something before an impairment holds the finger and waits for the hub's record of it (`until(hubEvents, …)`) before it impairs, never a fixed wait: the page sends a fader's set only in its animation frame, and WebKit on the runner can draw no frame for a second (0.65–1.37 s after a page's load, and once 1.07 s from a touch on: master run 38546278518, `forensics.spec.ts` as its leg's first test).
- **The harness's tools run in processes of their own (#43, `e2e/harness/child.py`):** the impair proxy, the fake Companion and the fake AbleSet are each their file's tool (`main`), and the harness drives them through `child.Child` subclasses (`impair.Child`, `fake_companion.Child`, `fake_ableset.Child`) with the in-thread class's calls. The contract (`child.serve` is the tool's side): `<READY> <port>` once it listens (`IMPAIR`, `FAKE_COMPANION`, `FAKE_ABLESET`), or one JSON `error` line and exit 1 when it cannot; one JSON answer per stdin control line, in order (an `error` for an unknown line or a refused value: `ValueError`); the end of its stdin stops it (SIGTERM only as the fallback, no force-kill), so a dead harness leaves none behind. A call that gives up waiting (`CALL_S`) leaves its answer owed, and the next call reads and drops it before its own: answers match calls by order. `Harness.stop` stops every part in its order (the proxy, the hub before the fakes, the hosts) even when one fails, logs each failure and raises the first. `test_harness.py`'s `LinkPace`, `CompanionPace` and `AbleSetPace` prove no tool shares the harness's interpreter: a client process makes round trips (a byte through the link to an echo, `PING`/`PONG`, a kept-alive GET) while the harness reads a 30k-record log, and a read (each `json.dumps`, which holds the interpreter's lock to its end, at least `LONG_READ_MS` 40 ms) held the tool when no trip ended in its middle half: a tool sharing the process holds every one (locally, the proxy and both fakes as threads: every read of 9 to 12), one of its own fewer than half (locally none). No bound in ms on a trip: a stall of a shared runner holds a read now and then, never most. Each fake's tests also run through its `Child` (`ChildTest`).
