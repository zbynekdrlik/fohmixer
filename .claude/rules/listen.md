# Listen (#210: a track's sound, before its fader, in the browser)

## The design (phase 1, the design comment on #210 of 2026-11-15)

- **The device, `FohMixer Listen`** (`live-device/FohMixer-Listen/FohMixer Listen.maxpat`, built by `build_amxd.py --patch …`, `--port`/`--select-port` rewrite its three port boxes): silent (`sig~ 0.` into `plugout~`), in a rack's parallel chain like the LUFS devices. `plugin~` → `jit.catch~ 2 @mode 1 @framesize 960` (whole 20 ms frames, every sample once) banged by a `qmetro 10` (the low-priority queue: the matrix and the socket write stay off the audio thread) that runs only while selected → `jit.net.send @ip 127.0.0.1 @port 39111` (TCP). That `@mode 1` hands out every sample once in whole frames is Cycling '74's documentation, proved only by probe P3's `shapes` and `samples_per_s`. **The listen id** (`expr $i2 * 100000 + $i1 % 100000 + 1`: the device's Max id mixed with a `random 21000` drawn once at load) names the device in the announce, the hello and the selects: the Max id alone is numbered per Live process, and both Lives on the FOH PC announce to the same port (the review of the lane: two equal ids would overwrite each other and one select would start both). The selects: `udpreceive 39112` → `route /fohmixer/listen/select` → `==` the listen id (`== -1` until it is known, so the hub's stop select of 0 never matches) → on, a match restarting the `delay 1500` first, which turns it off when no select names it; another id turns it off at once. A change to on sends the hello (`fohmixer_listen 1 <listen id> v<version> <sample rate>`) into `jit.net.send`'s right inlet first, then starts the `qmetro`; while on, the hello goes again each second (the hub records only a change: `stream::hello_news`). The identity (`live.path` id and four parents, the meter's section copied) and `dspstate~`'s sample rate go each second into the announce (`/fohmixer/listen ,iisssssii`, `udpsend 127.0.0.1 39111`). `scripts/check_listen_device.py` (CI's `python` job) holds every one of these, the select logic box by box and line by line (`BOXES`, `WIRING`, `SESSION_ONLY`), the ports and frame read from the proto crate.
- **In the bundle since phase 2:** the `bundle` job builds `FohMixer Listen.amxd` with `build_amxd.py` beside the LUFS and meter devices, `New-FohBundle` (`$script:BundleFiles`, `$script:Devices`) carries it and `Install-FohUserDevices` writes it into each Live user's `Presets\Audio Effects\Max Audio Effect\` (held, never replaced, while a Live runs: `deploy-pc.md`); `Test-Fohmixer.ps1`'s device lists name three. Placing it on tracks is the main session's PC step, after the probe kit below.
- **The wire** is `fohmixer_proto::listen`: `wire` (announce, select, hello; the LUFS wire's OSC readers shared), `jitnet` (the Jitter chunks; every number read in the order its own size field tells, the samples in the matrix header's), `frames` (`Framer`: 960-sample stereo frames, mono doubled, a non-finite value silence and counted, a 96 kHz device decimated first), `resample` (the 2:1 decimator, below).
- **The hub** (`crates/fohmixer-hub/src/listen.rs` and `listen/`): `[listen] port` (39111, 0 off) binds TCP then UDP on the same number, 127.0.0.1 only; `select_port` 39112. `stream.rs`: at most 64 connections (`jit.net.send` may connect at load and stay: P2), each through `jitnet::Reader` (a matrix at most `MAX_DATA` = 50 × 960 × 2 × 4 = 384 000 bytes: 0.5 s at 96 kHz, what a `qmetro` held up half a second leaves in `jit.catch~`, never seconds of encoding on the async path; a matrix with a 0 dimension and no data is an empty matrix, consumed and answered, with data behind it `matrix_strides`); a chunk begun and not finished for 5 s (`stalled`, judged on every pass from the time the chunk BEGAN: its first bytes' read or the read that finished the chunk before it, so a byte every 0.9 s still ends at 5 s) ends its connection, and only a connection holding an unfinished chunk reads with the 1 s timer (an idle one just waits); a latency answer per matrix with `try_write` (never waits on Max; `answer_of`: a full socket drops it, counted, a part written ends the connection, `latency_broken`), the hello recorded only when it changes (`hello_news`), `take` the pure decision (`no_hello`, `sample_rate` other than 48000 or 96000, `not_selected`); an encoder per connection, made at its first frame (a failure kept on the connection: logged once, then `encoder` counted). `udp.rs`: announces in (at most 256 devices kept, `keeps`; more counted `devices`), selects out every 500 ms while one is owed (`selecting`: a target, or the stop of 0 after one; an idle hub keeps no timer there) and at once on a start or a stop (`Listen::wake`). `listen.rs`: the pure `choose` (one fresh device on the set's track; `two devices` / `no device`), `start_of` (one track at a time, **the newest start wins**, the main session's ruling on the review of the merged lane: a start of another track is `Take`; same-track starts share it), `select_now` (0 once after the end). A take bumps the turn: one `listen` record `{what: taken, from, to, client, peer}` (`taken_fields`; `from`/`to` with instance, set, track and listeners), the pages of the old turn see it on `Listen::turns` (a `watch`) and are told `taken` with their track and stop, every packet carries the turn it was sent in (`session::passes`: a page hears only its own turn's), and a lease of an older turn leaves nothing when it drops. **A device is picked by its track's and Live set's names, never the instance** (accepted on the review): the target's set name is read again at every decision through `SetNames` (`set_name_of` over the Live handles), so a set loaded while a page listens is followed, a set unknown for a moment keeps the last name, and a track renamed meanwhile is no longer found. `session.rs`: `/ws/audio?token=` (any role, `Role::reaches` the instance; 503 `LISTEN_OFF` with port 0), `listen_start {instance, track}` (names 1 to 256 characters, `names_ok`) / `listen_stop`, `audio_status` back (`listening`, `stopped`, `no_source`, `taken`, `refused`), one Opus packet per 20 ms, `MAX_BEHIND` 4, `no_source` once after 2 s of silence and `listening` again before the next packet; every write within `ws::SEND_TIMEOUT` (`bounded`): a page that takes nothing (a locked iPad) is closed and its lease goes, so it never holds the one track. Records `listen` (warn class): `listening`, `start`/`stop` with the turn, `taken`, `hello`, `stream_up`/`stream_down`, `page`. `/api/status` `listen`.
- **96 kHz (ROZHODNUTÉ on #210 of 2026-11-16, after the PC probe found the master Live at 96 kHz):** the hub takes 48000 and 96000 (`fohmixer_proto::listen::resample::decimation`: 1 and 2), every other rate is refused `sample_rate`. At 96 kHz a 2:1 `Decimator` (a 95-tap windowed-sinc FIR, Blackman, cut-off 21 kHz, unity at DC; flat within 0.05 dB to 15 kHz, 70 dB or more down from 24 kHz; 47 input samples of delay) runs per stream before the `Framer`, which is made for the hello's rate (`Framer::for_rate`, `stream::reframe`): two 10 ms device frames make one 20 ms Opus frame. `jitnet::MAX_DATA` is 50 × 960 × 2 × 4 = 384 000 bytes (0.5 s at 96 kHz). SimLive: `listendev <where> <i> add [rack] [<rate>]` (48000 by default; `MAX_FRAMES` 50); `tests/it/listen.rs` `a_device_at_96_khz_is_decimated_to_the_pages_48_khz_tone` and `a_device_at_another_rate_is_refused`. Never drop samples instead: everything above 24 kHz would fold into the audio band.
- **The encoder:** `opus` 0.4 (`opusic-sys` builds libopus 1.6 with CMake: the runners and the dev box have it; `THIRD-PARTY-NOTICES.md` carries libopus's BSD notice), 128 kbit/s, the restricted low-delay application.
- **Tests:** `tests/it/listen.rs` (SimLive's `sim/listendev.py`: `--listen-port`/`--select-port`, host lines `listendev`, `tone`, `streamed`; the page decodes the hub's Opus back to the device's tone) and `tests/it/listen_wire.rs` (host-free, also in the `windows` job with the lib's `listen::`). Both in the `hub-hosts` nextest group. A test hub binds Listen only when it asks (`TestHub::start` sets `listen.port = 0`). The tests take a port free for UDP and TCP (`free_port`, as the LUFS tests take theirs): the SimLive host needs the hub's port and its select port when it starts. Decided against on the review (#210): an ephemeral hub port with SimLive told afterwards; the LUFS tests' pattern is kept until a race shows.

## The page (phase 2; the owner's approved mockup `docs/mockups/listen-v1.html`)

- **The decoder: WebCodecs `AudioDecoder` with `codec: "opus"`, 48 kHz stereo** (ROZHODNUTÉ on #210 of 2026-11-16): Safari 26 (iPadOS 26) added WebCodecs' AudioDecoder, the FOH iPad runs Safari 26.6.1, WebKit refuses Opus only above 2 channels (WebKit bug 327697), and Playwright's WebKit 26.0 and Chromium both decode it. It needs a secure context (the hub's https name, or `127.0.0.1` in the E2E): on the emergency plain-http address by IP the key says `no_decoder` and nothing opens. No wasm decoder.
- **Pure (`behave/listen.rs`, tests `behave/listen/tests.rs`):** `Listen` (the wanted `Target {instance, track, label}`, the `Phase`, whether the socket is open; `tap` stops when lit, else asks or opens; `follow` a new channel while lit; `opened`, `closed` (`Reopen` after `RECONNECT_MS` 1 s while wanted), `status` (the hub's `listening`/`no_source` only for the wanted track, `taken` for it and any `refused` end it: `Close`, `Silence`); `track_name` (a strip bound by name gives the hub's name at once; one by place, a Tuner marker strip or the master, reads `get_prop name` of `live_set tracks N` / `return_tracks N` / `master_track` first: the hub picks a device by its track's NAME), `name_of`, `foot_text` (`listening <label>`, `<label>: no source`, `: reconnecting`, `: taken by another page`, `: refused`, `no audio decoder in this browser`), `gain_db`/`gain` (0 silence, else -40 to +12 dB on a straight line; `VOLUME_DEFAULT` 0.7), `volume_at`. `net::audio_url`. The essential trace event `listen` (`diag::trace::listen`: `what` tap/follow/open/close/status, `phase`, the track).
- **Glue (`src/listen.rs`, mutants-excluded):** `Listener`, a context of `Surface` (outlives the detail: the foot names the track behind the mix), its own `/ws/audio?token=` socket (binary `arraybuffer`), the player through `listen_player.js` (a wasm-bindgen snippet: Trunk copies it to `dist/snippets/`), whose `startListenPlayer` runs INSIDE the key's tap (a browser starts a page's audio only in a user's gesture, and on a touch screen that is the LIFT: the key acts on `pointerup`, owns its touches); a strip bound by place has its name read meanwhile (`resolving` holds a second tap). `listen_player.js`: iemmixer's player adapted (an adaptive 80-500 ms jitter buffer, packets queued while the context is not running), the gain into `listen-limiter-worklet.js` (copied by `index.html`'s `copy-file`; -1 dBFS, the output is silent until it loaded), `window.__fohmixerListen()` (running, limiter, packets, decoded, played, dropouts, level, gain, error) for the E2E.
- **The look (`listen.css`, `components/listen.rs`):** `ListenKey` (`listen-key`, `data-state` the phase, `aria-pressed` lit) beside `ChannelSelect` in the detail's bar, grey and dimmed while idle, the accent while lit; `ListenVolume` (`listen-volume`, `data-value` 0-100, a pointer-captured slim track) only while lit; `ListenLine` (`listen-line`) in `ColumnFoot` after the scene's line. Mounting the key on a detail follows that channel while listening (`Listener::follow`): another strip's detail opened by SEL, or the channel selector's pick.
- **E2E (`e2e/tests/listen.spec.ts`, both projects):** the harness's `--listen-port`/`--listen-select-port` (CI 39197, 39198: the FOH hub's `[listen]` and the band host's SimLive devices; the MBC hub's config sets `[listen] port = 0`, else its default 39111 meets its own LUFS port) and the host lines `listendev`, `tone`. Both SimLive hosts load the same set name, so the hub finds a band device for master's track of the same name: a "no source" check uses a band track with no device (`B-Main repro #`).

## The PC probe kit (the main session runs it; nothing of it is done yet)

Announce it to dasio first (the shared FOH PC, its CPU). Never in a declared event. Results on #210 without host names, track names, user names or paths.

1. **Build and place.** On the dev box: `python3 live-device/FohMixer-LUFS/build_amxd.py --patch "live-device/FohMixer-Listen/FohMixer Listen.maxpat" --out <dir>/FohMixer Listen.amxd`; to the PC as `deploy-pc.md` moves the bundle (a short-lived LAN server, SHA-256 checked); copy it into the band user's `<User Library>\Presets\Audio Effects\Max Audio Effect\` (a new file: nothing loaded is replaced). Open it once in Live's Max editor: no Max error in the console (`jit.catch~`, `jit.net.send`, `dspstate~`, `qmetro` all made), the face shows `v<version>` and `Sending 0`. Place two through the LOM as the LUFS rollout does (`browser load_item`, then `move_device` into a rack of its own: an empty dry chain plus the device's chain), on two tracks the main session picks, and read each track's `latency_in_samples` before and after (unchanged).
2. **The probe stands in for the hub, on ports of its own** (a hub with this release holds 39111 and 39112 is every installed device's): build the probe's device with `--port 39121 --select-port 39122` (step 1) and run `python listen_probe.py --port 39121 --select-port 39122 --idle 60 --seconds 120 --device <id> --out <deploy folder>\listen-probe.json` with the PC's Python (`tools/listen-probe/listen_probe.py` copied, SHA-256 checked); check the two ports are free first (`Get-NetTCPConnection -LocalPort 39121`, `Get-NetUDPEndpoint -LocalPort 39121`). The ids come from a first short run's `devices` (`--idle 5 --seconds 0`): each device's `track_hash`/`set_hash` against `short_hash(<name>)` computed on the dev box.
3. **What each result answers:**
   - **P1, one select port for every device:** both devices are in `devices`, and with `--device <one>` only that one connects and streams (its `matrices` > 0); then a run with `--device <the other>` the same. Then once more with one device in EACH Live (band and master: two Windows users, two Max processes): do both hear their selects on one port, and are their listen ids different (`random` seeded per process)? If a device never hears its select (Max's `udpreceive` objects do not share a port, within a process or across the two users), the fallback is the design comment's: each device polls the hub over `maxurl`.
   - **P2, `jit.net.send`'s connection:** `opened_s` says whether it connects at load (before the select, `opened_s` < `--idle`) or at its first matrix; a second run with `--no-latency` says whether it waits for the latency answer (a stream that stops after one matrix: `matrices` 1). Restart the probe while a device is selected: does the device reconnect by itself (`connections` of the second run)?
   - **P3, the byte order:** `chunk_ids` (`JMTX/big` or `XTMJ/little`, and `chunk_size_order`) is the header's; `sample_stats` is the 50th matrix read both ways: the order whose `peak` and `rms` look like the track's audio (under about 4, a few `not_finite` at most) is the samples'. The hub takes the samples in the header's order: a different answer is a one-line change in `jitnet::samples` with its test.
   - **The stream itself:** `shapes` (`planes=2 type=2 dims=[960, k]`), `samples_per_s` near 48000 (the hub refuses another sample rate), `gap_ms_median` about 10 to 20 and `gap_ms_max` (the queue's stalls), `matrices_after_stop` 0 to 2 (it stops at the 0 select), `messages` holding the hello.
4. **P4, the CPU inside Live** (dasio's sampler, or `Get-Counter '\Process(<the band Live's process name>)\% Processor Time'` each second, numbers with the invariant culture, `live-probe.md`): the probe's `--idle` phase is the devices placed and idle, its `--seconds` phase one device streaming; a third phase with the two devices removed (or switched off) is the baseline. Alternate the phases (idle / streaming / idle / streaming, 5 min each, `live-probe.md`'s noise note), with the transport stopped and once while a rehearsal plays; also read the band audio driver's stall log over the same windows. Record per core where dasio's sampler gives it.
5. **Remove** the probe devices (or keep them, on the owner's word), save the set yourself, and read the `.als` write time.
