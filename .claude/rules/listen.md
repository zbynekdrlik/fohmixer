# Listen (#210: a track's sound, before its fader, in the browser)

## The design (phase 1, the design comment on #210 of 2026-11-15)

- **The device, `FohMixer Listen`** (`live-device/FohMixer-Listen/FohMixer Listen.maxpat`, built by `build_amxd.py --patch …`, `--port`/`--select-port` rewrite its three port boxes): silent (`sig~ 0.` into `plugout~`), in a rack's parallel chain like the LUFS devices. `plugin~` → `jit.catch~ 2 @mode 1 @framesize 960` (whole 20 ms frames, every sample once) banged by a `qmetro 10` (the low-priority queue: the matrix and the socket write stay off the audio thread) that runs only while selected → `jit.net.send @ip 127.0.0.1 @port 39111` (TCP). The selects: `udpreceive 39112` → `route /fohmixer/listen/select` → its id equal to the device's own → on, and a `delay 1500` turns it off when no select names it; another id turns it off at once. A change to on sends the hello (`fohmixer_listen 1 <id> v<version> <sample rate>`) into `jit.net.send`'s right inlet first, then starts the `qmetro`. The identity (`live.path` id and four parents, the meter's section copied) and `dspstate~`'s sample rate go each second into the announce (`/fohmixer/listen ,iisssssii`, `udpsend 127.0.0.1 39111`). `scripts/check_listen_device.py` (CI's `python` job) holds every one of these, the ports and frame read from the proto crate.
- **Not in the bundle yet:** the `bundle` job, `New-FohBundle` and the install carry only the LUFS and meter devices; the Listen device joins them in phase 2 (after the PC probe), with `Test-Fohmixer.ps1`'s device lists.
- **The wire** is `fohmixer_proto::listen`: `wire` (announce, select, hello; the LUFS wire's OSC readers shared), `jitnet` (the Jitter chunks; every number read in the order its own size field tells, the samples in the matrix header's), `frames` (`Framer`: 960-sample stereo frames, mono doubled, a non-finite value silence and counted).
- **The hub** (`crates/fohmixer-hub/src/listen.rs` and `listen/`): `[listen] port` (39111, 0 off) binds TCP then UDP on the same number, 127.0.0.1 only; `select_port` 39112. `stream.rs`: at most 8 connections, each through `jitnet::Reader`, a latency answer per matrix with `try_write` (never waits on Max), `take` the pure decision (`no_hello`, `sample_rate` other than 48000, `not_selected`); an encoder per connection. `udp.rs`: announces in, selects out every 500 ms and at once on a start or a stop (`Listen::wake`). `listen.rs`: the pure `choose` (one fresh device on the set's track; `two devices` / `no device`), `start_of` (one track at a time: `Busy`), `select_now` (0 once after the end). `session.rs`: `/ws/audio?token=` (any role, `Role::reaches` the instance; 503 `LISTEN_OFF` with port 0), `listen_start {instance, track}` / `listen_stop`, `audio_status` back, one Opus packet per 20 ms, `MAX_BEHIND` 4, `no_source` once after 2 s of silence. Records `listen` (warn class): `listening`, `start`/`stop` with the turn, `hello`, `stream_up`/`stream_down`, `page`. `/api/status` `listen`.
- **The encoder:** `opus` 0.4 (`opusic-sys` builds libopus 1.6 with CMake: the runners and the dev box have it; `THIRD-PARTY-NOTICES.md` carries libopus's BSD notice), 128 kbit/s, the restricted low-delay application.
- **Tests:** `tests/it/listen.rs` (SimLive's `sim/listendev.py`: `--listen-port`/`--select-port`, host lines `listendev`, `tone`, `streamed`; the page decodes the hub's Opus back to the device's tone) and `tests/it/listen_wire.rs` (host-free, also in the `windows` job with the lib's `listen::`). Both in the `hub-hosts` nextest group. A test hub binds Listen only when it asks (`TestHub::start` sets `listen.port = 0`).

## The PC probe kit (the main session runs it; nothing of it is done yet)

Announce it to dasio first (the shared FOH PC, its CPU). Never in a declared event. Results on #210 without host names, track names, user names or paths.

1. **Build and place.** On the dev box: `python3 live-device/FohMixer-LUFS/build_amxd.py --patch "live-device/FohMixer-Listen/FohMixer Listen.maxpat" --out <dir>/FohMixer Listen.amxd`; to the PC as `deploy-pc.md` moves the bundle (a short-lived LAN server, SHA-256 checked); copy it into the band user's `<User Library>\Presets\Audio Effects\Max Audio Effect\` (a new file: nothing loaded is replaced). Open it once in Live's Max editor: no Max error in the console (`jit.catch~`, `jit.net.send`, `dspstate~`, `qmetro` all made), the face shows `v<version>` and `Sending 0`. Place two through the LOM as the LUFS rollout does (`browser load_item`, then `move_device` into a rack of its own: an empty dry chain plus the device's chain), on two tracks the main session picks, and read each track's `latency_in_samples` before and after (unchanged).
2. **The probe stands in for the hub** (the deployed hub has no Listen yet, so 39111 is free; check with `Get-NetTCPConnection -LocalPort 39111` and `Get-NetUDPEndpoint -LocalPort 39111`): copy `tools/listen-probe/listen_probe.py` (SHA-256 checked) and run `python listen_probe.py --idle 60 --seconds 120 --device <id> --out <deploy folder>\listen-probe.json` with the PC's Python. The ids come from a first short run's `devices` (`--idle 5 --seconds 0`): each device's `track_hash`/`set_hash` against `short_hash(<name>)` computed on the dev box.
3. **What each result answers:**
   - **P1, one select port for every device:** both devices are in `devices`, and with `--device <one>` only that one connects and streams (its `matrices` > 0); then a run with `--device <the other>` the same. If only one device of the two ever hears its select (Max's `udpreceive` objects do not share a port), the fallback is the design comment's: each device polls the hub over `maxurl`.
   - **P2, `jit.net.send`'s connection:** `opened_s` says whether it connects at load (before the select, `opened_s` < `--idle`) or at its first matrix; a second run with `--no-latency` says whether it waits for the latency answer (a stream that stops after one matrix: `matrices` 1). Restart the probe while a device is selected: does the device reconnect by itself (`connections` of the second run)?
   - **P3, the byte order:** `chunk_ids` (`JMTX/big` or `XTMJ/little`, and `chunk_size_order`) is the header's; `sample_stats` is the 50th matrix read both ways: the order whose `peak` and `rms` look like the track's audio (under about 4, a few `not_finite` at most) is the samples'. The hub takes the samples in the header's order: a different answer is a one-line change in `jitnet::samples` with its test.
   - **The stream itself:** `shapes` (`planes=2 type=2 dims=[960, k]`), `samples_per_s` near 48000 (the hub refuses another sample rate), `gap_ms_median` about 10 to 20 and `gap_ms_max` (the queue's stalls), `matrices_after_stop` 0 to 2 (it stops at the 0 select), `messages` holding the hello.
4. **P4, the CPU inside Live** (dasio's sampler, or `Get-Counter '\Process(<the band Live's process name>)\% Processor Time'` each second, numbers with the invariant culture, `live-probe.md`): the probe's `--idle` phase is the devices placed and idle, its `--seconds` phase one device streaming; a third phase with the two devices removed (or switched off) is the baseline. Alternate the phases (idle / streaming / idle / streaming, 5 min each, `live-probe.md`'s noise note), with the transport stopped and once while a rehearsal plays; also read the band audio driver's stall log over the same windows. Record per core where dasio's sampler gives it.
5. **Remove** the probe devices (or keep them, on the owner's word), save the set yourself, and read the `.als` write time.
