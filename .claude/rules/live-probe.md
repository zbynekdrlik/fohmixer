# Live probe (learned on #5, K1/K2)

- **What it is:** `tools/live-probe/probe.py`, one stdlib file, a second localhost client of a FohMixer script (next to the hub): it records every heartbeat and times a `get_prop tempo` read every `--probe-ms`, then prints a JSON summary (`--raw FILE` keeps every sample). It writes nothing to Live and needs no Live restart. It sends no `Origin` header (the script refuses one) and waits for `connect`, skipping a heartbeat that comes first (the script can send one before its connect).
- **Run it on the Ableton PC** with the PC's own Python: fetch it from `airuleset.py share` (its LAN URL) with `Invoke-WebRequest`, check the SHA-256, then `python probe.py --port <PORT> --seconds 300`. The port is `PORT` in that Live user's `Remote Scripts\FohMixer\Config.py`; read it, never guess. A run longer than about 4 minutes outlasts one MCP call (the client aborts a call silent for 300 s): start it detached (`Start-Process`, output redirected to files) and poll for a marker file. A detached start from the MCP shell can still hold the call open until its timeout; the run goes on regardless.
- **Read the summary with the PC's clocks in mind** (Windows, Python 3.11/3.12): `time.monotonic()` is `GetTickCount64`, 15/16 ms steps, so `main_tick_age_ms` and `gap_ms` come in steps (see `distinct`); `time.time()` updates every ~0.5 ms, so the frames' `ts` is precise. Hence:
  - `result_tick_gap_ms` (gaps between the results' `ts`) is the main thread's tick interval — with `--probe-ms` below the tick (15 ms), not with the default 100 ms, where it shows the read spacing;
  - `read_inbound_ms` (send → the result queued on Live's main thread) and `read_outbound_ms` (queued → received) split `round_trip_ms` on the PC's wall clock; `heartbeat_outbound_ms` is the heartbeat's wait in the sender;
  - `timer_estimate` (2 × the mean age) is not the interval on the PC: the heartbeat thread samples the age just before a tick.
- **Keep the read rate low on the real Live:** the script's sender thread sends about one frame per main-thread tick (~30 frames/s, #5), so reads every 2 ms filled the connection's 1000-result queue in 2 s and the script closed the probe's connection (the hub's own connection is separate and was not touched). `--probe-ms 100` for load runs, 15 ms for a short tick run.
- **Compare configurations A-B-A** (e.g. `level`, `lr`, `level` again): run-to-run noise is large on the PC (two identical runs differed by 27 % of a core in the band Live's CPU and by several times in the master's outbound delays), so one before/after pair cannot tell a change from drift. With Live's transport stopped almost no meter moves, so a meter-source comparison then does not exercise the meter traffic; repeat it during a rehearsal. The results of #5: K1 and K2 comments there.
- **Load runs:** a surface open on the FOH page from the dev box (Playwright, PIN via `airuleset.py secret exec --file`, `localStorage.fohmixer_token` from `POST /api/auth`) subscribes every visible strip; the hub's `/api/status` shows `clients` and the subscriptions per instance. Live's CPU per process: `Get-Counter '\Process(<process name>)\% Processor Time'` (100 = one core); the band and master Lives run as differently named processes. Results go on the ticket without host names, IPs, user names or user paths.
