# Live probe (learned on #5, K1/K2)

- **What it is:** `tools/live-probe/probe.py`, one stdlib file, a second localhost client of a FohMixer script (next to the hub): it records every heartbeat and times a `get_prop tempo` read every `--probe-ms`, then prints a JSON summary (`--raw FILE` keeps every sample). It writes nothing to Live and needs no Live restart. Exit 1 with one `live-probe:` line when it cannot measure (a `--raw` path it cannot write is refused before connecting), and also when only the raw file failed after the run: the summary is still printed and written samples stay in `<raw>.tmp`. It sends no `Origin` header (the script refuses one) and waits for `connect`, skipping a heartbeat that comes first (the script can send one before its connect).
- **Run it on the Ableton PC** with the PC's own Python: fetch it from `airuleset.py share` (its LAN URL) with `Invoke-WebRequest`, check the SHA-256, then `python probe.py --port <PORT> --seconds 300`. The port is `PORT` in that Live user's `Remote Scripts\FohMixer\Config.py`; read it, never guess. A run longer than about 4 minutes outlasts one MCP call (the client aborts a call silent for 300 s): start it detached (`Start-Process`, output redirected to files) and poll for a marker file. A detached start from the MCP shell can still hold the call open until its timeout; the run goes on regardless.
- **Read the summary with the PC's clocks in mind** (Windows, Python 3.11/3.12): `time.monotonic()` is `GetTickCount64`, 15/16 ms steps, so `main_tick_age_ms` and `gap_ms` come in steps (see `distinct`); `time.time()` (the frames' `ts`) steps every ~0.5 ms there only because an audio app raised the system timer resolution (15.625 ms by default): the summary's `wall_clock_step_ms` is the step the probe measured at its start (the median of nine), and an inbound/outbound split resolves about that plus 1 ms (the `ts` is whole milliseconds). That holds only while the probe reads the script's clock: the summary's `wall_clock` must be `GetSystemTimeAsFileTime()` (Python before 3.13 on Windows, as Live's 3.11; a 3.13+ probe reads a precise clock the script does not). Hence:
  - `result_tick_gap_ms` (gaps between the ticks that queued results; results under 3 ms apart are one tick, since `ts` is whole milliseconds) is the main thread's tick interval — with `--probe-ms` below the tick (`--probe-ms 15 --seconds 5`), not with the default 100 ms, where it shows the read spacing;
  - `read_inbound_ms` (send → the result queued on Live's main thread) and `read_outbound_ms` (queued → received) split `round_trip_ms` on the PC's wall clock; `heartbeat_outbound_ms` is the heartbeat's wait in the sender;
  - `timer_estimate` (2 × the mean age) is not the interval on the PC: the heartbeat thread samples the age just before a tick.
- **Keep the read rate low on the real Live:** the script's sender thread sends about one frame per main-thread tick (~30 frames/s, #5), so reads every 2 ms filled the connection's 1000-result queue in 2 s and the script closed the probe's connection (the hub's own connection is separate and was not touched). `--probe-ms 100` for load runs, 15 ms for a 5 s tick run. The probe keeps at most `MAX_PENDING` (50) reads unanswered and skips its slots past that (`reads_skipped` > 0 means the script's send path fell behind).
- **Compare configurations A-B-A** (e.g. `level`, `lr`, `level` again): run-to-run noise is large on the PC (two identical runs differed by 27 % of a core in the band Live's CPU and by several times in the master's outbound delays), so one before/after pair cannot tell a change from drift. With Live's transport stopped almost no meter moves, so a meter-source comparison then does not exercise the meter traffic; repeat it during a rehearsal. The results of #5: K1 and K2 comments there.
- **Load runs:** a surface open on the FOH page from the dev box (Playwright, PIN via `airuleset.py secret exec --file`, `localStorage.fohmixer_token` from `POST /api/auth`) subscribes every visible strip; the hub's `/api/status` shows `clients` and the subscriptions per instance. The main checkout's `e2e/node_modules` Playwright may want a browser build that is not installed on the dev box: launch Chromium with `executablePath` at an installed `~/.cache/ms-playwright/chromium_headless_shell-*/…/chrome-headless-shell`. Live's CPU per process: `Get-Counter '\Process(<process name>)\% Processor Time'` (100 = one core); the band and master Lives run as differently named processes; write the numbers with the invariant culture (`ToString('F2', [Globalization.CultureInfo]::InvariantCulture)`), since the PC's culture writes a decimal comma into `Export-Csv`. Results go on the ticket without host names, IPs, user names or user paths.
