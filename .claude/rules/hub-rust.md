# Hub and protocol crates (learned on S3, #7)

## Code the mutation gate can judge

- **Never scan with a hand-stepped index** (`while … { pos += 1 }`). A `+=`→`*=`/`-=` mutant loops forever: the timeout recheck then fails the shard ("a hang"), and if the loop grows a `String`/`Vec` it eats the runner's memory ("The runner has received a shutdown signal", the whole shard lost). Count runs with iterators (`iter().take_while(..).count()`, `enumerate().skip(pos)`), and bound a scan loop by the input length (`for _ in 0..=len`). See `fohmixer-proto/src/path.rs` (`run_of`, `read_name`, `steps_from`).
- **Join a helper thread bounded** (#71: `plugwin::Encoder::stop` polls `is_finished()` `STOP_POLLS` × `STOP_POLL`, then leaves it behind with a warn). A plain `join()` in a stop or a `Drop` turns a mutant that keeps the thread waiting (a condvar predicate → `true`) into a hang at every test's end: TIMEOUT, then the recheck, and the shard runs out of its 20 minutes.
- **A branch that only logs survives mutation.** Put the decision in a small pure function with a unit test and log through `if let Some(..) = decision(..)` (`first_of_outage`, `write_failure`, `read_problem`, `pin_warning`, `failure_note`).
- **One counter per kind of id.** A run id and request uuids taken from one counter make the run counter's `+=`→`*=` mutant equivalent (`live/names.rs`: `next_run`, `next_uuid`).
- **Nothing compiles locally, so mind trait bounds in tests:** `Result::unwrap_err` / `expect_err` need `T: Debug` — for a type that must not derive it (it holds a key, e.g. `acme::StoredAccount`) take the error with `.err().expect(..)` (#17 lost a CI cycle to E0277).
- **No struct-update base (`..X::default()`) in a literal the diff adds:** cargo-mutants 27's "delete field … from struct X expression" mutants ignore the recheck's `--re` and fail it with "tested a mutant it did not select". Spell every field out.

## Test harness (`crates/fohmixer-hub/tests/`)

- Host-backed tests start real `sim/host.py` processes: take `support::serial()`, mark the binary `#![cfg(unix)]`, and add a NEW binary to the `hub-hosts` group filter in `.config/nextest.toml`.
- `support::Host` lives in `support/host.rs` (Unix only: it stops hosts with `kill -s TERM`). `tests/layout.rs`, `tests/auth.rs` and `tests/config_cli.rs` need no host and also run in the `windows` CI job (the hub's platform): keep them host-free.
- `Client::next_message` reads in arrival order (pending first) — use it to assert ORDER (offline → online → fresh value); `wait` searches and cannot. `wait`, `next_message` and `gets` drop binary messages (Pro-Q frames); `Client::next_any` (#71 PR I) returns text and binary in arrival order (`Incoming`), so a test sees a frame's place among the pongs (`clear()` the kept text first).
- A client that "never reads" only blocks the hub's writer when the kernel buffers are full: open it on a `TcpSocket` with `set_recv_buffer_size(4096)` and make the hub send megabytes (a `sub` with a ~200 kB bad prop is echoed twice in its `subbed`). Proof that the writer blocked: the client is closed no earlier than `SEND_TIMEOUT` after the burst.
- Expected `values` items come sorted by hub key: `bandx|…` sorts before `band|…` (`x` < `|`).
- **Asserting a log line (#9):** put the line in a small function and read it back in a unit test through a scoped subscriber: `ws/tests.rs` `logged(|| …)` (`tracing_subscriber::fmt()` with a capturing writer, `with_ansi(false)`, `without_time()`, `tracing::subscriber::with_default`). It sets the tests' global `Quiet` subscriber once (writes nothing, `Interest::sometimes()` for every callsite): with a scoped subscriber the only one alive, tracing-core asks the REGISTERING thread's own default about a new callsite, so a callsite first reached on another test's thread (no subscriber) was cached as never and `logged` lost its line (dev run 38919475834, ableset's lock warn; `logged_keeps_a_line_whose_callsite_another_thread_reached_first`). Never add another `set_global_default` to the hub's unit tests. Its output is the hub log's shape: ` INFO <target>: <message> <field>=<value> …\n` (match with `contains`, never `starts_with`). A `%` value is unquoted; a `?` value or a bare `&str` is Debug-quoted. **Log a client's own text quoted** (`?`, as `ws` does for `origin` and `client_report` for its fields): unquoted, a space in it adds fake `key=value` pairs to its line. A test like that kills the "replace with ()" mutant of a function that only logs. For a line the real listener must produce, use the end-to-end form `tests/ws_log.rs`: a global subscriber (`set_global_default`), the binary's only test, then poll the captured log for the line.
- **A watched file rewritten in place (#5):** `std::fs::write` truncates, then writes, so the layout poll (100 ms in `TestHub`) can read the file empty and report `layout does not parse` for a moment. Wait for the exact error of the content the test wrote (`status_until` on `starts_with("layout is invalid: ")`), never for the first error of any kind (`error.is_some()`): the hub recovers on its next poll and never serves a partial file. `tests/layout.rs` pins both moments.
- **A LAN peer in a test is a private address** (`10.0.0.5`, as in `routes.rs` `lan()`). The documentation ranges (192.0.2.x, 198.51.100.x, 203.0.113.x) are public to `access::is_private_ip`, so they are `internet`. Use them for a forwarded client or a port-forwarded peer.
- The Stream Deck's tests (#52) use the scripted fake Companion `tests/support/companion.rs` (a tokio listener; `Script` sets the API version, an `ADD-DEVICE` refusal, silence; `refuse(true)` closes the open connection and new ones at once; `close()` is a clean FIN; lines kept with their connection and time): `tests/companion_client.rs` drives `CompanionHandle` directly, `tests/deck.rs` (12 tests) the whole hub. Both are host-free (also in the `windows` job) and in the `hub-hosts` nextest group (timing checks: 2 s pings, the 2 s silence, 5 s of Companion's silence). A page attached before Companion's `ADD-DEVICE OK` gets a `deck` saying offline, then one saying online: `wait` for `online` leaves the offline one pending, so `clear()` the client before waiting for a LINK LOSS's `deck` (`tests/deck.rs` `…logged_lost…`). A stopped hub's records: poll `support::events_in(dir)` (the writer thread may still be flushing). `lib.rs` `the_stop_waits_for_the_companion_task_to_remove_its_device` proves the stop waits for the task (a Companion that never answers: the stop lasts at least `STOP_BOUND`); `graceful_stop.rs` `sigterm_removes_the_stream_deck_from_companion` proves the binary's stop sends `REMOVE-DEVICE` before the process ends.

## Design facts to keep

- Subscription table (`live/subs.rs`): a guard is its own entry, key `hub_key(..)|guard` (never a client's key, those end in `|true`/`|false`); a guard keeps its Live key when its re-resolution fails, so a rename back fires it again. A new `sub` of a name binding or of one in error resolves it again (a page switch, a reconnect). While a client entry a list guard guards is in error, `sync_watches` (run at the top of `drain_outgoing`, fed by `watch_dirty`: a list guard's value change, a dependent's error starting or ending, a dependent added or dropped, a disconnect) keeps one `name` guard per item of the list (`<list> <i>`, from the list guard's value, which the script encodes as a list), so a rename of any item re-resolves the name bindings: a binding made while its name was missing heals by itself (#58, no REFRESH ALL). A sync that adds watches also sends the list's bindings in error and their guards again, after the new watches (an index target sorts before a name step's `[`), so a rename that lands before a watch is heard is still found and the name guard gets its object. A watch on an index path is resolved again only when a list fired (`re_resolves`): a rename moves no index. Real Live answers a list property as `Base.Vector` (module `Base`); the script's codec takes that as a vector (#58), so the list guard's value is the list. `seq` is numbered across the table. A track of `live_set` by index (`tracks N …`, `return_tracks N …`: a marker strip, #68) is guarded by its list (`track_by_index`, `Entry.indexed`): a list change resolves it again and its value in that frame is not delivered (a track inserted, moved or deleted puts another object at the index; without this a key both layouts share kept showing the old track); the item name watches serve name bindings only. Generic index bindings in the unit tests use `live_set scenes N`.
- **The rules' transport (#104, #130, D18, `router.rs`):** `RULES_CLIENT` (0, clients count from 1) subscribes every instance's `live_set` `is_playing` in `Router::new` (`TransportWatch { key, playing }` per instance; the table resolves it at the connect). `flush` collects `RULES_CLIENT`'s deliveries and hands each to `on_transport` after the loop: a value that changes the instance's transport (`transport_change(prev, playing)`, pure: none for the same value) is one `transport` record `{instance, playing, prev}` (`prev` null for a session's first value; a `Disconnected` forgets it, so the first value after a reconnect is a first one again) and one info line, then STAGE AUT (`stage_value(bool)`) when its target is in that instance, then REVERB (`reverb_transport`; the rule follows only its first fader's instance); a delivery with an `error` (the listener failed: `transport_heard`, pure, the error before the value) is one warn line `the rules cannot follow the transport` and a `transport` record `{instance, error}` (warn class by its error), and forgets the transport (`transport_failed`; review M6), REVERB's too (`reverb_transport_lost`: its wait ends); `set_stage_binding` keeps the target only (no subscription of its own) and applies the instance's transport as last heard (`transport_now`). STAGE AUT's steps are `stage_aut` records: `{step: "flag", on, client, peer}` at every `set_hub` of it, `{step: "write", instance, mute}` before each write and `{step: "failed", target, problem}` from the write's task. Both kinds are warn class (`is_warn`). `/api/status`: `RULES_CLIENT` is in the `own` lists, so `subscriptions` and `listeners` count the pages' only (the e2e `expectHubToHold` is the page's `data-subs` exactly), and each instance carries `playing` (`InstanceStatus.playing`, `#[serde(default)]`). A router unit test that counts `subs.subscriptions("band")` counts the rules' transport too (1 on a bare router). The router unit tests feed Live's answers through the table itself (`answer_listeners`: `subs.connected`, `drain_outgoing`, `on_result`; later pushes `on_values`) and `flush`: a page and the rules on the one `is_playing` entry each get their delivery, and the page's unsub leaves the rules following (review M7); a `flush` mutant is caught there at once, never only by the host tests' timeouts.
- **REVERB and REVERB AUT, and the fader links' switches (#130, D18, PR 2 and PR 4):** `rules/reverb.rs` (pure, tests in `rules/reverb/tests.rs`) is the whole rule: `Reverb::set_faders` takes each served layout's `Layout::reverb_faders` (the placed `+REVERB` strips by index with their volume targets, each with its write key) and every input (`live`, `cached`, `transport`, `tap`, `set_aut`, `hand`, `applied`, `tick`, `offline`, `tracks_changed`, `tracks_known`, `tracks_served`) returns `Act::{Write, Step, Save, Tell}`; `step_line` / `step_warn` (WARN: `stopped`, `skipped`, a `restored` with faders still waiting). The numbers are literal-tested constants (`DROP_DB` 10, `STOP_WAIT_MS` 2000, `LOWER_MS` 2000, `TAP_MS` 500, `RETURN_MS` 500, `STEP_MS` 25, `SAME_VOLUME` 1e-6); a `Glide` is linear in dB on `fohmixer_proto::volume` (each end at the −70 dB floor at least) and its last step writes `to` exactly, so a return lands on the remembered Live value bit for bit. A fader is known by identity `(instance, label)`, never its index: a new layout takes the held state by label (`take_over`; a target that moved stops its glide, `stopped why=layout`, and so does a fader the layout drops mid-glide), a held fader the layout no longer names waits in `restore` (saved too) until one names it (`restored {faders, waiting}`); a lowering for the stop restored while AUT is on and Live plays returns at once. `set_faders` emits `Save` only when `saved()` changed, so a `hub-state.json` the hub could not read stays until a value changes (`HubState::load`). A first transport value (`playing` was none: a hub start, a reconnect, a set load, a new followed Live) never lowers; it only returns (playing, `low == Stop`, AUT on). When the stop's wait ends with nothing to lower (every fader in the hand, silent or without a value) the rule records `cancelled` and tells the pages (the wait is over). **`low` means the rule holds at least one fader lowered:** the last one let go (a page, Live, a track-list change) ends it (`drop_low`: `low` none, no `reverb_low` saved), and a return with nothing to move records no `return`. **`RUKA` lasts until the next stop or lowering (F30; #130 PR 5 review M2, the main session's ruling):** a fader let go (`hand`, by a page or by Live) keeps it through a start and a tap back (`return_all` returns the held faders only and clears no hand, so whether another fader was still held changes nothing); every stop of the followed transport clears every hand, with AUT on or off (`transport`'s stop arm, `drop_hands`; with AUT on it then waits and lowers), and a lowering clears the hand of each fader it takes (a tap down asks for every fader, the hand's too; AUT's lowering takes the faders the stop freed). A first transport value is no stop and clears nothing. `hand` is not saved: a hub restart forgets it. **A return never writes blind:** a held fader whose Live value the hub has not heard (a restart, a reconnect, an offline instance) stays held with its return pending (`Fader::pending`, one `pending` record) until its first value: at `left` it glides back from there, elsewhere it is let go by Live (`hand`); a lowering takes a pending fader back as held, a tap down over a waiting return too (`tap`'s `(true, true)` with a pending fader: `lower`, recorded with nothing to move: "their waiting return is off"); a layout that drops a pending fader keeps the flag in `restore` (`Waiting`: each saved fader and its pending flag), so the strip named again comes back waiting. **A recomposed fader's value:** `reverb_layout` hands the rule the table's value of EVERY followed key after `set_faders` (`Reverb::cached`: taken only by a fader with no value yet), the keys followed before too: a track-list change can move a fader onto the other reverb's old key, which needs no new subscription, and without it that fader would wait for good (review N1); M6's restore runs inside `set_faders`, before these values, so it resolves at once. **A lowering during a return** (a tap back then down within 0.5 s, two pages' taps crossing) keeps the song level: a fader not held glides only back up, so `lower` takes that glide's end (`Glide::to`) as `back` and glides down from where the return is. A transport listener failure (`transport_failed` → `reverb_transport_lost` → `transport_lost`) forgets REVERB's transport and ends its wait (`cancelled`): an unknown transport never lowers. A track-list change lets go of a fader it stops mid-glide (its value lies between the levels for good, never at `left`); a held fader at rest stays held and unsettled until Live reports `left`; it saves only when what the rule holds changed (as a layout). **Accepted (round-3 note 1):** after a track-list change, a move made in Live itself (not on a page) on a lowered reverb is not seen as a hand until Live reports `left` once; a page's move is still seen (the conservative direction: never a false hand). **The window (review W1, M1, W2, M3):** a track-list change (`tracks_changed`) or a disconnect (`offline`, W2: a set loaded or a track moved meanwhile shows only in the connect's read) opens the instance's window (`moved`; one `window {instance, open: true, why: tracks|offline}` record when it opens; only for a Live the rule has a reverb fader of, on a layout or in `restore`, `has_fader_in`, so a Live without one gets no vacuous record); while it is open nothing is written to that instance's faders: a lowering skips them (`skipped` "track list"), a return waits (`pending` with `why: "track list"`; a return waiting for Live's value is `why: "value"`), and Live's values of a held fader are kept and judged when it ends (`Fader::unjudged`, `resume`), never by an index that may be stale. Only the router ends it, instance by instance, once the instance's markers are settled (`reverb_settled` = `tracks_settled(Keeper::settled, markers_pending)`: no read of it runs, none failed or was missed by a disconnect since its last whole read (`Instance.unsure`, set by `Keeper::disconnected`, which also drops the read in flight so an answer handled after the disconnect is void (review N1), and by a failed read; the migration's `stale` names move no strip), and no composition waits): at the `MarkersRead` answer and at a `markers_settled` that serves nothing (`tracks_known`, `why: settled`), and after every layout's faders and their cached values (`tracks_served`, `why: layout`); `set_faders` itself ends no window (M1: a composition that predates the instance's newest read, such as a second list change within the first composition's quiet time, leaves the window to that read). A failed read keeps it open until a read answers (the keeper's retries; after `CONNECT_RETRIES`, or a definite refusal, until the next read, as the surface's own layout waits). A lowering also takes back the faders waiting in `restore` (their pending flags clear, their `by` becomes the lowering's; a tap down counts them too, `waiting_return`); when that changes `restore` and no surface fader is held, it still records `lower` with no faders, sets `low` and saves (M2), and the stop's wait ends `cancelled` only when it lowered nothing (`lowers`). The router tests drive the closing points through `handle` on `marked` (a router whose keeper composed Rev ST and Rev PA from its own read; `next_read` takes a read's offline answer, `read_answered` answers both batches as Live would, `settle` the quiet time). **Accepted (review M5 a):** a disconnect or a hub restart inside the 2 s lowering leaves a fader between the song level and `left`; at the reconnect or the restore its value is elsewhere, so it is let go: the hand-wins direction, a 2 s window, and the surface shows the real value. Likewise an interrupted 0.5 s return (a track-list change, which lets the fader go, or an offline instance): the fader is left between levels, and the next lowering takes that level as its song level. Its glue `router/reverb.rs` (tests in `router/reverb/tests.rs`): the rule's own subscriber and writer `REVERB_CLIENT` (`ClientId::MAX - 2`, peer `rule:reverb` in `Router.peers` from `new`) subscribes each fader's volume (`reverb_layout`, `watched`; in the `Status` `own` lists, so `/api/status` `subscriptions`/`listeners` stay the pages'); `flush` hands its deliveries to `reverb_value`, then the marker keeper's `tracks`/`return_tracks` values to `reverb_list` (`list_instance`; only a CHANGE within a session is a track-list change, `list_changed`: a connect's first list value is none, and `reverb_offline` forgets the instance's lists, so a reconnect's values are judged as Live's own once the connect's read ends the window and a fader found elsewhere is the hand), all before the transport.
