# Hub and protocol crates (learned on S3, #7)

## Code the mutation gate can judge

- **Never scan with a hand-stepped index** (`while … { pos += 1 }`). A `+=`→`*=`/`-=` mutant loops forever: the timeout recheck then fails the shard ("a hang"), and if the loop grows a `String`/`Vec` it eats the runner's memory ("The runner has received a shutdown signal", the whole shard lost). Count runs with iterators (`iter().take_while(..).count()`, `enumerate().skip(pos)`), and bound a scan loop by the input length (`for _ in 0..=len`). See `fohmixer-proto/src/path.rs` (`run_of`, `read_name`, `steps_from`).
- **A branch that only logs survives mutation.** Put the decision in a small pure function with a unit test and log through `if let Some(..) = decision(..)` (`first_of_outage`, `write_failure`, `read_problem`, `pin_warning`, `failure_note`).
- **One counter per kind of id.** A run id and request uuids taken from one counter make the run counter's `+=`→`*=` mutant equivalent (`live/names.rs`: `next_run`, `next_uuid`).
- **Nothing compiles locally, so mind trait bounds in tests:** `Result::unwrap_err` / `expect_err` need `T: Debug` — for a type that must not derive it (it holds a key, e.g. `acme::StoredAccount`) take the error with `.err().expect(..)` (#17 lost a CI cycle to E0277).
- **No struct-update base (`..X::default()`) in a literal the diff adds:** cargo-mutants 27's "delete field … from struct X expression" mutants ignore the recheck's `--re` and fail it with "tested a mutant it did not select". Spell every field out.

## Test harness (`crates/fohmixer-hub/tests/`)

- Host-backed tests start real `sim/host.py` processes: take `support::serial()`, mark the binary `#![cfg(unix)]`, and add a NEW binary to the `hub-hosts` group filter in `.config/nextest.toml`.
- `support::Host` lives in `support/host.rs` (Unix only: it stops hosts with `kill -s TERM`). `tests/layout.rs`, `tests/auth.rs` and `tests/config_cli.rs` need no host and also run in the `windows` CI job (the hub's platform): keep them host-free.
- `Client::next_message` reads in arrival order (pending first) — use it to assert ORDER (offline → online → fresh value); `wait` searches and cannot.
- A client that "never reads" only blocks the hub's writer when the kernel buffers are full: open it on a `TcpSocket` with `set_recv_buffer_size(4096)` and make the hub send megabytes (a `sub` with a ~200 kB bad prop is echoed twice in its `subbed`). Proof that the writer blocked: the client is closed no earlier than `SEND_TIMEOUT` after the burst.
- Expected `values` items come sorted by hub key: `bandx|…` sorts before `band|…` (`x` < `|`).
- **Asserting a log line (#9):** put the line in a small function and read it back in a unit test through a scoped subscriber: `ws/tests.rs` `logged(|| …)` (`tracing_subscriber::fmt()` with a capturing writer, `with_ansi(false)`, `without_time()`, `tracing::subscriber::with_default`). Its output is the hub log's shape: ` INFO <target>: <message> <field>=<value> …\n` (match with `contains`, never `starts_with`). A `%` value is unquoted; a `?` value or a bare `&str` is Debug-quoted. **Log a client's own text quoted** (`?`, as `ws` does for `origin` and `client_report` for its fields): unquoted, a space in it adds fake `key=value` pairs to its line. A test like that kills the "replace with ()" mutant of a function that only logs. For a line the real listener must produce, use the end-to-end form `tests/ws_log.rs`: a global subscriber (`set_global_default`), the binary's only test, then poll the captured log for the line.
- **A watched file rewritten in place (#5):** `std::fs::write` truncates, then writes, so the layout poll (100 ms in `TestHub`) can read the file empty and report `layout does not parse` for a moment. Wait for the exact error of the content the test wrote (`status_until` on `starts_with("layout is invalid: ")`), never for the first error of any kind (`error.is_some()`): the hub recovers on its next poll and never serves a partial file. `tests/layout.rs` pins both moments.
- **A LAN peer in a test is a private address** (`10.0.0.5`, as in `routes.rs` `lan()`). The documentation ranges (192.0.2.x, 198.51.100.x, 203.0.113.x) are public to `access::is_private_ip`, so they are `internet`. Use them for a forwarded client or a port-forwarded peer.
- The Stream Deck's tests (#52) use the scripted fake Companion `tests/support/companion.rs` (a tokio listener; `Script` sets the API version, an `ADD-DEVICE` refusal, silence; `refuse(true)` closes the open connection and new ones at once; `close()` is a clean FIN; lines kept with their connection and time): `tests/companion_client.rs` drives `CompanionHandle` directly, `tests/deck.rs` (12 tests) the whole hub. Both are host-free (also in the `windows` job) and in the `hub-hosts` nextest group (timing checks: 2 s pings, the 2 s silence, 5 s of Companion's silence). A page attached before Companion's `ADD-DEVICE OK` gets a `deck` saying offline, then one saying online: `wait` for `online` leaves the offline one pending, so `clear()` the client before waiting for a LINK LOSS's `deck` (`tests/deck.rs` `…logged_lost…`). A stopped hub's records: poll `support::events_in(dir)` (the writer thread may still be flushing). `lib.rs` `the_stop_waits_for_the_companion_task_to_remove_its_device` proves the stop waits for the task (a Companion that never answers: the stop lasts at least `STOP_BOUND`); `graceful_stop.rs` `sigterm_removes_the_stream_deck_from_companion` proves the binary's stop sends `REMOVE-DEVICE` before the process ends.

## Design facts to keep

- Subscription table (`live/subs.rs`): a guard is its own entry, key `hub_key(..)|guard` (never a client's key, those end in `|true`/`|false`); a guard keeps its Live key when its re-resolution fails, so a rename back fires it again. A new `sub` of a name binding or of one in error resolves it again (a page switch, a reconnect). While a client entry a list guard guards is in error, `sync_watches` (run at the top of `drain_outgoing`, fed by `watch_dirty`: a list guard's value change, a dependent's error starting or ending, a dependent added or dropped, a disconnect) keeps one `name` guard per item of the list (`<list> <i>`, from the list guard's value, which the script encodes as a list), so a rename of any item re-resolves the name bindings: a binding made while its name was missing heals by itself (#58, no REFRESH ALL). A sync that adds watches also sends the list's bindings in error and their guards again, after the new watches (an index target sorts before a name step's `[`), so a rename that lands before a watch is heard is still found and the name guard gets its object. A watch on an index path is resolved again only when a list fired (`re_resolves`): a rename moves no index. Real Live answers a list property as `Base.Vector` (module `Base`); the script's codec takes that as a vector (#58), so the list guard's value is the list. `seq` is numbered across the table. A track of `live_set` by index (`tracks N …`, `return_tracks N …`: a marker strip, #68) is guarded by its list (`track_by_index`, `Entry.indexed`): a list change resolves it again and its value in that frame is not delivered (a track inserted, moved or deleted puts another object at the index; without this a key both layouts share kept showing the old track); the item name watches serve name bindings only. Generic index bindings in the unit tests use `live_set scenes N`.
- Outbox: instance states are ORDERED with the replies (not coalesced); `offline` drops the instance's pending values.
- Live client: no request goes out before the script's `connect` names this instance; while connecting or offline a request is dropped (the caller reads "offline").
- Live client (#9): requests are written by a writer task of their own (`write_requests`); the session's `select!` loop only reads frames, ticks and queues, and never awaits a socket write. A write that waits (the script reads slowly) must not stop the heartbeat stamping, or the instance flaps busy while Live is fine (one of the two mechanisms the #9 flapping could come from; which one the PC hit is for its log to tell). `tests/live_client.rs` `deaf_script` (a 4 KB receive buffer, never reads, 16 MB of requests) proves it.
- Busy (#9): `busy_reason` is the one decision (150 ms tick age, 300 ms heartbeat overdue — never raise the 300 ms); the session logs it on every change, and `late_heartbeat` logs a heartbeat after an overdue gap with the script's `gap_ms` (long: the script did not make it; since #5 it is made in Live's main-thread tick, so a stall stops the heartbeats and the first one after reports it) and its time on the way (`ts` to `wall_ms`, one PC clock). Read those lines in the PC's `hub.out.log` before guessing where a late heartbeat was held.
- Layout schema 2 (#21): every struct and the `Control` enum have `deny_unknown_fields`; the internally tagged `Section` has none of its own (its newtype variants `Group` / `Pager` deny). One id namespace (pages, sub-pages, groups, pagers); `Page::controls` / `Layout::controls` are the one document-order walk the hub's `bindings()` and `stage_aut_binding()` use.
- `/api/status` carries `connect_failures`, `last_error` per instance and `layout.unresolved` (checked on layout accept and on connect; `live/names.rs` `layout_targets` checks the controls' bindings — a new name-bearing layout field belongs there too; #58 removed `config.unfold`). Per instance also `unfolded`: the groups the router's unfold keeper holds (`router/unfold.rs`, #58).
- Client reports (#26, `client_report.rs`): `POST /api/client-report` is public (before a login; Access guards the internet path), 10 KiB like `/api/client-error`. Only `fohmixer_proto::client::ReportFields` survive (serde drops the rest; a new field goes into `clean_fields`, the log line and the route tests' expected JSON — #5 K4 added `fps`, `long_frame_ms`, `touches_max`, `pointer`, all text from the page), each value `clean`ed (control characters out, 64 characters, `ua`/`error` 300), logged at INFO as `client report` with `peer`, `client` (the `cf-connecting-ip` of an internet request, `forwarded_client`) and `source` (`access::classify`), the newest 50 kept for `/api/status` `client_reports` — next to `clients`, the socket count, which keeps its meaning. A peer's budget is 60 per 10 s (`Budget`, at most 256 peers tracked); over it the report is dropped with one warn per window, and the answer is still 204 (a 429 is a console error on the page). The ring drops one per push with an `if`, never a loop a mutant could spin in.
- Writes (#43, protocol 2): a page's control write is a `set` (`seq`, page `t`, `final`), never a `cmd`; the router hands it to the instance's `setter.rs` (pure: latest want per key, one `set_prop` batch in flight through `LiveHandle::call`, `superseded` when another client's newer arrival takes the slot, a disconnect forgets the batch in flight and the pending wants without acks) and `router/writes.rs` carries the batches out (the result comes back as `RouterMsg::Applied`). Acks and each instance's `link` are coalesced in the outbox (per key the ack of the highest `seq`; per instance the latest `link`), after the values. `cmd` stays for reads.
- The event log (#43, `events.rs`): `EventLog::record(ev, fields)` never waits (a bounded channel; a full one counts `dropped`), one writer thread per hub writes `<data>/logs/events-<UTC date>.jsonl`, flushes per burst, sweeps files past 60 days at start, when the day turns and hourly while idle, and past a day's 256 MB writes only warn-class records (`is_warn`: a `trace` only when it holds a `dropout` or a `reset`, since PR C's flight recorder made the page's batches bulk; the Stream Deck's `deck_link`, `deck_release`, `deck_press`, `deck_ok` and `deck_view`, #52, while `deck_key`/`deck_keys` stay bulk). Record fields are built by small pure functions (`ws::sock_fields`, `ws::trace_fields`, `router::writes::set_fields` / `ack_fields`) so a test reads them back; a client's first set of a touch (`setter::SetOutcome::touch_start`: no set of the key from that client before, the previous one final, or `starts_touch` — over `TOUCH_GAP_MS` = 500 ms of the PAGE's clock after the previous one, so a stalled link never cuts a drag in two) carries `live_before`, `Subs::live_value(write key)`: the cached value of `<key>|true`, else `<key>|false` (what the hub pushes to pages), null when none; the field is absent on the touch's other sets (#43 PR D); the writer is tested on a temp folder through `Writer::take` and `EventLog::channel`, the end-to-end form reads `TestHub::events()` / `events_until` (`tests/ping.rs`, `tests/setter.rs`). A page's clock maps to the hub's through its pings (`clock.rs`, Cristian: a ping carries the latest pong's round trip with the number of the ping it measured, `rtt_n`, and the hub pairs it with that ping's own time and arrival from a ring of the last 64 pings, never with the carrying ping's (on a slow link the measured ping is n − 2 or older; a number not in the ring gives no sample); the lowest-RTT exchange of the last minute wins; a clock step, an exchange whose offset lies over `STEP_MS` = 500 ms from the estimate beyond half of each round trip, `clock::step`, drops the stored exchanges and starts the window over from it, so the Stream Deck's late gate never refuses on-time downs, or lets late ones through, for a minute after a time sync or a page's sleep: logged once, a warn line (at most one per client per 10 s, `ws::step_warn_due`, #54) and `clock_step_ms` on that `ping` record, #52); a `set` record carries its socket's last offset and the one-way delay. The hub's `serde_json` has `float_roundtrip`: a page's 17-digit ms times must reach the pong and the event log to the bit (the default parser misreads some, which the first E2E run of `link.spec.ts` caught). An outbox keeps per write key the ack of the highest `seq` (a late result of an older write must not hide that a newer one was superseded).
- Socket lines (#9, `ws.rs`): `client connected` / `client disconnected` carry `client` (the socket number, as on every `ws` line), `peer`, `forwarded`, `source` and `origin`. `ws::opener` works them out from the upgrade's `ConnectInfo` and headers:
  - `source` is `client_report::source(access::classify(..))`, the one classifier.
  - `forwarded` is `client_report::forwarded_client` (`cf-connecting-ip` of an internet upgrade, cleaned), `"-"` without one, Debug-quoted. A client report calls the same value `client`; on a socket line `client` is the socket number.
  - `origin` is the page's `Origin` host through `access::origin_authority`, the Origin guard's parser, `clean`ed to 64 characters, or `-` without one. It is Debug-quoted on the line, and so is `source` (`source="lan"`, as in a client report).

  A new per-client field belongs on those lines too, never in a second classifier or parser.

- **The unfold keeper (#58, `router/unfold.rs`, `UNFOLD_CLIENT` = `ClientId::MAX`):** Live meters no track inside a folded group (verified on the PC: frozen `output_meter_level`, no listener pushes), so the hub holds open every group a strip's track sits in, up the chain. Live lets no one listen to a track's `group_track`, `fold_state` or `is_visible` (`not observable`, read on the PC; SimLive now matches), so the keeper listens to each instance's `live_set` `tracks` and `visible_tracks` (a fold or unfold changes it) and on every value (and a layout change, a connect, a retry) reads, in one batch, the `name` and `fold_state` of `tracks[name=T] group_track`, `… group_track group_track`, … up to `MAX_DEPTH` for each strip track (an error past the top); a folded group (real Live `true`, SimLive 1) gets `set_prop fold_state false` through that same path, so a group named like another unfolds the right one. A newer read voids an older answer (`reads`, its own counter); a layout without an instance's strips voids its read in flight; a failed read is logged and tried again after `RETRY_MS` (2 s), at most `MAX_RETRIES` (3) in a row (`RouterMsg::UnfoldRetry`). The router carries out a batch in two fixed steps (`unfold_apply`: subscriptions, then their cached values, which ask only for reads), never in a loop a mutant could make endless. Its subscriptions are the hub's own: `/api/status` `subscriptions` leaves them out (`Subs::subscriptions_besides`), `unfolded` lists the groups the latest reads found. A strip whose track name is ambiguous (SimLive's `Keys 1`) has no group: test with `Drums #` (in `Stems grp#`). Until the owner-timed Live restart loads the 0.1.0-dev.37+ script, Live answers both lists as a `<Base.Vector …>` string, which may not change on a fold.
- **The marker keeper (#68, spec D16, `router/markers.rs`, `MARKERS_CLIENT` = `ClientId::MAX - 1`; glue `router/markers_io.rs`):** finds each instance's Tuner markers and hands every changed set to the layout store (`LayoutStore::set_markers`), which composes its frame file with them (`fohmixer_proto::markers::compose`) and bumps the revision only when the composition changed (I10, its own `served.json.<stamp>` backups); the router then handles `layout_msg(rev, …)` as it does a file change. It listens to `live_set` `tracks` and `return_tracks`; a list value that differs from the last one reads every track's `devices`, then the `class_name` of every device of class `Device` (Live's own: a rack, plug-in or Max device is never a Tuner), and after each read keeps every track's `devices` it already holds (the subscription table binds an index path of `live_set tracks` to the new object when the list changes) and subscribes every Tuner's `name` AFRESH (a device inserted before a Tuner moves it, and a device list is no list the table guards). A list change gives every track's `devices` a new value, each asking for a read in one flush: the router hands a flush's values to `Keeper::values`, which keeps only the last read of each instance (`latest_reads`; a newer read voids an older answer). The store writes a served backup under its lock, as `poll` does (two writers never pick the same free name). A value equal to what the read saw starts nothing (no endless read on a fresh subscription's first value); a Tuner's `name` value updates that Tuner without a read. Real Live 12.2 observes `Track.devices` and `Device.name` (probe on #68); no `insert_device` there. Its subscriptions are the hub's own (`subscriptions_besides(n, &[UNFOLD_CLIENT, MARKERS_CLIENT])`). Retries as the unfold keeper (`RETRY_MS`, `MAX_RETRIES`; only a whole read resets the count). `/api/status` `listeners` counts a guard only for the clients it serves (`Subs::serves_besides`: an item watch guards a list guard, which guards the bindings), so the keeper's list guards stay out. The store names a backup the next free millisecond when its own is taken (`free_backup_name`: the poll's served backup and the markers' next often share one); `tests/layout.rs` counts only `layout.json.*` backups. A change waits `SETTLE_MS` (300 ms) for the next one (`RouterMsg::MarkersSettle` with a generation: a set load or a burst of edits is one new layout), and the router ignores a `Layout` whose revision is not newer than its own (two producers: the poll and the markers). The frame's own rules (`markers::frame_problems`, in `layout::check`): no view page, no id starting `view-`, no strip in a `tags` group's controls (its other controls follow its marker strips, `fill`). `tests/markers.rs` drives it end to end with the host's `tuner` and `delete-track` lines, the router tests prove the retry, the quiet time and the store hand-off. **The migration (PR C):** `fohmixer_proto::markers::migrate::migration(frame)` gives the converted frame, each track's planned marker and its `problems` (`LayoutStore::migration` adds one for a migrated group whose name Tuner markers in Live other than the planned ones already use); `GET /api/markers/migration` (a token) first reads every instance's `tracks` and `return_tracks` afresh (`markers_migration` → `RouterMsg::MigrationLists` → `Keeper::refresh`: Live fires no list listener on a track's rename, so the kept names may be old; a changed list starts a read), (an instance whose lists did not answer is `stale`: it counts as `reading` and gets no rename until a fresh read answers), then answers `Keeper::migration_rows` (each planned track found by name in those lists, whose items carry `name`: matches, index, plain and marker Tuners, done), the frame's `problems` (`Migration::problems`: what a marker cannot carry — a track pinned or guarded in one group only, twice in a group, a width, label, path or a strip kind unlike its track's, a control before its group's last strip) and `reading` (a read running); `POST` adds `Keeper::renames` (a ready row: one track of the name, one plain Tuner, no marker; none while the frame has a problem or the instance's read runs) carried out as `Action::Rename` → `set_prop name` on the Tuner's `$ref` as the last read saw it (`markers_rename`: a device inserted before it since moves no rename onto another object; a deleted one answers stale); the script's registry starts over with each connection, so a connect (`LiveEvent::Connected`) and a failed rename (`RouterMsg::MarkersRetry`) read the Tuners and their refs again; the new name returns through the Tuner's own `name` watch. `fohmixer-hub markers plan|frame` (the CLI, `layout::plan_lines`, `migrate_file`: a new file only, refused while `problems`; `plan` exits 1 and prints them) print or write it on the PC: their output holds track names. Equal labels (also across the instances: a KONFLIKT) take the track's name without its marks, then a number: such a label changes on the surface.
- The Stream Deck (#52, `companion.rs`, `companion/client.rs`, `deck.rs`, `deck/holders.rs`, `router/deck.rs`): one Companion task like a Live client (a writer task AND a reader task: the session's `select!` awaits no socket; lines read with `take(MAX_LINE + 1).read_until`, 2 MiB, Companion's own cap; `bitmap_px` allows 32..=512). Companion 5.0.7 facts the code rests on (the plan `docs/superpowers/plans/2026-10-06-streamdeck-tab.md` has the probe): every line ends with a space; a bare `ERROR MESSAGE=` answers no press (only `KEY-PRESS OK|ERROR` feed the `Fifo`); it closes a socket silent for 5 s (the 2 s ping is required); it keeps a key held when its surface goes away, so the router releases the keys held at a link loss after the next `ADD-DEVICE OK` (`deck_release reason=reconnect`) and at the stop before `REMOVE-DEVICE`. A release (a page's up or the hub's own) forwarded into a link that is already dead (up to 5 s of silence before the loss shows) has left the holder set and is answered `offline`: `Deck::answered` (`release_lost`) puts its key with those, so it is released after the reconnect too (every `offline` answer reaches the router before the next `Up`: the task answers a session's waiting presses before it reports the next registration, and presses it refuses while not registered come after the `Down`, still before that `Up`); a release of a key it does not hold is a no-op. A fresh `DEVICEID` per connection (`fohmixer-<attempt>`), one `SERIAL` (`fohmixer`). Every press gets exactly one answer: Companion's `KEY-PRESS OK|ERROR`, or `offline` (no session, the link lost, the stop; a press after the stop is answered `offline` by the handle itself). A down whose one-way delay (`clock::one_way_delay`, as a `set`'s) is over `DECK_LATE_MS` = 500 ms (`deck::late`: 500 not late, 500.001 late, no offset yet not late) is `PressOutcome::Late`: not forwarded, not held, `reason: "late"`, acked `ok: false, error: "late"` (it waited in a stalled page link; spec §0 "nothing late"); an up is never refused for its delay. `tests/deck.rs` gives the socket its offset with two pings (the second carries the first's round trip) and sends presses at a chosen page `t`. The router owns the holders (one down/up per key whatever the fingers), the viewers (keys only to them, `Outbox::deck_key` written last, at most `DECK_KEYS_PER_TAKE` = 4 per batch round the key numbers from the one after the last written, the rest at once in the next batch after what came meanwhile, so a pong queued meanwhile is not kept behind a whole page of images; the writer's send returns once a frame is in the TCP send buffer, so on a slow link a pong can still wait behind about one send buffer (~64 KB) of key frames, far less than a page; `forget_deck` on a closed tab drops the waiting keys and restarts the round at the lowest key), the 2 s silent-holder release (`RouterMsg::Heard` from every page message, `RouterMsg::Tick` every 100 ms) and the `deck_key` rules (pressed change, 10 s after a press, 1/s per key while viewed, a `deck_keys` summary a minute; images only as FNV-1a hash and size). The stop: the router's `deck_stop` (`Deck::stop`'s `release` keys forwarded as `deck_release reason=stop`, then `CompanionHandle::stop`, one channel so `REMOVE-DEVICE` comes after them; its `lost` keys (held when the link went, or a release the link lost, and the link still down) are only logged `deck_release reason=lost`, warn class, nothing sent: in that double fault the key stays held in Companion until its next press), and `serve_until` awaits `HubInner::companion_stopped` (bounded 1 s, `COMPANION_STOP_WAIT`). The stop's releases are answered after the router ended, so they get no `deck_ok` record; their `deck_release reason=stop` record is the trace. The task's stop is graceful: after the stop's lines the writer shuts its half down (the FIN) and the reader reads on until Companion answers `REMOVE-DEVICE` (`OK`/`ERROR`), closes, or `STOP_BOUND` (500 ms) passes; only then is the socket dropped. Never close it at once: a close with unread data sends a reset that can make Companion drop the stop's lines (a key left held). `Deck::stop` leaves `online`/`down_at` as they are: never read `status()`/`snapshot()` after a stop expecting a reset.
