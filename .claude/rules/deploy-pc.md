# Deploy on the Ableton PC (S5, `docs/superpowers/specs/2026-09-28-s5-deploy-design.md`)

- **Only a hosted-CI build of `master` is installed.** The `bundle` job (master pushes, after `wasm` + `windows`) uploads `fohmixer-windows-<version>-<sha>`: one zip with `fohmixer-hub.exe` (release, real UI embedded), `fohmixer-tray.exe` (release, #39), `THIRD-PARTY-NOTICES.md` (#71: the repo root's notices, the IJG credit jpeg-encoder's licence asks for; a new licence notice goes into that file, `deny.toml`'s exception names it), `FohMixer\`, the `scripts/fohmixer-pc` scripts, `VERSION` and `SHA256SUMS`. `gh run download <run> -n <name>` yields that zip. `New-FohBundle` in `FohmixerPc.psm1` builds it (`-HubExe`, `-TrayExe`), the module the install itself uses. The module dot-sources its parts (`FohmixerLivePrefs.ps1`, `FohmixerFirewall.ps1`, `FohmixerRemote.ps1`, `FohmixerTray.ps1`, `FohmixerHubProcess.ps1`: the running hub, `FohmixerTasks.ps1`: our tasks and their read-back); each is in `$script:BundleFiles`, and a new part goes there too.
- **Install** (elevated Windows PowerShell 5.1 on the PC, e.g. over MCP): unzip the bundle to a temp folder, then `powershell -NoProfile -ExecutionPolicy Bypass -File <unzipped>\Install-Fohmixer.ps1 -BundleZip <zip> -BandUser <band account> -MasterUser <master account> -Layout <import output>\layout.json`. Account names, host and paths are passed at run time and never enter the repo, nor the tickets (`public-repo-hygiene.md`; the install's own output leaves the user paths out). The user names are bare local account names (a domain part is refused); the install looks every one up as `<COMPUTERNAME>\<name>` (`Get-FohLocalAccountName` / `Get-FohAccountSid`: the account check, the DACL, the task principal and logon trigger, the task read-back), because Windows looks a bare name up as a domain name first: where an account is named like the computer (as on the PC), `NTAccount('<name>').Translate(...)` hits the PC's account domain and fails "could not be translated" (#9); never translate a bare user name directly. Pass `-BandUserLibrary` / `-MasterUserLibrary` when Live's User Library is not `C:\Users\<user>\Documents\Ableton\User Library` (OneDrive-redirected Documents, a moved library). **Live must use that User Library** (#9): Live lists a remote script only from the User Library its own preferences name, `<profile>\AppData\Roaming\Ableton\Live <version>\Preferences\Library.cfg` (one folder per Live version; the newest by number is the one in use), where `ContentLibrary/UserLibrary/LibraryProject` holds `ProjectPath` (forward slashes) + `ProjectName`. On the PC the master user's had `<UserLibrary />` (none set), so Live never listed FohMixer although the install had copied it. The install reads that file (`Test-FohLiveUserLibrary`, before any change) and refuses an empty or different User Library with the fix to make **in Live** (Settings > Library, the User Library location, restart Live); it never edits Live's preferences. `-BandAbletonPrefs` / `-MasterAbletonPrefs` point at another preferences folder (default `<SystemDrive>\Users\<user>\AppData\Roaming\Ableton`; the self-test passes fake ones), or at one `Live <version>` folder or its `Library.cfg` when a newer, unused Live left its folder behind. The check lives in `FohmixerLivePrefs.ps1`, dot-sourced by `FohmixerPc.psm1` and listed in the bundle. When recording a refusal on a ticket, leave its paths and account names out (it prints them, as the other refusals do). A second run writes nothing but restarts the hub. Errors: one `fohmixer install FAILED: …` line on stderr, exit 1; a failure after the stop starts the hub task again.
- **What it writes** (`-DataDir`, default `C:\ProgramData\fohmixer`, protected DACL: SYSTEM, Administrators, the band user Modify): `app\<version>\` (earlier versions stay for a rollback), `app\current.txt`, `fohmixer-hub.toml` (no `data_dir` key: the hub refuses unknown keys), `layout.json`. The hub adds `secrets\`, `layout-backups\`, `logs\events-YYYY-MM-DD.jsonl` (the event log, #43: UTC days, 60 days kept, 256 MB a day) and `logs\hub.out.log`/`hub.err.log` (the launcher keeps the last 20 starts as `hub.out.<UTC stamp of the run's last write>.log`, `Move-FohHubLog` in `FohmixerHubProcess.ps1`, #43; an older launcher's `.prev` joins them); the scripts add `logs\hub-launch.log`, `logs\hub-stop.log`, `logs\hub-stop.result.json`. Per Live user: `<User Library>\Remote Scripts\FohMixer\`, replaced only when `version.py` differs (Live's `logs\` stays); `Config.py` INSTANCE/PORT always per user. The firewall rule `fohmixer-hub-http`: TCP `<HttpPort>`, Domain + Private profiles (a Public-profile LAN needs the network set to Private). Live's preferences and a running Live are never touched: selecting `FohMixer` in a slot and restarting Live is the owner-present step (design note §4.2).
- **The hub has no `--config`; it reads `FOHMIXER_DATA`** (not the design note's `FOHMIXER_HUB_DATA`; default: the working folder), and `PORT` overrides the toml's port. A task action cannot set a variable, so the task `\fohmixer\fohmixer-hub` runs `conhost.exe --headless powershell.exe … Start-FohmixerHub.ps1` (no window, also where Windows Terminal is the default terminal), which sets `FOHMIXER_DATA`, drops `PORT`, keeps `RUST_LOG` (the debugging switch), and starts the hub with `CREATE_NO_WINDOW | CREATE_NEW_PROCESS_GROUP` (its own windowless console and its own process group, output straight to `logs\`), then waits for it.
- **Stop = Ctrl-Break, never Task Scheduler's End (spec I7).** End has no graceful request for a process without a window, only a hard end; both tasks are registered with `-DisallowHardTerminate`. The install runs `\fohmixer\fohmixer-hub-stop` (`Stop-FohmixerHub.ps1` in the band user's session: a console is reachable only from its own session), waits for `logs\hub-stop.result.json` (conhost passes no exit code on), then up to 10 s for the exit, and fails, never kills, when the hub stays up. The Ctrl-Break goes to the hub's process group (`GenerateConsoleCtrlEvent(CTRL_BREAK_EVENT, <hub pid>)`), never group 0: the sender is attached to the hub's console while it sends, and `AttachConsole`/`FreeConsole` reset its ctrl-handler table to the default one (`SetConsoleCtrlHandler` docs, Remarks), so no handler registered around them protects it: group 0 ended the stop script with `0xC000013A` before it wrote its result (#9). A hub not started by the launcher (no group of its own) is not reached: the install then fails on the 10 s wait, it never kills. `check_integrity.py` bans force-kill verbs in these scripts, comments included.
- **The tray (#39, `crates/fohmixer-tray`, `FohmixerTray.ps1`):** `\fohmixer\fohmixer-tray` runs `app\<version>\fohmixer-tray.exe --data "<DataDir>"` at the band user's logon (the hub task's settings: Interactive, Limited, never ended hard, a failed start restarted 3 x 1 min); the install starts it after the hub answers and waits until it runs (`Start-FohTray`; the result's `tray` is its pid). It reads only `fohmixer-hub.toml` (`http_port`, the `[tls]` name and port) and polls the public `GET /api/version` every 5 s: the instances and the layout need a login, so its tooltip says hub up or down and the hub's version, not the Lives. A left click on the icon opens fohmixer (#68: `show_menu_on_left_click(false)`, `view::click_opens`; a click within `OPEN_GAP_MS` = 800 ms of the last opening one opens nothing, so a double click opens one tab); the right click shows the menu. Menu: the hub's version (disabled), **Open fohmixer** (`http://localhost:<http_port>/` in the default browser), **Tag manual** (#68: the tag manual, `<the same>/znacky.html`), **Copy URL** (`https://<name>/`, disabled without `[tls]`), **Exit** (the tray only). Log: the band user's `%LOCALAPPDATA%\fohmixer\logs\fohmixer-tray.log.<date>` (one line per hub state change and per menu action). **Stop (spec I7):** a second start `fohmixer-tray.exe --exit` hands `--exit` to the running tray (Tauri's single-instance plugin, the same session only) and it exits; the install runs that through `\fohmixer\fohmixer-tray-stop` in the band user's session before it replaces `app\<version>` (the tray first, then the hub), waits 10 s, and fails, never kills, when the tray stays; a failed install starts the tray task again when a tray had run. **Post-deploy proof:** the tray runs in the band user's session from `app\<new version>`, its log has `the hub answers version=<new>`, and Open fohmixer opens the surface on the PC: a `client report` with `peer=127.0.0.1` in `hub.out.log`.
- **Not automatic:** Task Scheduler restarts only a failed start, so a crashed hub stays down until the next logon or `Start-ScheduledTask -TaskPath \fohmixer\ -TaskName fohmixer-hub`.
- **PIN:** the pepper is DPAPI for the hub's user, so `fohmixer-hub pin set-engineer` must run **as the band user** with `FOHMIXER_DATA=<DataDir>` (PIN on stdin, design note §4.5). The same holds for the Cloudflare API token of the ACME client (#17): `fohmixer-hub cloudflare set-token`, as the band user, the token on stdin.
- **Remote access (#17, `FohmixerRemote.ps1`, only with `-PublicName`):** `-PublicName <name> [-HttpsPort 443] [-AcmeEmail] [-AcmeDirectory] [-AccessTeam <team>.cloudflareaccess.com -AccessAud <aud[,aud]>] [-SetTunnelToken] [-CloudflaredExe] [-TunnelMetricsPort 20241] [-TunnelDir] [-HostsFile] [-BandDesktop]`. An update without `-PublicName` keeps it as installed (the toml's remote tables carried over; hosts block, shortcut, firewall rule and service untouched). Refused before any change: a taken `-HttpsPort` (pid 4 = HTTP.sys, e.g. an IIS site), a cloudflared without `tunnel run --token-file` (install a current release), a remote-access parameter without `-PublicName`. **Every install (#17) checks its new toml with the new bundle's hub** (`fohmixer-hub config check <file>`, `Test-FohHubToml`) before the stop: a config the hub would refuse (a plain-http ACME directory, a bad e-mail, a kept `[tls]` port equal to a new `-HttpPort`) never reaches the data folder. The toml gets `[tls]`/`[acme]`/`[access]`/`[tunnel]`; the hosts file a marked block `<name> → 127.0.0.1`; the band user's desktop `fohmixer.url` → `https://<name>/`; the firewall rule `fohmixer-hub-https`. `-SetTunnelToken` reads the cloudflared connector token from stdin (`Get-Content <file> | powershell … -SetTunnelToken`) or a hidden prompt, never argv, into `<ProgramData>\fohmixer-tunnel\tunnel-token` (protected DACL: SYSTEM, Administrators) and runs the service `fohmixer-tunnel` (`tunnel --no-autoupdate --protocol http2 --metrics 127.0.0.1:<port> run --token-file …`, automatic, restarted on failure); later runs keep the stored token. The PC already has an older, disabled `Cloudflared` service: never touched. See `.claude/rules/remote-access.md`.
- **AbleSet's name (#90, `-AbleSetName <name> [-AbleSetAccessAud <aud[,aud]>] [-AbleSetTitle <title>]`, only with `-PublicName`):** the toml gets `[ableset]` last, after `[tunnel]` (`name`; `access_aud` only when given; `title` only when it is not the hub's default `AbleSet`, since a hub before 1.0.0 refuses the key; `upstream` never: the hub's default `http://127.0.0.1:80` is AbleSet's port on the PC), and the hosts block maps both names to 127.0.0.1 (the same marked block, one line each). The hub checks the name (one label beside or under the public name: the same site), never PowerShell. Refused before any change: `-AbleSetName` equal to `-PublicName`, `-AbleSetAccessAud` without `-AccessTeam`, `-AbleSetAccessAud`/`-AbleSetTitle` without `-AbleSetName`, any of them without `-PublicName`. Without `-AbleSetAccessAud` it is the LAN only, and `install.log` says so on one line. An update without `-PublicName` keeps `[ableset]` with the other remote tables; one with `-PublicName` and without `-AbleSetName` removes it (and its hosts line). The install result's `remote.ableset` names it. **The first setup, in this order** (site values at run time only, never in the repo or a ticket):
  1. Cloudflare from the dev box (the name a sibling of the public name, `ableset.<domain>`, never a child: Cloudflare's edge certificate covers one label under the zone, so a child's internet path fails TLS at the edge): `fohmixer_cloudflare.py … --name <public name> --ableset-name <ableset name>` dry-run; it must keep the public name's route and show **no** `REMOVE route` line; then `--apply`, and take the printed `[ableset] access_aud`. `curl -sI https://<ableset name>/` answers 302 to the Access login.
  2. LAN DNS (the router project's workflow): `<ableset name>` as a CNAME to the same local-only name as the public name's entry; `check_lan_dns.py` for each of the two names prints `OK`.
  3. The install (elevated, the last `install.cmd` with the version swapped): the last install's remote parameters plus `-AbleSetName <ableset name> -AbleSetAccessAud <aud>`, no `-SetTunnelToken` (the stored token is kept). `install.log`: the config check OK, `remote.kept` false, the hosts line with both names.
  4. The certificate: the hub's second ACME keeper orders it with the Cloudflare token already set; `/api/status` `ableset.cert` names it, `remote.https` is unchanged.
  5. Read-only checks only (never a tap or a POST inside AbleSet: it runs the live show): TLS by SNI for both names, `/api/status` `ableset` `online`, a `GET` of AbleSet's versions through the LAN path.
- **The Stream Deck tab (#52, `-CompanionHost <host[:port]>`):** the install writes `[companion]` (`host`, `port`, default 16622; the grid, image size and title keep the hub's defaults) between the instances and the remote tables (`Get-FohCompanionToml`); a run without it keeps an installed table verbatim, so a site's `columns`/`rows` added by hand (e.g. to match a Companion emulator's 5 × 3; read its row and column count in Companion's Surfaces tab) survive later installs; after such an edit, run the installer without `-CompanionHost` to check the config and restart the hub gracefully as it is (`Get-FohInstalledCompanionToml`, read from the line before `[companion]` to the next table), and the new hub checks the toml before the stop. The host is site data: pass it at run time; on the PC read Companion's address from Companion Satellite's established connection (`Get-NetTCPConnection -RemotePort 16622 -State Established`), never print it, write it straight into `install.cmd`. The install result's `companion` says whether the table is there. After the install: the hub log's `Stream Deck registered with Companion` with `companion=5.0.7…`, the event log's `deck_link` `up`, `/api/status` `companion.online` and `keys` 32, and the tab with 32 images in a browser (no key pressed: they switch real lights and sockets). One-time owner step in Companion's Surfaces tab: the "fohmixer" surface's start page, or a group with the physical deck.
- **The Pro-Q 4 screen (#71 PR E, `.claude/rules/plugin-window.md`): off on the PC until it is turned on by hand.** The hub's default on Windows is `[eq] backend = "off"`: the detail's cards say "EQ is switched off on the PC.", and nothing opens or touches a plug-in's window. A first install writes no `[eq]` table (the safe default); an update keeps the one it finds (PR H, below). Turning it on, only after `fohmixer-hub.exe eq-probe` passed against Carla's bridge (recorded on #71):
  1. In `<DataDir>\fohmixer-hub.toml`, add the two lines `[eq]` and `backend = "windows"` right after the `[[instances]]` tables, before `[companion]` and `[tls]`. Never put them at the end of the file after `[tls]`: an install keeps everything from `[tls]` to the end as the remote tables, so an `[eq]` there rides with them (kept by an update without `-PublicName`, dropped by one with it) and is never the `[eq]` the install keeps.
  2. Check the file with `fohmixer-hub.exe config check <file>`.
  3. Restart the hub: `\fohmixer\fohmixer-hub-stop` (above), then `Start-ScheduledTask -TaskPath \fohmixer\ -TaskName fohmixer-hub`. The `hub started` line in `logs\hub.out.log` then says `eq=Windows`.
  4. **An update keeps the table** (PR H, from the 0.1.0-dev.52 installer on; before, every install rewrote the file without it, and 0.1.0-dev.49, .50 and .51 each needed the two lines written again): `Resolve-FohEq` reads it from the installed toml (`Get-FohInstalledEqToml`: its lines from `[eq]` to the next table, looked for only before `[tls]`, blank lines dropped, CRLF; the `backend` value as it is, which the new hub checks with the rest of the config before the stop) and `New-FohHubToml` writes it back after the instances, before `[companion]`. `install.log` then says `the [eq] table kept as installed`, and the install result's `eq` is `true`. To turn the screen off again, take the two lines out (or write `backend = "off"`) and do steps 2 and 3; the next install keeps that. The install has no switch for it. The header may carry a comment (`[eq] # …`); the table ends at the next line starting with `[`, so it holds plain keys only (no sub-table, no multi-line array: `[eq]` has `backend` alone today).
  `eq-probe` reads no config: it drives the window backend directly, whatever `[eq]` says.
- **Post-deploy check on the live hub (#9):** fetch the bundle on the PC from `airuleset.py share` (its LAN URL) and compare its SHA-256 with the CI artifact's; an update install without `-PublicName` keeps remote access (`remote.kept`). The install replaces FohMixer in both User Libraries, but a running Live keeps the loaded script until Live restarts (the hub logs `script_version`, it does not enforce it), so a hub-only change needs no Live restart. In Playwright, log in with the PIN through `secret exec --file`, then wait for a settled surface (every visible fader `aria-disabled=false`) before reading states: a snapshot taken while controls still wait for their first values reads as a broken deploy (#58 removed REFRESH ALL, whose automatic run 1 s after load put every control back to `waiting`).
- **The event log (#43) is where a move's path is read:** `logs\events-<UTC date>.jsonl`, one JSON object per line: `set` (the page's `t`, the hub's `hub_ms`, `offset_ms`, `delay_ms`, `gap_ms`), `batch` / `applied` (the batch number, Live's `rtt_ms`) and `ack` per write, a `ping` per page ping (10 a second while a page is visible), `trace` (a page's flight-recorder batch, design note §5.2: its touches — a fader's or pan's down with where it started —, the moves of each frame that sent (`mv`), writes its socket did not take, ack arrivals, a round-trip summary a second (`rtt`), socket transitions, long frames, visibility, dropouts, the dropout counter's resets and what its backlog dropped (`overflow`); `tools/forensics/timeline.py` reads them back, `.claude/rules/forensics.md`); a touch's first `set` carries `live_before` (Live's value before it, #43 PR D), `link` (Live busy changes), `sock` (a socket's open and close with its reason). After a deploy, drag one fader and find `set` → `batch` → `applied` → `ack` of its last `seq` there; read the file with `Get-Content -Tail` (a service day is tens of MB), never whole over MCP.
- **From the `fohmixer` dev account (#43, 0.1.0-dev.27 deploy):** the PC cannot reach `airuleset.py share --private` (its listener is on an address the PC has no route to) and the account has no public drop lane, while the dev box does reach the hub. So the bundle goes over a short-lived `python3 -m http.server <port> --bind <dev box LAN address> --directory <dir>` serving `<random path>/bundle.zip`, run with `timeout` and stopped right after the PC's download; the SHA-256 against the CI artifact is the proof. Stop it by its listener (`ss -ltnp`), never a `pkill -f` whose pattern also matches the calling shell. Start it detached (`setsid nohup timeout <s> python3 -m http.server … < /dev/null & disown`), or the Bash call waits on it; the dev box's saved address file holds the address and a port (`read ADDR PORT < <file>`), never pass the whole line as `--bind`.
- **Keep the deployed build's `wasm-dist` (#43, PR #92):** download the same master run's `wasm-dist` artifact next to the bundle (outside the repo) at every deploy. The shipped page is stripped, so a stack from the real iPad reads `wasm-function[N]`; `scripts/wasm_names.py lookup` against that build's `wasm-dist` names it, and CI keeps the artifact only 7 days.
- **The band Live waiting at "Can't access file database: No Database file found" (#5, 2026-10-12):** it loads neither its set nor the FohMixer script until OK is pressed, so the hub's band link stays down (port refused). Since Live 12.4.6 the band user had no `Live-files-12300.db` in its `AppData\Local\Ableton\Live Database` (the master Live migrated its own from `12201` on its first start; the band's never did, and its own `Ableton Index` never starts while the master's runs). If the message comes back after a Live update, check the two users' Live logs (`Database:` lines) and folders first; press OK only with the owner's yes.
- **The elevated install over MCP (#43, 0.1.0-dev.28 deploy):** the MCP shell runs with a filtered token (not elevated: `WindowsPrincipal.IsInRole(Administrator)` is false). Write a one-line `install.cmd` (ASCII) that runs `powershell -NoProfile -ExecutionPolicy Bypass -File <unzipped>\Install-Fohmixer.ps1 … > <dir>\install.log 2>&1` and then `echo exit=%ERRORLEVEL% >> <dir>\install.log`, start it with `Start-Process cmd.exe -ArgumentList '/c "<dir>\install.cmd"' -Verb RunAs -Wait -PassThru` in the same MCP call, and read `install.log` back (its `fohmixer install:` lines and `exit=`): the elevated process's own output never reaches the MCP shell. Keep each version's download, unzip and log in its own `C:\temp\fohmixer-deploy\<version>` folder.
- **No engineer PIN on the dev account (#43):** for the Playwright check, mint a short-lived engineer token on the PC in one PowerShell call (HS256 over `{"typ":"JWT","alg":"HS256"}` and `{"sub":"engineer","iat":<now>,"exp":<now + 1800>}`, base64url without padding, the HMAC key being the text of `<DataDir>\secrets\jwt_secret`, as `auth::issue_token` does) and POST it to a one-shot receiver on the dev box's LAN address (a random path, writes a mode-600 file, exits); never print it, put it in `localStorage.fohmixer_token` with `addInitScript`, delete the file after. Record that the check ran this way on the ticket, without the address.
- **A deploy check that drags a live fader puts it back (#43):** read Live's value first from the page's own socket (`page.routeWebSocket` + `connectToServer`: the strip's volume is subscribed with its display string, so its `sub` is `<instance>|<target>|value|true`, from `subbed` then `values`), and after the drag send one `set` of that value through the routed socket (`server.send`, a `seq` far above the page's), then read the pushed value back. Print a short hash of the key, never the key (it holds a track name).
- **The forensics timeline on the PC (#43 PR C, `.claude/rules/forensics.md`):** copy the eight files of `tools/forensics/` (`timeline.py`, `timeline_read.py`, `timeline_model.py`, `timeline_touch.py`, `timeline_eq.py` (#71), `timeline_ableset.py` (#90), `timeline_rules.py` (#130), `timeline_report.py`, from the merged commit with `git show <sha>:<path>`) into one folder on the PC, next to the bundle on the same short-lived LAN server, each checked by its SHA-256; the PC's Python is 3.12 (`python` on PATH). Run `python timeline.py --events C:\ProgramData\fohmixer\logs --from "<PC local time>" --to "<PC local time>" --out <the version's deploy folder>\report.html` (the PC's local time is UTC+2 in summer) and read only its stdout summary over MCP (`name=value` lines, keys as hashes); the HTML holds track names and stays on the PC.
- **The touch-diagnosis check (#43 PR D, `verify-d.cjs` in the dev box's work-products):** drag an ORDINARY single-track fader: a fader whose sets name more than one key (a multi-target fader) is put back to each key's value and the next one is tried. Then read the PC's day file over MCP without printing a key: `Get-Content -Tail` → keep lines containing `"ev":"set"` / `"ev":"trace"` → `ConvertFrom-Json` → print only numbers (`seq`, `t`, `live_before`, the down's `dt`/`c`/`travel`/`pos`/`live`/`local`/`from`, `keys.Count`, the `mv` count). Windows PowerShell 5.1 there prints decimals with the PC's comma (`0,85`), and `ConvertTo-Json` of a nested 2-element array gives `{"value":[…],"Count":2}`: read the values, not the shape. The touch's first set carries `live_before`, the next one none.
- **The no-lost-moves check (#43 PR E, `verify-e.cjs`):** after PR D's checks, a 12 s continuous drag of the same fader (`LONG_MS`); the page's own frames must show one `mv` per set (`q` = `seq`), no `overflow` note and no `send`/`ack` event, and it prints `TIMES_E` for the PC's count: in the day file, the key's hub `set` records with `t` in that window against the trace `mv` records of the key (`q` distinct), plus `send`/`ack`/`overflow` page events since the check began, numbers only. **In that PowerShell, give helper functions long names and wrap the whole call in `try { … } catch { "failed: $($_.Exception.GetType().Name)" }`:** an alias beats a function of the same name (a key-hash helper named `H` ran `Get-History`, whose error printed the key it was given, a track name), and an uncaught error echoes its argument.
- **The touch-start check (#43 PR F, `verify-f.cjs`):** on the same single-track fader, a touch dispatched in the page (`PointerEvent`s with a made-up `pointerId`: the fader's `set_pointer_capture` result is ignored, so nothing reaches the console) whose first `pointermove` comes 10 px up 80 ms after the down, then 2 px every 17 ms; the cap, sampled every frame, must stay at its rest on every frame between the first move and the next, and the first `mv` of the touch carries `a` = the down's `from`. On the PC: the day file's first `mv` of the key has `a` = `from`, and `timeline.py` over the window prints `first_moves_anchored=1`, `first_touch_jumps=0`. The dev box's viewport gives a 323 px travel, not the iPad's 207 px.
- **The touch-guard check (#43 PR G, `verify-g.cjs`):** in the page, a dispatched `touchstart` is prevented on a fader, its cap, a pan, a mute and the dropout counter, and not on a row's background or a strip's tag; the cap's `-webkit-user-drag` is `none`. A REAL finger then drags the usual single-track band fader through the DevTools protocol (`Emulation.setTouchEmulationEnabled` + `Input.dispatchTouchEvent`, 30 px in 2 px steps; a fader whose sets name several keys is put back and the next one tried).
