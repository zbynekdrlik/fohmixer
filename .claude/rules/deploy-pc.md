# Deploy on the Ableton PC (S5, `docs/superpowers/specs/2026-09-28-s5-deploy-design.md`)

- **Only a hosted-CI build of `master` is installed.** The `bundle` job (master pushes, after `wasm` + `windows`) uploads `fohmixer-windows-<version>-<sha>`: one zip with `fohmixer-hub.exe` (release, real UI embedded), `FohMixer\`, the `scripts/fohmixer-pc` scripts, `VERSION` and `SHA256SUMS`. `gh run download <run> -n <name>` yields that zip. `New-FohBundle` in `FohmixerPc.psm1` builds it, the module the install itself uses.
- **Install** (elevated Windows PowerShell 5.1 on the PC, e.g. over MCP): unzip the bundle to a temp folder, then `powershell -NoProfile -ExecutionPolicy Bypass -File <unzipped>\Install-Fohmixer.ps1 -BundleZip <zip> -BandUser <band account> -MasterUser <master account> -Layout <import output>\layout.json`. Account names, host and paths are passed at run time and never enter the repo, nor the tickets (`public-repo-hygiene.md`; the install's own output leaves the user paths out). Pass `-BandUserLibrary` / `-MasterUserLibrary` when Live's User Library is not `C:\Users\<user>\Documents\Ableton\User Library` (OneDrive-redirected Documents, a moved library). A second run writes nothing but restarts the hub. Errors: one `fohmixer install FAILED: …` line on stderr, exit 1; a failure after the stop starts the hub task again.
- **What it writes** (`-DataDir`, default `C:\ProgramData\fohmixer`, protected DACL: SYSTEM, Administrators, the band user Modify): `app\<version>\` (earlier versions stay for a rollback), `app\current.txt`, `fohmixer-hub.toml` (no `data_dir` key: the hub refuses unknown keys), `layout.json`. The hub adds `secrets\`, `layout-backups\`, `logs\hub.out.log`/`hub.err.log` (+ `.prev`, rotated per start only); the scripts add `logs\hub-launch.log`, `logs\hub-stop.log`, `logs\hub-stop.result.json`. Per Live user: `<User Library>\Remote Scripts\FohMixer\`, replaced only when `version.py` differs (Live's `logs\` stays); `Config.py` INSTANCE/PORT always per user. The firewall rule `fohmixer-hub-http`: TCP `<HttpPort>`, Domain + Private profiles (a Public-profile LAN needs the network set to Private). Live's preferences and a running Live are never touched: selecting `FohMixer` in a slot and restarting Live is the owner-present step (design note §4.2).
- **The hub has no `--config`; it reads `FOHMIXER_DATA`** (not the design note's `FOHMIXER_HUB_DATA`; default: the working folder), and `PORT` overrides the toml's port. A task action cannot set a variable, so the task `\fohmixer\fohmixer-hub` runs `conhost.exe --headless powershell.exe … Start-FohmixerHub.ps1` (no window, also where Windows Terminal is the default terminal), which sets `FOHMIXER_DATA`, drops `PORT`, keeps `RUST_LOG` (the debugging switch), and starts the hub with `CREATE_NO_WINDOW | CREATE_NEW_PROCESS_GROUP` (its own windowless console and its own process group, output straight to `logs\`), then waits for it.
- **Stop = Ctrl-Break, never Task Scheduler's End (spec I7).** End has no graceful request for a process without a window, only a hard end; both tasks are registered with `-DisallowHardTerminate`. The install runs `\fohmixer\fohmixer-hub-stop` (`Stop-FohmixerHub.ps1` in the band user's session: a console is reachable only from its own session), waits for `logs\hub-stop.result.json` (conhost passes no exit code on), then up to 10 s for the exit, and fails, never kills, when the hub stays up. The Ctrl-Break goes to the hub's process group (`GenerateConsoleCtrlEvent(CTRL_BREAK_EVENT, <hub pid>)`), never group 0: the sender is attached to the hub's console while it sends, and `AttachConsole`/`FreeConsole` reset its ctrl-handler table to the default one (`SetConsoleCtrlHandler` docs, Remarks), so no handler registered around them protects it: group 0 ended the stop script with `0xC000013A` before it wrote its result (#9). A hub not started by the launcher (no group of its own) is not reached: the install then fails on the 10 s wait, it never kills. `check_integrity.py` bans force-kill verbs in these scripts, comments included.
- **Not automatic:** Task Scheduler restarts only a failed start, so a crashed hub stays down until the next logon or `Start-ScheduledTask -TaskPath \fohmixer\ -TaskName fohmixer-hub`.
- **PIN:** the pepper is DPAPI for the hub's user, so `fohmixer-hub pin set-engineer` must run **as the band user** with `FOHMIXER_DATA=<DataDir>` (PIN on stdin, design note §4.5).
- **Rollback:** deselect `FohMixer` in the Live slot; `Disable-ScheduledTask -TaskPath \fohmixer\ -TaskName fohmixer-hub`; `app\<older version>` is still there to reinstall from.
- **Self-test:** `Test-Fohmixer.ps1 -HubExe target\debug\fohmixer-hub.exe`, the last step of the `windows` job. It parses every script, builds a bundle from the checkout, runs `-NoTask` installs as separate `powershell.exe` processes into temp folders (idempotence by file times, a port change, a version bump, refusals that change nothing), starts the real hub through the launcher and stops it through the stop script (both as their tasks run them), registers both tasks in a unique test folder and reads them back, and checks the firewall rule (disabled, removed after) and the DACL. Keep the scripts Windows PowerShell 5.1 and ASCII only (no `??`, `?.`, ternary, `utf8NoBOM`). Zip entries are written by name with `/`: `ZipFile.CreateFromDirectory` keeps `\` under `powershell.exe`. Nothing runs PowerShell locally (no `pwsh` on the dev box), so CI is the check.
