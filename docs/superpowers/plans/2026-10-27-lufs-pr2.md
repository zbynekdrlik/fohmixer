# The LUFS source (PR 2 of #151) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** the strips show loudness. Each PA singer's strip shows its short-term loudness after the Trim IN, judged against −25 LUFS, under the caption `LUFS IN`. The PA return and the output buses show their plain short-term under `LUFS OUT`. An armed PA mic's two meter bars follow its fader. The numbers come from two Max for Live devices without parameters that send their readings to the hub over localhost UDP.

**Architecture:**

- **Two devices, no parameters** (spec §4.2, P1 in §4.3): `FohMixer LUFS` (the existing `gen~` DSP) and `FohMixer Meter` (L/R peaks, last in an armed track's chain). Both output silence and always sit in a rack's parallel chain (the owner, 27.10). Each sends an OSC datagram to `127.0.0.1:39110` (5×/s and 30×/s; the owner, 27.10: was 10×/s). The datagram carries its own id, version, canonical path and track name.
- **The hub listens on 127.0.0.1 only** (`lufs_udp.rs`). The pure parser is `fohmixer_proto::lufs::wire` and the per-key bound is in `rules/lufs/bound.rs`. Readings reach the router as `RouterMsg::Lufs`.
- **A pure rule matches readings to strips** (`rules/lufs.rs`). The path names the track. The `+LUFS` strips (any strip, for a meter device) on that track are the candidates. One confirming LOM read per candidate instance says which Live sent it. The rule also handles staleness, problems and the state log. The glue is `router/lufs.rs`; it does the reads, `LEVELS_CLIENT` and the meter keys.
- **To the pages:** `ServerMsg::Lufs`, paced with the meters (`Outbox`). The strip's `LufsView` takes `fohmixer_proto::lufs::judge`, the shared pure decision. The armed tracks' levels go out on the strip's own meter keys, so the surface does not know the source.
- **Deleted:** the Rust reference DSP `fohmixer_proto::lufs::dsp` and the table half of `scripts/check_lufs_device.py` (the owner, 27.10).

**Tech Stack:** Rust (fohmixer-proto, fohmixer-hub on tokio, fohmixer-ui on Leptos 0.7), Max for Live patches (`.maxpat` JSON, `gen~`), Python 3.11 (SimLive, the device check, the live probe), PowerShell (the PC installer), Playwright (Chromium and the WebKit iPad project).

**Spec:** `docs/superpowers/specs/2026-10-26-lufs-design.md` as revised on 27.10: §3.1, §3.3–§3.4, §4.2, §4.4–§4.5, §5–§9; the rollout is §10. #151's comments of 27.10 are binding: the `lr` re-test, P1's result, and the DECIDED and FINDING comments. The caption's layout is mockup v9 (Task 10), which the owner must approve before Task 11.

## Rulings *(the plan's own calls, each also marked *(call)* in the spec)*

1. **Wire format: OSC 1.0, address `/fohmixer/lufs` or `/fohmixer/meter`, type tags `,iisssii`** (spec §4.4's table). Max's `udpsend` sends only OSC. JSON would need a `js` or `node.script` sender in every device. The parser is our own, about 80 lines, for this one shape. `rosc` was considered and not taken: it brings bundles and time tags for one fixed message, and the mutation gate should judge our parser.
2. **Port 39110, fixed in the patches; the hub's `[lufs] port` defaults to it.** A device cannot read the hub's config. Another port therefore means the devices rebuilt with `build_amxd.py --port <n>` (README). `port = 0` turns the listener off. `check_lufs_device.py` keeps the patches' `udpsend` port equal to `fohmixer_proto::lufs::wire::DEFAULT_PORT`.
3. **The instance is found by a confirming read.** Both Lives send to one port, and Max ids are per process. For each instance with a candidate strip, the hub reads `<device path>` `class_name` and `name` through that instance's script. Exactly one `MxDeviceAudioEffect` named `FohMixer LUFS` / `FohMixer Meter` matches. Both: `two LUFS meters`. None: asked again after that instance's track-list change or 10 s.
4. **A key is `(device id, path, track name)`.** A moved device or a renamed track is a new key, confirmed again; the old one goes stale.
5. **Bounds:** 10/s per `/lufs` key (20/s before the owner's 5×/s of 27.10), 60/s per `/meter` key (twice nominal), 64 keys, 512-byte datagrams. **Stale:** 1000 ms (`/lufs`), 500 ms (`/meter`). The problem `no LUFS meter` appears 3 s after an instance connects or a layout is served (`NO_METER_GRACE_MS`).
6. **The meter device is a sibling** (`FohMixer Meter`, `live-device/FohMixer-Meter/`), not a mode: the two devices sit at different points, and a mode would need a parameter. It carries L/R peaks in tenths of dBFS, −700…120, 30×/s.
7. **The caption is on two lines:** `LUFS` over `IN` / `OUT`, PR 1's caption font. One line does not fit the iPad's 29 px column (estimate). Mockup v9 shows it to the owner before Task 11 (memory "approve layouts").
8. **The tenths travel end to end** (device → `ServerMsg::Lufs` → `judge`). The strip shows `round(tenths / 10)`, half away from zero.
9. **No change to the Live script or its protocol:** the confirming reads are ordinary `get`s. `UI_PROTO` stays 2, as for every `ServerMsg` variant added since #43.

## Revisions after the UDP probe *(27.10, #151 comment "Probe of the UDP path"; binding over the text below)*

1. **No path on the wire.** Max's `live.path` `getpath` echoes the path it was given. The identity is the Max id plus the names of the device's first four canonical parents (`-` past the top); the last named one is the set, the one before it the track (`lufs::wire::track_and_set`). Type tags `,iisssssii`; `track_of`, `TrackRef` and `WireError::Path` are gone, `Identity` and `Trailing` came. Task 9's key is `(device id, parents)`, its `candidates` match by track name and set name, and its confirm walks the track's devices (no path to read).
2. **Silent output, always in a parallel chain (the owner's ruling of 27.10, replacing a brief pass-through).** Both devices feed `plugout~` from a `sig~ 0.` only, and each is ALWAYS placed in a parallel chain of an Audio Effect Rack, never in series: a mic's in `CORE Effects` beside trueLevel, an output point's and an armed track's meter device in a rack of their own (an empty dry chain plus the device's chain). `check_lufs_device.py` refuses anything but silence into `plugout~`. The LUFS face shows `Short-term` and `Voice` big under the caption `LUFS`, the version small (the owner, 27.10).
3. **One datagram per reading:** the patch's `pack` (cold slots, the identity cached) is banged by its `metro`; the device's version travels as `v<version>` (a `pack` argument Max cannot read as a number).
4. **The reference DSP and the table check go** (Task 2, done).

## Review Focus

1. **Two Lives, one port** (Task 9): the band and master sims send the same device id and path. Only the instance whose set holds a `FohMixer LUFS` there is matched. A device at the same place in both sets gives `two LUFS meters` and shows nothing.
2. **The stale boundary** (Tasks 8–9): a key last heard 999 ms ago is fresh and one heard 1000 ms ago is stale. After stale the strip shows nothing within one router tick, and there is exactly one `lost` record.
3. **The bound** (Task 8): a sim flooding 200 datagrams/s from one key delivers at most 20 per second to the router. A second key in the flood is unaffected. Refused datagrams are counted by reason in `/api/status`.
4. **`judge`'s boundaries and the rounding** (Task 4): −21.5 → −22 `fine`, −22.4 → −22 `fine`, −21.6 → −22 `fine`, −18.5 → −19 `warn`.
5. **The armed meter keys** (Task 13): while a meter device is fresh, Live's own values on those keys never reach the page (no flicker between sources). 500 ms after the device stops, Live's values flow again.
6. **The bind address** (Task 8): the socket's local address is `127.0.0.1:<port>`. A config cannot widen it.
