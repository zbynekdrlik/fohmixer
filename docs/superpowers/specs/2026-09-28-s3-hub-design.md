# S3: fohmixer-hub, proto and TouchOSC import, design note

**Ticket:** #7. **Spec:** `docs/superpowers/specs/2026-09-28-fohmixer-program.md` §2.4, §2.5 (layout and binding), §2.6, §2.7, §3.2.

**Inputs**
- The S2 script and SimLive host (`sim/host.py`): the S2 design note §3.10 envelope.
- K3 triage on #5.
- iemmixer server pieces: auth, login guard, pepper, secrets, static routes, graceful stop.

## 1. Goal

A thin hub that connects to N FohMixer instances, fans the LOM out to many clients, serves the UI and the layout, and runs the one STAGE AUT rule. Plus a one-shot import tool that turns the TouchOSC project and the band set's MIDI mappings into the layout document.

**Done means**
- Hub integration tests run against **real `sim/host.py` processes** (band and master) and pass in CI. They cover:
  - pass-through;
  - dedupe (two clients, one Live listener);
  - resync after a host restart;
  - busy from heartbeat;
  - a slow client does not stall others;
  - STAGE AUT;
  - layout validation with last-good fallback;
  - auth.
- The import tool produces a valid layout from a synthetic `.tosc` + `.als` fixture, and its report lists the drops.

## 2. Crates and files

- **`fohmixer-proto`** (WASM-safe; the UI uses it too):
  - client protocol types (§3);
  - layout document types (§5), with `serde` and `validate() -> Vec<LayoutError>`.
- **`fohmixer-hub`:**
  - `config.rs`: TOML config in `<data>/fohmixer-hub.toml`: `http_port` (8480), `instances = [{name, port}]`, `layout = "layout.json"`.
  - `live/client.rs`: one task per instance. It uses tokio-tungstenite, reconnects with backoff 250 ms doubling to 2 s, correlates by uuid, and tracks `status {online, busy, main_tick_age_ms, set_name, live_version, script_version}`.
  - `live/subs.rs`: the subscription table.
  - `ws.rs`: the client WebSocket with per-client latest-value coalescing.
  - `rules.rs`: STAGE AUT.
  - `layout.rs`: load, validate, last-good, backups, mtime poll every 2 s.
  - `auth.rs`, `login_guard.rs`, `pin_hash.rs`, `pin_store.rs`, `pepper*`, `secrets.rs`, `provision.rs`: copied from iemmixer, engineer role only.
  - `routes.rs`: from S0, plus `/api/layout`, `/api/auth` and `/api/status`.
- **`tools/import-tosc/`** (Python standard library, deleted at S6):
  - `import_tosc.py <file.tosc> --set <FOH.als> --out layout.json --report report.md`;
  - tests on synthetic fixtures `tools/import-tosc/fixtures/test.tosc` and `test.als`, both generated by a fixture builder script in the same folder so they stay reviewable.

## 3. Client protocol (hub ⇄ UI)

This is JSON over `/ws?token=<jwt>&proto=1`. The first server message is `Hello{proto, build, min_client_proto}`, as in iemmixer.

**Client → hub**

| Message | Shape |
|---|---|
| Command batch | `{"type":"cmd","id":"<client-uuid>","instance":"band","commands":[{target,name,args}]}`. Forwarded as-is (script envelope §3.10). The reply is `{"type":"result","id",data:[slots]}` |
| Subscribe | `{"type":"sub","instance","target","prop","display"?}`. Deduplicated in the hub. The reply is `{"type":"subbed","sub":"<hub-key>","value","display"?}` or an error |
| Unsubscribe | `{"type":"unsub","sub"}` |
| Hub value | `{"type":"set_hub","key":"stage_aut","value":true}` |

**Hub → client**

| Message | Shape |
|---|---|
| Values | `{"type":"values","items":[{"sub","value","display"?}\|{"sub","error"}]}`, coalesced per client |
| Instance status | `{"type":"instance","name","online","busy","set_name"}`, sent on change |
| Hub values | `{"type":"hub","key","value"}` (STAGE AUT) |
| Layout | `{"type":"layout","rev"}` when the layout changed; the UI then GETs `/api/layout` |

A hub key is `instance|target|prop|display`, with `target` normalised (whitespace collapsed).

## 4. Subscriptions and resync

- **First subscriber:** the hub sends `add_listener` to the instance and records the Live key. It caches `value`/`display`.
- **Later subscribers:** get the cached value at once. This is how I8 is served: the UI enables a control only after its first value arrives.
- **Last unsubscribe:** the hub sends `remove_listener`.
- **Live `values` push:** the Live key is mapped to the hub key; the cache is updated; every subscribed client's pending map is updated.
- **Instance disconnect / reconnect:**
  - Mark offline and broadcast the status.
  - On `connect`, re-send `add_listener` for every hub key, using the **original target** (a name path), because ids from the old session are invalid.
  - A failure gives `{"sub","error"}` to the subscribers; the UI shows red (I5).
- **Busy:** `main_tick_age_ms > 150` or no heartbeat for 300 ms.

## 5. Layout document (`layout.json`, schema version 1)

**Top level:**
```
{ "schema": 1,
  "canvas": {"w":2360,"h":1640},
  "pages": [Page],
  "overlay": [Item],
  "config": {"unfold": [...], ...},
  "report": {...} }
```

- **Page:** `{id, title, tab:{color, text_size}, items:[Item], pager?: {orientation, bar_size, pages:[Page]}}`.
- **Item:** `{kind, frame:{x,y,w,h} (canvas coordinates), z, style:{bg?, color?, text?, ...}, ...kind fields}`. The kinds:
  - `area` (a box with an optional vertical title);
  - `strip`: `{binding, strip_kind: standard|narrow|return|solid|meter_mute_only, children: {fader?,pan?,mute?,meter?,status?,db?,label?,instance_label?: frame}, mute_guard: bool}`;
  - `solo`: `{binding}`;
  - `stage`: `{binding, aut: true}`;
  - `param_toggle`: `{label, targets:[{binding, prop, on, off}], press: "toggle"|"double_tap_latch"|"pulse_and_double_tap_latch"}`;
  - `param_fader`: `{label, targets:[{binding, prop, scale:"cc_linear"}]}`;
  - `alert`: `{binding (TechAlert mute), period_ms: 300}`;
  - `refresh`;
  - `label`.
- **binding:** `{instance, anchor:{track|return|master|song, name?}, path?: "devices[name=…] parameters 1"}`. This is the spec §2.5 general form.

`validate()` checks:
- the schema version;
- unique ids;
- frames inside the canvas;
- known kinds;
- well-formed bindings (the `path` grammar of S2 §3.1);
- `param_*` targets having `prop`.

The hub keeps the last good file in memory, writes `layout.json.<UTC timestamp>` backups when it accepts a changed file, and keeps 30 backups.

## 6. STAGE AUT rule

- The flag is persisted in `<data>/hub-state.json` and exposed as hub value `stage_aut`.
- The target is the first `stage` item's binding in the layout: `mute` of the stage-mic track.
- The hub subscribes to `live_set is_playing` on that instance. On every change while the flag is on, it sends `set_prop mute` = `is_playing` (playing → muted, stopped → live). The action is logged at INFO, one line per change.
- Turning the flag on applies the rule once immediately.

## 7. Import tool

It implements spec §2.6. It classifies by role, composes frames into canvas coordinates, builds the script-hash table from the file itself, and produces:
- the root overlay;
- the pager tab bar;
- strip kinds with per-child geometry;
- the `Conf` config;
- the parameter toggles and faders from the K3 triage, read from the `.als` `KeyMidi` entries:
  - channel 0-based, 13 = MIDI channel 14;
  - on/off thresholds 64–127 give `on:true/off:false` on the activator, written as a mute inversion (activator on = unmuted);
  - continuous full range gives `cc_linear`;
  - rack macro gives `devices[name=Latencies] parameters 1` with values 0/127 (read from the mapping target's device name).
- **Drops go into `report`:** unmapped (CC28, CC65, note 29), ambiguous, stale config names, off-canvas and hidden nodes, and the page-change message.

## 8. Proof

**Rust unit tests**
- proto: layout (de)serialisation and `validate` cases;
- hub: key normalisation, coalescing, busy thresholds, STAGE AUT decisions (pure function `stage_rule(flag, is_playing) -> Option<bool>`), config parsing, layout last-good.

**Rust integration tests** (`crates/fohmixer-hub/tests/live.rs`):
- spawn `python3 sim/host.py` for band (port P) and master (P+1);
- start the hub on an ephemeral port;
- drive it with a tokio-tungstenite client.

The cases:
- pass-through get/set;
- two clients on one subscription → one Live listener (checked via a `describe`-free probe: SimLive exposes `value_has_listener` through `get_prop`);
- a host kill and restart gives offline, then online, then a resubscribed value;
- `stall 400` on the host stdin gives `busy` true and then false;
- a client that stops reading does not delay another client's push by more than 50 ms;
- the STAGE AUT flag on plus `start_playing` gives mute true;
- a layout file replaced with an invalid one keeps the old one served and reports an error;
- auth: 401 without a token, and a login with the provisioned PIN.

**Python tests** for the import tool on the fixtures.

**CI:** the Rust `test` job needs `python3` and `websockets` for the host. That is already present on ubuntu runners; the job installs `requirements-dev.txt`.
