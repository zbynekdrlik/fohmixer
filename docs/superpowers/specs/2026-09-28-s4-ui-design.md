## 1. Goal

The engineer's touch surface, reproducing the TouchOSC surface from the imported layout. It is fast, keeps several faders movable at once, and every control shows Live's real state before it accepts input.

**Done means.** Playwright E2E runs in CI in two projects:
- Chromium desktop;
- WebKit iPad Pro 11 landscape with touch.

It runs against the real hub and two real `sim/host.py` instances (band, master) with a synthetic layout. It covers F1–F16 and F19–F22, then F17 and F18. The console guard is on for every test.

## 2. Rendering model

**Stage**
- The stage is one `<div class="stage">` of the layout canvas size (2360×1640).
- It is scaled to the viewport with `transform: scale(s)`, where `s = min(vw/2360, vh/1640)`, and centred.
- Every item is absolutely positioned from its `frame`, and node order sets `z-index`.

**Controls**
- Controls are DOM elements.
- Moving parts (fader cap, pan dot, meter fill) are updated **only** through `style.transform` / `--level` from **one shared `requestAnimationFrame` loop** (iemmixer's `meter.rs` registry pattern).
- A value change never re-renders the view tree. Signals hold values; the rAF loop reads them.

**Meters**
- Meters draw on one `<canvas>` per visible page, layered under the controls. The same rAF loop draws them.
- Ballistics: 300 ms rise with ease-out, 200 ms linear fall. Colour follows the PAR-15 thresholds on the fader scale (≥ −3 red, ≥ −12 yellow, else green), smoothed by 0.3.

**Colours and fonts** come from the layout `style`. Solid fills replace the TouchOSC workarounds.

## 3. Input model

**Pointer handling**
- Pointer Events only, with `touch-action: none` on the stage.
- Each fader, pan or toggle handles `pointerdown`, `pointermove`, `pointerup` and `pointercancel` itself, and calls `setPointerCapture(pointerId)`.
- A per-control `active_pointer: Option<i32>` is kept. Several faders can therefore move at once, each with its own pointer.

**Fader** (F8–F10)
- Position *p* ↔ Live value *v*: `v = p^0.515`, `p = v^(1/0.515)`. Movement is relative, with no jump on grab.
- Touch shaping (F9, X3) is a pure state machine `Shaper` ported from `fader_script.lua` 2.5.4:
  - 0.1 dB minimum first step (binary search, ε 1e-4);
  - reaction compensation 0.3 / 0.5 / 0.7;
  - gradual ×0.9 → ×1.0 over 10 moves, and ×0.85 in the 0.7–1.0 range;
  - emergency bypass above 3 %, released below 1.5 %.
- Shaping is on when layout `config.fader_shaping` is true (default true).
- Double-tap: a tap is movement < 0.01 and < 200 ms; two taps 50–250 ms apart start a time-based glide at 0.3 position/s to *v* = 0.85; a touch cancels it.
- Sends are coalesced to one `set_prop value` per animation frame while the control is touched. The final value is sent on `pointerup`.
- Echo handling (I4): while the control is touched, incoming values are stored but not shown. On release, the control snaps to the latest Live value after `config.post_release_ms`: 1000 with shaping on, 100 with it off.

**Pan** (F11). `panning = 2p − 1`. Two releases within 300 ms centre it. Grey `#646464` when centred (|p − 0.5| ≤ 0.01), otherwise `#34C1DC`.

**Mute** (F12)
- The `mute` property (`true` = muted). The control is lit when the track is audible.
- `mute_guard` requires a second tap within 500 ms to apply. The first tap arms: a visible pulse, then it reverts.

**Solo** (F14). The `solo` property of its track. Independent toggles. `#3D61B8` when on, `#3C3C3C` when off.

**Stage mics** (F15)
- The mute of the stage-mic track, lit while the mics are live (`mute` false) like every strip's mute and TouchOSC's button; an unknown state stays dark (#9: it was built lit while muted).
- The STAGE AUT toggle is the hub value `stage_aut` (`set_hub`). The hub runs the rule; the UI only shows the flag and the real mute.

**Former MIDI controls** (F17, F18, after the core)
- `ParamToggle`: its targets are written directly.
  - The shown state comes from the targets: all on → lit; all off → dim; mixed → a half-lit "mixed" style.
  - A tap sets every target to "on" (or all to "off" when all are on).
  - `press` modes follow design §5 of S3: `toggle`, `double_tap_latch` (only a double-tap within 200 ms flips), `pulse_and_double_tap_latch` (a tap sends on-then-off, i.e. mute then unmute; a double-tap latches).
- `ParamFader`: position = LOM value of the targets = CC/127 semantics; it writes every target. Its label shows Live's `display` of the first target (X10).

**Refresh** (F6)
- The REFRESH ALL button (0.5 s debounce, 300 ms yellow flash) and the automatic refresh 1 s after load do the same thing:
  1. unsubscribe all;
  2. `set_prop fold_state false` for every `config.unfold` group;
  3. resubscribe all.
- Every control is disabled until its first value arrives (I8).

**TechAlert** (F16). A full-screen overlay (12 % red) toggles every 300 ms while the TechAlert track's `mute` is false.

**Status pill** (F5). Red when unbound. Yellow for < 150 ms after any value for that strip, fading to green by 500 ms.

**Strip label** (F4). The first word of the name, after dropping a leading `X-`. The instance label sits under it.

## 4. Binding and data flow

**Store.** `LiveStore` (a Leptos context) owns:
- the hub WebSocket, with reconnect < 2 s that never gives up;
- the `Hello` handshake;
- the subscriptions map `sub → RwSignal<Option<Value>>` plus `display`;
- the instance status signals;
- the hub values.

**Binding a component**
- A component asks `store.bind(binding, prop, display)`. That builds the target string:
  - `live_set tracks[name=<name>] <path>` for a track anchor;
  - `return_tracks[…]` for a return anchor;
  - `master_track` for master;
  - `live_set` for song.
- The store deduplicates it (one `sub` per key), returns a signal, and unsubscribes when the last user is dropped.
- **Errors** (`{"sub","error"}` or a failed `sub`) mark the binding unresolved: the control is disabled and the strip turns red (I5). The store retries the binding on the next refresh, instance reconnect or layout change.
- **Meters.** `config.meter_source`: `"level"` (default, parity) subscribes to `output_meter_level`; `"lr"` subscribes to left and right.
- **Commands.** `store.set(binding, prop, value)` sends a `cmd` with `set_prop`; a failed slot is shown as a brief red flash on that control.

## 5. Pages and navigation

- The top tab bar comes from the layout pages (60 px high, per PAR-01).
- The nested pager is a vertical tab bar with its own tabs.
- The root overlay layer is always visible.
- The selected page is kept in `localStorage`, wrapped in try/catch.
- Only the visible page's controls are subscribed. Hidden pages unsubscribe, which saves Live listeners. The overlay and TechAlert stay subscribed.

## 6. Login, version, connection

- `/login` is a PIN pad (the iemmixer engineer login). The JWT goes to `localStorage`, and a 401 sends the user back to login.
- A small version label (`data-testid="version"`) sits in the stage corner, top-right over the tab bar, and on the Conf page.
- Connection badges per instance: a green, red or amber (busy) dot with the instance name, in the tab bar.

## 7. Proof

**Rust unit tests** (native, `cargo test -p fohmixer-ui --lib`), for the pure modules:
- fader law;
- the `Shaper` state machine, with a trace from the Lua reference;
- tap and double-tap detection;
- mute guard;
- pan mapping and colour;
- the meter ballistics and colour;
- strip label;
- `ParamToggle` state aggregation (on/off/mixed) and the press modes;
- target string building;
- the page subscription set.

**Playwright E2E** (`e2e/tests/*.spec.ts`)
- **Harness.** The e2e job starts two `sim/host.py` instances and the hub with a test config and `e2e/fixtures/layout.json`. The layout is generated by the S3 import tool from its synthetic fixture and committed, so a mismatch fails CI through `git diff`.
- **Tests:**
  - pages and tabs;
  - bound, unbound and renamed strips;
  - a fader drag changes the host value, read through a test-only hub endpoint (or a second WebSocket client in the test);
  - two-finger simultaneous drag in both projects:
    - Chromium via CDP `Input.dispatchTouchEvent`;
    - WebKit by dispatching `PointerEvent`s with distinct `pointerId`s;
  - double-tap to 0 dB;
  - mute guard;
  - solo;
  - STAGE AUT with a host `start_playing` (a hub test endpoint, or host stdin via the harness);
  - TechAlert blink;
  - refresh;
  - I8: controls disabled until the first value, and after a host restart;
  - busy badge during a host stall;
  - the version label equals `/api/version`;
  - login;
  - a zero-console-errors assertion in every test.

## 9. Deviations (see the decisions on #8)

What was built differs from this note in these points; the reasons are on the ticket.

- **Meters (§2)** are DOM bars (a fill scaled by `transform: scaleY`, its colour set) in the shared rAF loop, not one canvas per page. The E2E suite reads the level from `data-level`.
- **Subscriptions (§4)** come from one pure function, `binding::visible_subs(layout, pages on screen)`; `LiveStore::set_wanted` sends only the difference (`unsub`/`sub`). There is no `store.bind()` and no Drop-based release. Every component takes its subscriptions from the same `binding` functions (`strip_subs`, `solo_sub`, `mute_sub`, `param_subs`) that `item_subs` uses.
- **Unresolved bindings (§4, I5)** are `Slot::Error`. Every control bound to one carries `data-binding="unresolved"`, is red and disabled (`store::Readiness`); a `ParamFader` takes input only while every target has Live's value and its range.
- **The connection (§4)**: its decisions live in a pure, unit-tested `store::conn::Conn` (reconnect schedule, hello, the watchdog, layout and instance changes); `store::live::LiveStore` carries them out. After the hello the page pings the hub every second (`ping`/`pong` in the client protocol); a socket silent for 3 s is replaced. A reconnect replaces the layout only when it changed, so controls under a finger survive it (I4). Parameter ranges are read again when an instance comes back online, loads another set or is no longer busy.
- **The E2E harness (§7)** serves the import tool's own fixture, `tools/import-tosc/fixtures/expected-layout.json`, with no committed copy under `e2e/`. `e2e/harness/harness.py` starts the two hosts and the hub, and its control API (stall, rename, host and hub restarts, a layout swap) replaces test-only hub endpoints; the tests read and write Live through a second WebSocket client.
